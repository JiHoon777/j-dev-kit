# 리뷰 원칙

`/start`의 리뷰 단계가 리뷰 에이전트와 판정 에이전트에 넣는다. 그대로 둔 지적과 사용자가 바로잡은 것에서 모은다.

- 기준 판(기준 브랜치, 그 판의 파일)을 구하지 못하면 조용히 넘어가지 말고 그렇다고 알린다 — 판정이 무엇에 대고 한 것인지 모르게 된다. 두 번 빠뜨렸다 (009, 010)
- 리뷰용 개발 서버는 끄지 않아도 된다 — 포트가 항목마다 달라 다른 항목과 부딪히지 않는다 (006)
- 테스트를 돌리는 스크립트는 테스트마다 시간 제한을 둔다 — 멈춘 테스트 하나가 검증이나 Stop 훅 전체를 취소시킨다. 두 번 빠뜨렸다 (009, 011)
- AC 와 사용자가 답한 것이 명시적으로 정한 삭제나 범위는 그 자체로 버그로 보지 않는다 — 사용자가 정한 것이다. 바꿔야 할 근거가 있으면 지적이 아니라 결정을 다시 볼지 묻는 것으로 올린다. Claude 가 스스로 정한 것(항목의 `### 정한 것`, 계획)은 여기에 들지 않는다. 리뷰 대상이다 (012, 016)
- 후보를 거르는 판정에는 "애매하면 떨어뜨린다"를 쓰지 않는다 — 사실이 맞는 후보까지 숨겨 사용자가 고르지 못한다. 근거 약함으로 표시해 남긴다 (013)
- 플러그인 절차는 사용자 저장소의 무시 목록(`.gitignore`, `.git/info/exclude`)을 대신 고치지 않는다 — 추적되지 않은 파일은 git 에 보이고 사용자가 처리한다 (013). 이 키트가 메모와 기록을 두는 `.claude/.local/`을 `.gitignore`에 더하는 것은 예외로 된다 (사용자, 2026-11-27)
- eval 사례는 `skill-creator`의 사례 형식(`expected_outcome`, 번호 붙인 채점 파일, `focus: trace`·`weight: 1`)을 따른다 — 사용자가 정했다 (013)
