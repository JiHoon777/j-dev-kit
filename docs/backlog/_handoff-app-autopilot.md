# 인수인계: 앱 하나를 아이디어부터 자동으로 완성하는 워크플로우

작성: 2026-11-20 · 기준 커밋: 23bc6c7 · 상태: 검토만 했고 아무것도 만들지 않음

## 하려는 것

1. 사용자가 앱 아이디어와 예시를 말한다.
2. 아키텍처와 앱 완성을 위한 기획을 만든다.
3. 필요한 화면의 시안을 만들고, 화면 작업 때 참고하게 한다.
4. 최상위 세션 하나가 역할을 나눠 하위 세션에 일을 맡긴다. 하위 세션은 보고하고, 끝나면 최상위 세션에 완료 처리를 요청한다.
5. 주기적으로 QA 전문 세션이 각 영역을 QA 하고, 나온 것을 백로그로 만들어 다시 하위 세션에 맡긴다.
6. 이 과정이 자동으로 반복되어 앱이 완성된다. 사용자 확인이 꼭 필요하지 않은 것은 최상위 세션이 스스로 정하고 알림만 보낸다.

질문: Claude Code 앱만으로 충분한가, 연동된 대시보드 앱(웹)을 만들어야 하는가?

## 결론

- Claude Code 앱만으로 대부분 된다. 지휘·실행을 하는 별도 대시보드 앱은 만들지 않는다.
- 대시보드가 쓸모 있는 것은 "보는 화면"뿐이다. 백로그 상태, 돌고 있는 세션, QA 결과, 시안을 한 페이지로 보는 것. 원장(`docs/backlog`, 제안함, git)을 읽어 그리는 Artifact 페이지나 플러그인 출력이면 된다.
- 먼저 할 것은 대시보드가 아니라 **자동 판단 정책**, **QA 역할**, **킥오프 흐름**이다.

## 단계별 현황

| 단계 | 지금 쓸 수 있는 것 | 빈 곳 |
| --- | --- | --- |
| 1. 아이디어 입력 | 최상위 세션(`/lead`) | 없음 |
| 2. 아키텍처·기획 | `/arch design`, `/task create` | 둘을 잇는 킥오프 흐름 |
| 3. 화면 시안 | `/ui system`, `/ui mockup`, DESIGN.md, `design-reviewer` | 시안을 항목에 잇는 규칙 |
| 4. 위임과 보고 | `/lead run`(세션 띄우기, 세션 간 메시지, 끝나면 상위 세션 깨우기) | 없음. 002 를 이 방식으로 끝까지 돌렸다 |
| 5. 주기 QA → 백로그 → 재위임 | `/lead schedule` + scout, `frontend-evaluator`, `design-reviewer` | QA 역할 에이전트. scout 처럼 제안함에 쓰게 하면 된다 |
| 6. 자동 반복, 스스로 판단 | 알림은 `PushNotification` | 가장 큰 빈 곳. 지금은 계획·리뷰·머지를 모두 사용자에게 묻는다 |

## 앱만으로 할 때의 한계 (확인한 것)

- 세션 안 예약(CronCreate, `/loop`)은 세션이 열려 있고 쉬고 있을 때만 돌고 7일 뒤 만료된다.
- 앱의 예약 작업은 실행마다 새 세션을 만들고 결과를 상위 세션에 돌려주지 않는다. 그래서 보고는 파일(백로그, 제안함)에 쓰고 상위 세션이 읽는 방식으로 푼다.
- 세션 간 메시지는 보고이지 승인이 아니다(앱의 설계). 상위 세션이 스스로 정하게 하려면 무엇을 정해도 되는지 정책을 미리 정해야 한다.
- 002 를 돌릴 때 리뷰 진행 알림으로 상위 세션이 여섯 번 깨어났다. 항목이 늘면 전체를 한눈에 보기 어렵다.

## 클라우드 대안: Projects (public beta)

요구 구조와 거의 같은 제품이다. 대화 하나가 코디네이터가 되고, 작업마다 클라우드 thread 가 PR 을 열고, Overview 패널·예약 작업·데스크톱 알림이 들어 있으며, 컴퓨터가 꺼져도 돈다.

대가: 클라우드 thread 는 로컬 스킬을 읽지 않아 플러그인을 Project settings 에 넣어야 한다. 백로그가 푸시되어 있어야 보인다. Pro·Max·Ultra 만 된다. 코디네이터는 전체 기록이 아니라 최근 내용과 메모리로 일한다. 클라우드 예약의 최소 주기는 1시간이다.

## 대시보드 판단

- 실행을 하는 앱(Agent SDK 로 세션을 띄우는 웹앱)은 앱과 Projects 가 이미 하는 세션 관리, 권한, 알림, 워크트리를 다시 만드는 일이다. 남에게 팔 제품이 아니면 불필요하다.
- 보기만 하는 화면은 쓸모 있다. 앱이 아니라 원장을 읽는 페이지 하나로 만든다.

## 정말 어려운 곳: 6번

서베이 결론은 같다. 완전 자동화의 한계는 누가 "끝났다"고 판정하느냐다.

- 상위 세션이 스스로 승인하면 작성자와 판정자가 같은 모델이 되어 판정이 관대해진다.
- 공개된 무인 사례는 모두 강한 판정 기준(오라클)이 있었다: 작성자가 볼 수 없는 시나리오(홀드아웃), 기준 구현, 포괄적 테스트.
- 사람 게이트는 거의 모든 곳에서 계획 승인과 머지 승인 두 곳에 남는다.
- 워커 수는 처리량이 아니라 사람의 검수 용량에 맞춘다. 여러 세션이 동시에 코드를 쓰면 손해이고, 읽기·조사·리뷰를 나누면 이득이다.

## 다음에 할 일

먼저 정할 것: **플러그인 확장으로 갈지, Projects 를 먼저 시험해 볼지.**

플러그인 확장으로 가면 순서는 이렇다. 메모리 규칙대로 서베이를 보강하고 계획을 승인받은 뒤 만든다.

1. **자동 판단 정책:** 상위 세션이 정하고 알림만 보낼 결정과 꼭 물을 결정을 나눈다. 예: 🟡 없고 검증이 모두 통과한 머지, 작은 항목의 계획 승인.
2. **QA 역할 에이전트:** 주기적으로 돌아 QA 결과를 제안함에 쓴다. `frontend-evaluator`, `design-reviewer` 를 재료로 쓴다.
3. **킥오프 흐름:** `/arch design` → `/ui system`·`/ui mockup` → 항목 만들기를 잇는다.
4. (필요하면) 원장을 읽는 보기 화면.

## 함께 볼 것

- 근거 서베이 두 편은 회사 PC 의 `.claude/.local/reports/` 에만 있다(커밋하지 않음): `세션 오케스트레이션 자동화 서베이.md`, `AI 코딩 작업 전체 자동화 서베이.md`. 위 결론의 요지는 이 문서에 옮겨 두었다.
- 제안함(`_proposals.md`)도 커밋하지 않아 집에는 없다. 이 일과 이어지는 제안:
  - **작성자가 볼 수 없는 판정 기준(홀드아웃)** — AC 와 테스트를 구현 에이전트가 직접 보고 쓰므로 루프에 홀드아웃이 없다. 6번의 핵심이다.
  - **검증 훅 시나리오 테스트** — `plugins/workflow/hooks/verify-on-stop.sh` 판정에 테스트가 없다. 자동 판단에 기대려면 먼저 믿을 수 있어야 한다.
  - **플러그인 업데이트 뒤 옛 경로를 보는 예약** — 예약 프롬프트에 버전이 든 경로가 들어가 업데이트 뒤 다시 걸어야 한다. 주기 실행에 기대려면 풀어야 한다.
  - 그 밖에 남아 있던 제안: 항목 번호 겹침 막기, 반대쪽 짝 검사, dependencies 일치 검사.
