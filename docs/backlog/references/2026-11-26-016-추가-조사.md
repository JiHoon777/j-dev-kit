## 2. `/until-done`은 왜 안 쓰였나

**규칙이 틀려서가 아니라, 켜 보지 않은 채 지워졌다.** 확신은 중간이다. 노트: `research_notes/…/until-done.md`

- 이 맥의 세션 기록 370개에서 `/until-done`·`/auto`를 부른 기록은 0번이다. 같은 방법으로 세면 `/task`는 입력 24번, 호출 28번이다.
- 켜는 비용이 컸다. 사용자가 직접 쳐야 했고, 끝 조건을 인자로 줘야 했고, `/goal` 한 줄을 따로 붙여 넣어야 했다(`219f092` SKILL.md `:5`, `:19`, `:21-27`).
- main 에 있던 기간은 약 43시간이다(`41037a2` → `3603f93`). 006 은 여섯 가지를 한꺼번에 지운 정리였다.
- 016 에 주는 뜻: 모드를 따로 두지 않고 기본값을 바꾸는 방향은 맞다. 하지만 선례가 규칙을 검증해 주지는 않는다. AC #11 의 측정이 유일한 검증이다.
- **새로 알게 된 것:** simplify 질문 두 번은 사용자가 11-25 에 직접 넣었다(`fa91c89`, "항상 묻도록 하라고 내가 지시했다"). AC #5 는 이것을 지운다. 기록에서는 7번 물었고, 사용자가 내용을 바꾼 것은 1번이다.

## 4. 플랜 모드 없이 "답 전에 고치지 않기"

Claude Code 공식 문서를 읽었다. 노트: `research_notes/…/edit-guard-and-approval-relay.md`

- **추천: 순서로 지킨다.** 착수 전 질문은 부모 세션에서 묻고, 답을 받은 뒤에 워크트리·브랜치·하위 세션을 만든다. 답 전에는 고칠 곳이 없다. 앞선 서베이의 추론과 문서가 맞는다.
  - 서브에이전트는 AskUserQuestion 을 쓸 수 없다. 그래서 질문은 어차피 메인 세션에서 해야 한다(sub-agents 문서).
- 도구로 막고 싶다면 플러그인 `hooks.json`의 PreToolUse 훅이 있다. 세션별 플래그 파일이 있으면 Edit·Write·Bash 를 막는 방식이다. 플래그가 남으면 막히는 위험이 있어 지금은 권하지 않는다.
- 주의: 사용자가 `askUserQuestionTimeout`을 켜 두면 답 없이 스스로 판단해 진행한다. 스킬이 통제할 수 없다.
- **승인 중계의 한계는 문서로 확인했다.** 세션 사이 메시지는 승인·동의가 되지 않는다(cross-session-messaging, agent-teams 문서). 부모가 받은 "머지해"를 하위 세션에 전해도 하위 세션은 그것을 승인으로 쓸 수 없다. 머지는 사용자가 답한 세션에서 하거나, 하위 세션의 권한 프롬프트에 사람이 답해야 한다. AC #8 에 이것을 넣어야 한다.

## 사용자가 정한 것 (2026-11-26, 이 조사를 본 뒤)

- 위 표에서 AC #8(머지는 답한 세션에서)과 AC #2 (나)(착수 전 질문을 하위 세션을 띄우기 전에 부모 세션에서)는 **넣지 않는다.** 사용자가 거절했다. 실제로 부모 세션이 전한 "머지해"로 하위 세션이 머지해 왔고 문제가 없었다. 착수 전 질문은 지금처럼 하위 세션이 묻는다. 4절의 문서 내용은 조사 기록으로만 남긴다.
- 나머지 행은 016 항목에 넣었다.
- **superpowers 를 쓰지 않는다.** 3절의 "부를지, 미리 답해 넘길지"는 필요 없어졌다. 다섯 스킬에서 필요한 규칙만 `/task`에 직접 적고, 플러그인 의존성에서 뺀다(016 AC #9).
- **simplify 는 묻지 않고 늘 찾기만 모드로 돈다.** 찾은 것은 end 의 마지막 메시지에서 고칠지 고른다(016 AC #5). 11-25 의 "항상 확인한다"는 이렇게 지킨다.
- **start 와 end 를 합친다.** `/task start` 하나가 구현부터 리뷰, 머지 질문까지 한다. `end` 모드는 없다(016 AC #12). 1절의 "end 를 진행할까요?" 6번은 이렇게 없앤다.
- **푸시:** 묻는 것은 기준 브랜치·배포 브랜치로 가는 푸시뿐이다. 그 밖의 브랜치는 묻지 않고 푸시한다. 강제 푸시 금지도 기준·배포 브랜치에만 건다.
- **기록:** 묻지 않고 정한 것은 왜 그렇게 정했는지와 함께 항목 파일에 적으면서 진행한다. 나중에 진입 모드 스킬을 만들어도 같은 기준을 따른다.

- `docs/review-principles.md`(프로젝트마다 쌓이는 리뷰 원칙)와는 다른 것이다. 이름이 헷갈리지 않게 계획에서 정한다.

### 함께 가져오는 것

- 일하는 방식 세 줄(016 AC #14): "No is an acceptable answer", "Never hand the human a check you could run", "Give each claim its evidence or a label"(`poteto-mode/SKILL.md` Autonomy, Writing the reply).
- 테스트 규칙(016 AC #9): pstack `tdd`의 "Prefer no new test over a bad test". superpowers TDD 를 떼면서 그 자리에 넣는다. 싸고 분명한 테스트 길이 있을 때만 실패하는 테스트를 먼저 쓰고, 없으면 가장 가까운 실행 확인을 쓴다.

- 플레이북 22개: 작업 종류별 절차다. 절반은 PR·Cursor 클라우드 에이전트 중심(Babysit, Shipping, Autopilot)이고, 나머지(Bug fix, Investigation 등)는 `/task` 밖의 일을 다루는 진입 모드 스킬의 몫이다. 진입 모드 스킬을 정할 때 함께 본다.

## pstack 전체를 읽고 가져올 것을 다시 고름 (2026-11-26, 사용자 결정)

사용자가 "가져올 건 다 가져와서 pstack 처럼 자연스럽게 쓰게 하자. 단계에 녹이지 않더라도 어딘가에 스킬을 나열해서 쓰게 하는 것 아니냐"고 했다. pstack 의 스킬 59개와 플레이북 22개, Claude Code 어댑터(`docs/harness/claude-code.md`)를 원문으로 읽었다. setup-pstack, make-bot-ui, poteto-help, 형식 검증 둘, statechart, automate-me, ketchup-video 는 앞부분만 읽었다.

### pstack 이 "자연스럽게 쓰는" 방법

- 진입 스킬 `poteto-mode/SKILL.md` 하나에 색인이 있다. Non-negotiables 는 "Across a function boundary → architect", "A number you measured → benchmark-checklist"처럼 한 줄에 "언제 → 무엇"이다. Principles 는 원칙마다 "언제 쓰는지" 한 줄이다. Playbooks 는 이름 목록이고 "작업에 맞는 플레이북을 골라 단계를 할 일 목록에 옮긴다"고 적는다.
- 본문은 스킬·플레이북마다 파일 하나다. 다른 스킬은 모두 `disable-model-invocation: true`라 스스로 뜨지 않는다. Claude Code 어댑터도 "다른 pstack 스킬을 쓸 때는 그 파일을 Read 로 읽고 따른다"고 적는다.
- 그래서 우리도 색인 하나(`task` SKILL.md)와 본문 파일들로 가져온다. 스킬을 플러그인 스킬 목록에 수십 개 늘리지 않는다. 틀렸을 때 비용: `/task` 밖의 일(그냥 묻는 질문, 항목 없는 수정)에는 색인이 뜨지 않는다. 그 자리는 진입 모드 스킬을 만들 때 같은 본문을 가리키게 하면 된다.

## 검증 스킬(기능 지도)과 cursor-team-kit (2026-11-26, 사용자 결정)

사용자가 "검증할 때도 지도 같은 것을 만들어서 한다", "pstack 이 cursor-team-kit 을 참조해서 쓰니 거기서도 가져올 것이 있다"고 했다. `cursor/plugins`의 `cursor-team-kit/`(MIT, Copyright (c) 2026 Cursor)을 받아 스킬 18개, 에이전트 2개, 규칙 2개를 원문으로 읽었다. pr-review-canvas 는 앞부분만 읽었다.

### pstack 이 cursor-team-kit 에서 쓰는 것

`poteto-mode/SKILL.md` Non-negotiables 와 플레이북에 적혀 있다.
- "Shipping UI / IDE / CLI → `control-ui` or `control-cli`". Bug fix 1단계(직접 재현), Feature 5단계(실제 화면에서 검증), Shipping 1단계(검증자가 사용자처럼 돌려 본다)가 모두 이 스킬로 앱을 몬다.
- "Before commit → `/deslop`". Opening a PR 도 커밋 전에 deslop 을 돌린다.

### 가져오는 것 (016 AC #13 에 더함)

| 무엇 | 어디서 | 언제 쓰나 | 우리 쪽과의 관계 |
| --- | --- | --- | --- |
| create-verification-skill | pstack | 프로젝트에 앱을 실제로 몰아 확인할 정해진 방법이 없을 때. 프로젝트 스킬 `verify-<앱>`에 띄우기(Launch), 점검(Doctor), 몰기(Drive), 증거(Evidence), 정리(Cleanup)를 적고, 기능마다 "무엇인지, 어떻게 가는지, 어떻게 모는지, 무엇이 보이면 된 것인지"를 적은 기능 지도를 둔다. 만든 뒤 한 번 끝까지 돌려 증명한다 | 지금은 `frontend-evaluator`가 항목마다 화면 조작을 새로 짠다. 지도가 있으면 그것을 따른다. 앞선 판단("두고 본다")을 사용자가 뒤집었다 |
| maintain-verification-skill | pstack | 기능 지도가 앱과 어긋날 때. 기능마다 소스를 읽고, 한 번씩 실제로 몰아 보고, 증명된 고침만 낸다 | 같음 |

## 정리는 deslop 으로 (2026-11-26, 사용자 결정)

- pstack 의 텍스트 파일 158개를 모두 받아 검색했다. pstack 이 cursor-team-kit 에서 부르는 것은 control-ui(5개 파일), control-cli(5개), deslop(6개)뿐이다. verify-this, fix-merge-conflicts, thermo-nuclear 리뷰는 한 번도 부르지 않는다. verify-this 와 fix-merge-conflicts 는 pstack 을 따른 것이 아니라 이 조사에서 판단해 넣은 것이고, 사용자가 그대로 두기로 했다.
- thermo-nuclear 리뷰는 team-kit 안에서도 다른 스킬이 부르지 않는다. `disable-model-invocation: true`라 사용자가 직접 시킬 때만 돈다.
- **사용자가 "우리도 pstack 처럼 deslop 을 쓰는 것이 맞다"고 했다.** 위 표의 "deslop 의 점검 목록만 simplify 에 더한다"를 뒤집는다. deslop 을 스킬째 가져와 커밋 전에 돌리고, 묻지 않고 바로 고친다(016 AC #5). simplify 를 돌릴지와 무엇을 고칠지 묻던 두 질문(11-25, `fa91c89`)은 없앤다. 2절의 "AC #5 는 사용자가 직접 넣은 질문을 지운다"는 걱정은 사용자가 직접 정해서 풀렸다.

### 이번에 016 에 넣은 것

- **unslop, technical-writing (AC #13).** pstack 은 "Prose, your reply included → unslop. Docs, PR descriptions, commit messages → technical-writing"을 Non-negotiables 에 둔다. 앞서 "사용자가 글쓰기 항목(015)을 지웠다"는 이유로 뺐는데, 015 는 보고서를 써 주는 별도 플러그인이었고 이것은 `/task`가 쓰는 모든 글의 규칙이라 다른 것이다. 사용자가 이 대화에서 "이해할 수 있게 적어"를 여러 번 말했다. 틀렸을 때 비용: 규칙 파일 둘이 는다. 원문의 영어 낱말 목록은 한국어로 옮겨야 한다.

### 넣지 않은 것

- **no-comments.** 주석을 미워하는 리뷰어(comment-sicko)가 주석을 지우고, 주석이 가리던 우리 코드의 놀라운 동작을 구조를 바꿔 고치게 한다. 군더더기 주석은 deslop 이 이미 지운다. no-comments 까지 넣으면 리뷰 전마다 구조 수정이 자동으로 들어가 diff 가 커진다. 원하면 넣는다.
