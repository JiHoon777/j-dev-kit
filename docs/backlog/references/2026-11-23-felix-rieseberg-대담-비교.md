## 대담 요점 (타임스탬프)

- 8:52–10:39 지식 노동의 비결은 "좋게 만들어 줘" 사이에 한 단계를 끼우는 것: 그 분야 최고는 어떻게 일하나, 그 단계를 자동화할 수 있나. "전문가가 밟는 단계를 똑같이 밟아." Blender 예: "전문 애니메이터가 쓰는 도구를 써." 열쇠는 매체·기법·도구.
- 25:08–26:07 "넌 뛰어난 X야"는 2024년 방식. "이 분야 최고가 쓰는 도구를 말해 줘" → 같은 걸 쓰게. 역할을 주면 역할극(어휘)만 따라 한다. 말투는 쉽게, 도구는 최고로.
- 17:43–19:56 에이전트에 과하게 쏠려 있다. 모델은 좋은 제너럴리스트. 등장인물을 짜면 스스로 폭을 좁힌다. 자료를 쪼개 나눠 주지 말고 도구를 주고 그 뒤 자료를 잘 적어 둔다.
- 21:31–22:48 스킬 반감기는 짧다. 통째로 지웠더니 좋아지기도. eval 이 있어야 판단 가능. 모델 경험: 날것의 자료, 컴퓨터, 소프트웨어 설치, 스스로 결정.
- 22:49–23:21 컨베이어 벨트: 크래시 하나씩 넘기지 말고 데이터 전부를 주고 고를 것을 스스로 정하게.
- 12:57–15:48 적대적 검토(틀렸음을 증명하라는 스레드 여럿, 한 단계 낮은 모델도 됨) → judge 가 타당성 판정 → 타당한 것만 만든 쪽에 돌아가고, 만든 쪽도 가려 반영.
- 26:07–27:06 지금 세션이 자기 일을 판정하게 하지 않는다. 바깥 신호, 급하면 다른 세션, 가장 좋은 건 단단한 바깥 증거.
- 27:45–29:09 피드백 3단계: 모으기 → 원칙으로 압축 → 모르고 믿던 원칙 → 이후 리뷰의 입력. 30:05 나란히 돌려 비교.
- 7:37–8:09 찍어서 맞힌 건 낙제, 믿을 만한 자료로 제대로 간 과정이 낫다.

## j-dev-kit 개선 후보

1. 전문가의 도구와 단계 (8:52, 25:28, 22:24)
   - start.md 3단계에 "이 항목의 일을 그 분야 최고 실무자는 어떤 도구·단계로 하나"를 정하는 단계가 없다. 도구는 스택 점검에 고정(frontend-design, svelte-autofixer, oasdiff, advisors).
   - 리뷰 에이전트 5개가 "너는 X 리뷰어다/평가자다"로 시작.
   - server-end-check 는 "설치된 것만 쓰고 새로 내려받지 않는다", api-reviewer 는 curl 재현을 "돌리지는 않는다". 모델 경험(설치, 직접 실행)과 반대.
   - 반례: supabase-reviewer 의 "두 사용자로 로컬 DB 에 SQL" 은 이미 전문가 방식.
2. 지적 판정을 만든 세션 밖으로 (14:55, 26:24): end.md 4단계에서 작업 세션이 틀린 지적을 직접 뺀다. judge 에이전트 → 타당한 것만 보여 주고, 5단계 receiving-code-review(만든 쪽의 가려 반영)는 그대로.
3. 사용자 피드백을 원칙으로 (28:45): Final Summary 에 "그대로 둔 지적과 이유"가 없다. 모아서 원칙으로 압축해 end 3단계 리뷰 지시문 입력으로. 예: 006 포트 지적.
4. UI 가 아닌 AC 판정 (26:24): start.md 6.4 에서 구현 세션이 스스로 체크. UI 만 frontend-evaluator. _proposals.md 홀드아웃과 같은 문제.
5. eval 로 덜어내기 (21:49): 고정 체크리스트(frontend-reviewer Svelte/React 항목, Explore 최대 2개, 질문 최대 3개 등)가 지금 모델에 도움이 되는지 잰 적 없음. 있을 때/없을 때 비교 후 근거 있는 것만 삭제.
6. 리뷰 모델 한 단계 낮추기 (13:47): 선택. 비용.
