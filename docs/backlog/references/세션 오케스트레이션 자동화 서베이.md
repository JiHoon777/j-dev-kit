# 상위 세션은 원장과 검수 용량으로 지휘한다

2026-11-20 기준으로 하나의 상위 세션이 하위 세션을 지휘하는 구조는 세 가지 위에 선다. 세션이 죽어도 남는 원장(백로그 파일, 이슈 트래커, git), 워커마다 격리된 worktree나 VM과 브랜치·PR로 나오는 결과물, 그리고 사람에게는 적은 수의 결정만 올리는 에스컬레이션이다. 사람들이 실제로 쓰는 오케스트레이터는 LLM 코디네이터가 워커를 띄우는 계층형, 이슈 트래커를 폴링하는 데몬형, 리드 없이 사람이 세션을 나란히 돌리는 병렬 러너로 갈린다. Claude Code는 이제 부품을 거의 다 기본 기능으로 준다. 서브에이전트, 동적 워크플로, 백그라운드 세션, 세션 간 `SendMessage`(2026-08-07), 스케줄러 세 종류, 클라우드 코디네이터인 Projects(2026-09-17 베타)가 그것이다. 다만 재부팅을 넘겨 사는 스케줄러(Desktop 예약 작업, 클라우드 예약 작업)는 실행마다 새 세션을 만들 뿐이고, 이미 열려 있는 리드 세션으로 결과를 돌려주지 않는다. 그래서 "주기적으로 도는 백로그 담당 세션이 상위 세션에 보고한다"는 요구는 직접 호출이 아니라 공유 원장에 쓰고 리드가 읽는 방식으로 풀게 된다. 근거는 한 방향을 가리킨다. 읽기·조사·리뷰를 여러 세션에 나누면 이득이고, 여러 세션이 동시에 코드를 쓰면 손해다. 오케스트레이터의 값은 처리량보다 오류 차단에 있다. 실패는 토큰 폭주, 같은 파일 덮어쓰기와 머지 충돌, 원장의 거짓 상태, 리드의 조기 완료 선언, 리드로 몰리는 권한 프롬프트로 반복된다. 앞선 서베이 이후 넉 달 동안 상시 코디네이터가 제품이 됐고(Projects, Dots, Duet, Devin Bots), 머지 직전 단계의 자동화가 preview와 정책 설정으로 들어왔으며, 대규모 독립 연구가 병목이 리뷰로 옮겨 갔음을 보였다. 그래서 이 구조의 설계 변수는 워커 수가 아니라 사람의 검수 용량이다.

## 앞선 서베이 뒤 넉 달, 코디네이터 층이 제품이 됐다

앞선 서베이(`reports/AI 코딩 작업 전체 자동화 서베이.md`)의 결론은 세 가지였고 지금도 유효하다. 첫째, 도구가 달라도 과정은 요구사항·백로그 → 계획·분해 → 구현 → 검수 → 머지의 다섯 단계로 모인다. 둘째, 사람 게이트는 스펙·계획 승인과 머지 승인 두 곳에 남는다. 셋째, 검수 자동화는 돌아가지만 믿을 만한 수준은 아니다. 독립 측정에서 SWE-bench 테스트를 통과한 AI PR의 약 절반은 maintainer가 머지하지 않았고 ([METR](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)), CodeRabbit 코멘트의 수용률은 36.4%였다 ([arXiv 2607.03316](https://arxiv.org/abs/2607.03316)). 이번 서베이는 그 위에 층 하나를 더 얹는다. 앞선 서베이가 다룬 것은 세션 하나가 도는 루프였고, 이번에 다루는 것은 그 루프들을 며칠에서 몇 주 동안 관리하는 코디네이터다.

**2026-08~11에 가장 크게 달라진 것은 상시 코디네이터의 제품화다.** Anthropic은 2026-09-17에 Claude Code Projects를 베타로 냈다. 계속 이어지는 대화 하나가 코디네이터가 되고, 작업마다 thread(대부분 클라우드 세션)를 연다 ([VentureBeat](https://venturebeat.com/orchestration/anthropic-launches-claude-code-projects-an-always-on-conversation-that-remembers-and-delegates-your-long-running-dev-work); [Projects 문서](https://code.claude.com/docs/en/claude-projects)). OpenAI는 2026-09-29 DevDay에서 상시 에이전트 Dots를 냈다. 자기 클라우드 컴퓨터를 갖고, 필요하면 Codex에 작업을 만든다 ([BetaNews](https://betanews.com/article/openai-dots-agents-chatgpt/); [heise](https://www.heise.de/en/news/OpenAI-Launches-Dots-Permanently-Active-AI-Agents-with-Their-Own-Cloud-Computer-11470571.html)). Anthropic의 Claude Duet(2026-10-21, research preview)은 코딩 전용은 아니지만 사용자가 자리를 비운 뒤에도 일을 잇고, 메시지 전송·결제·삭제 전에는 묻는다 ([MacRumors](https://www.macrumors.com/2026/10/21/anthropic-claude-duet/)). Cognition의 Devin Bots(2026-11-17)는 팀 Slack에 멤버로 들어가 여러 Devin에게 일을 나누고 며칠에서 몇 주 동안 맥락을 유지하며, Bot마다 예산을 둔다 ([Fortune](https://fortune.com/2026/11/17/exclusive-cognition-bets-on-devin-bots-coding-agents-in-challenge-to-anthropics-duet-and-openais-dots/)). GitHub는 Universe 2026(2026-10-28)에서 "From issue to merge, in one app"을 내건 Copilot app과, 목표 하나를 여러 repo에 걸친 병렬 세션으로 실행하는 Copilot projects, 일정과 이벤트로 도는 automations를 발표했다 ([GitHub](https://github.blog/news-insights/company-news/github-universe-2026-evolving-every-layer-of-the-stack/)). Markdown으로 쓰는 예약 에이전트인 GitHub Agentic Workflows도 같은 날 GA가 됐다 ([GitHub changelog](https://github.blog/changelog/2026-10-28-github-agentic-workflows-generally-available)).

**Claude Code 쪽에서는 세션끼리 말을 주고받는 통로가 생겼다.** v2.1.224(2026-08-07)가 세션 간 `SendMessage`와 `ListAgents`를 추가했다 ([release v2.1.224](https://api.github.com/repos/anthropics/claude-code/releases/tags/v2.1.224)). 네이티브 Windows는 v2.1.234부터 되고, 상대 세션이 유휴가 되면 한 번 알려 주는 `notify_when_idle`은 v2.1.236에서 들어왔다 ([세션 간 메시지 문서](https://code.claude.com/docs/en/cross-session-messaging.md)). routines는 "클라우드 예약 작업"으로 이름이 바뀌었는데 바뀐 날짜는 공식 페이지에 없다 ([routines 문서](https://code.claude.com/docs/en/routines.md)). Task 도구(`TaskCreate` 등)는 v2.1.268부터 Opus 4.7, Sonnet 4.6, Haiku 4.5 이하 모델에서만 기본으로 켜지고, `TaskOutput`은 v2.1.277에서 없어졌다 ([도구 레퍼런스](https://code.claude.com/docs/en/tools-reference.md)). v2.1.329(2026-11-19)는 `/tasks` 한 화면에 예약 작업, `/loop` 웨이크업, goal, 포크를 모았다 ([CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)). Code Review는 2026-10-15에 Team·Enterprise 대상 GA가 됐고, 리뷰 시간이 약 20분에서 6~10분으로 줄었다고 Anthropic이 밝혔다(자사 수치). 발표문에 승인이나 머지 언급은 없다 ([claude.com](https://claude.com/blog/code-review-is-now-generally-available)). auto mode는 2026-08-07 공지에서 8월 14일부터 Pro·Max·Team의 새 세션 기본값이 된다고 했는데, 같은 페이지의 10월 22일 업데이트가 출시를 "next week"라고 적어 실제 적용일은 단정할 수 없다 ([claude.com](https://claude.com/blog/auto-mode-default-in-claude-code)). 같은 기간에 모델도 바뀌었다. Opus 5.5(2026-09-22), Sonnet 5.5(09-28), Haiku 5.5(10-07), Fable 5.2(11-09)가 나왔고, Fable 5.1의 출시일은 Platform 릴리스 노트가 9월 1일, Anthropic 뉴스 페이지가 9월 15일로 서로 다르게 적는다. Opus 5.5는 Anthropic 표현으로 "costs 40% less to run than Opus 5 on typical workloads"이고 토큰 단가로는 20% 낮다 ([릴리스 노트](https://platform.claude.com/docs/en/release-notes/overview); [Anthropic](https://www.anthropic.com/news/models)).

**"머지는 사람에게"라는 경계는 기본값으로는 그대로지만 가장자리가 풀리기 시작했다.** VS Code의 agent merge(preview, 2026-10-01)는 세션 안에서 리뷰 피드백, 실패한 체크, 머지 충돌, 워크플로 재실행을 처리해 PR이 머지되게 한다 ([GitHub changelog](https://github.blog/changelog/2026-10-01-github-copilot-in-vs-code-september-2026-releases)). Devin Bots는 저위험 변경을 자동 승인·머지하도록 설정할 수 있다 ([Fortune](https://fortune.com/2026/11/17/exclusive-cognition-bets-on-devin-bots-coding-agents-in-challenge-to-anthropics-duet-and-openais-dots/)). GitHub automations는 스스로 낸 개선안을 사람이 승인하게 한다 ([GitHub](https://github.blog/news-insights/company-news/github-universe-2026-evolving-every-layer-of-the-stack/)). 어느 벤더도 사람 승인 없는 머지를 기본값으로 두지 않았다. 앞선 서베이는 배포까지 에이전트 파이프라인에 넣은 공개 사례를 찾지 못했는데, 이번에는 하나가 나왔다. 게임 스튜디오 Spawn은 에이전트가 라이브 코드를 직접 바꿔 매시간 프로덕션에 배포한다고 밝혔다. Simon Willison은 이것이 고위험 소프트웨어에는 맞지 않을 것이라고 평했다 ([simonwillison.net](https://simonwillison.net/2026/Oct/29/)).

**새 근거는 병목이 리뷰로 옮겨 갔다고 말한다.** Harvard 워킹페이퍼(Chen & Stratton)는 Jellyfish 데이터로 에이전트 도입 전후를 비교했다. 수치는 버전에 따라 다르다. 2026-08-04 버전은 718개 기업에서 LOC +30%, PR +23%, PR에서 머지까지 걸리는 시간 +49%였고 완료 작업은 유의한 변화가 없다고 했다 ([complexdiscovery](https://complexdiscovery.com/harvard-researchers-find-ai-coding-agents-shifted-the-bottleneck-to-code-review/)). **현재 버전(2026-11-19)은 655개 기업, 720,542명, 2021-01~2026-08을 다루고 LOC +44.0%, 커밋 +36.0%, PR +35.7%, 머지까지 +56.1%(기준 3.56일), PR당 코멘트 +38.6%다.** 완료 작업은 Jira issue +13.7%(경계선 유의), epic +18.0%로, 코드 산출에 비해 훨씬 작다. AI 리뷰 도구는 2026-07 기준 기업의 79.1%가 쓰지만 리뷰 코멘트 중 AI 몫은 23.3%다 ([논문 PDF](https://fion.ac/jellyfish.pdf)). 동료 심사 전 단계다. 벤더 쪽 수치는 결이 다르다. GitHub Octoverse 2026은 2026년 9월 PR의 40% 이상이 에이전트 초안으로 시작했고(3월 17%, 에이전트가 시작한 PR 1.1억 건), 2주 안 머지율이 에이전트 관여 PR 90%, 미감지 PR 약 86%라고 했다 ([GitHub](https://github.blog/news-insights/octoverse/octoverse-commits-pushes-reach-new-highs-in-2026-as-developers-build-with-agents/)). Anthropic은 하루 머지가 5월 약 2,500건에서 9월 30,000건 이상으로 늘어 monorepo를 자체 시스템으로 옮겼다고 했다. 구성원은 여전히 모든 change request를 리뷰하지만 한 줄씩 읽지 않고 의도를 본다 ([Anthropic](https://www.anthropic.com/research/redesigning-source-control)). 담론도 같은 곳을 본다. Dex Horthy는 사람이 코드를 읽지 않는 factory는 하네스를 아무리 다듬어도 성립하지 않는다고 했고 ([PostHog](https://posthog.com/newsletter/software-factories); [원문](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)), Andrew Zigler는 병렬 에이전트 루프가 모두 희소한 리뷰 용량으로 흘러든다며, 세션을 시작할 때 팀의 리뷰 대기 시간과 자기 대기 PR을 보고 새 작업을 시작할지 리뷰부터 비울지 정하는 `/sdlc` skill을 제안했다. 그가 인용한 LinearB 수치로는 에이전트 PR이 리뷰를 받기까지 5.25배 오래 기다리고(P75 17.6시간 대 3.4시간), AI 생성 PR의 머지율은 32.7%로 사람 PR 84.4%보다 낮다 ([Dev Interrupted](https://devinterrupted.substack.com/p/your-agents-should-ask-the-factory)). Octoverse의 90%와 LinearB의 32.7%는 정의가 달라 나란히 비교할 수 없다. reward hacking 근거도 늘었다. 한 연구에서 GLM 5.2는 SWE-bench rollout의 73%에서 reward hacking을 했다 ([arXiv 2609.19101](https://arxiv.org/abs/2609.19101)).

스펙 주도 프레임워크는 골격을 유지한 채 진입부를 가볍게 했다. Spec Kit은 v1.0.0(2026-08-21)을 넘어 v1.4.3까지 왔고 ([spec-kit releases](https://github.com/github/spec-kit/releases)), Superpowers v7.0.0(2026-10-10)은 brainstorming을 다시 써서 작업 크기에 따라 설계 문서를 건너뛰게 했고, 문서 리뷰어를 새 서브에이전트가 구현자 입장에서 설계를 읽고 남는 질문을 뽑는 builder check로 바꿨다 ([superpowers releases](https://github.com/obra/superpowers/releases)). OpenSpec v2.0.0(2026-11-11)은 슬래시 명령을 없애고 skill을 `.agents/skills/` 한 곳에 설치한다 ([OpenSpec releases](https://github.com/Fission-AI/OpenSpec/releases)). GSD 원 repo는 2026-06-26에 archived 됐고 GSD Core가 잇는다 ([GSD](https://github.com/gsd-build/get-shit-done)). BMAD v7은 여전히 preview alpha이고 ([BMAD](https://github.com/bmad-code-org/BMAD-METHOD)), Task Master는 2026-08 이후 릴리스가 없다 ([Task Master releases](https://github.com/eyaltoledano/claude-task-master/releases)).

## 오케스트레이터는 세 갈래이고, 모두 원장과 격리에 기댄다

### 리드의 실체는 LLM 코디네이터, 결정적 데몬, 사람 셋 중 하나다

2026년의 오케스트레이터는 "누가 리드인가"로 나뉜다. 어느 쪽이든 공통 기반은 워커마다 git worktree나 VM·컨테이너를 주고 결과를 브랜치나 PR로 받는 것이다.

| 갈래 | 대표 | 리드 | 조율 매체(상태가 사는 곳) | 머지 처리 |
|---|---|---|---|---|
| 계층형 | Gas Town·Gas City, Claude Code agent teams, Claude Code Projects, Devin(manager와 child), Factory Missions, Cursor planner–worker–judge, Orca, Paperclip | LLM 코디네이터 | Beads 원장(Dolt), 파일 task list, 프로젝트 메모리 파일, 자체 티켓(Postgres) | 대부분 브랜치·PR과 사람. Gas Town만 직렬 머지 큐 |
| 데몬형 | OpenAI Symphony, Composio Agent Orchestrator | 결정적 폴링 루프 | 외부 이슈 트래커(Linear, GitHub) | 에이전트가 PR을 남기고 "Human Review" 같은 handoff 상태에서 끝남 |
| 병렬 러너 | Claude Squad, Conductor, Vibe Kanban, Crystal, Codex 앱, GitHub mission control | 사람 | 없음(사람이 세션을 지켜봄) 또는 칸반 | 사람이 리뷰하고 머지 |

**계층형의 가장 자세한 공개 설계는 Steve Yegge의 Gas Town이다.** README 기준으로 Mayor가 "primary AI coordinator"이고, Polecats는 정체성은 지속되지만 세션은 일회용인 워커다. Refinery는 rig별 머지 큐, Witness는 워커를 감시해 멈춘 에이전트를 찾는 역할, Deacon은 모든 rig를 순찰 주기로 도는 백그라운드 감독자다. 사람이나 Mayor가 `gt sling <bead-id> <rig>`로 작업을 배정하고, 작업은 git worktree 기반 hook에 남는다("Work persists in git-backed hooks") ([gastownhall/gastown](https://github.com/gastownhall/gastown)). 사람은 직접 고치지 않고 Mayor에게 수정 작업을 만들게 한다 ([heise](https://www.heise.de/en/background/Full-Control-Gas-Town-Orchestrates-Ten-or-More-Coding-Agents-11178824.html)). Gas Town은 LLM 리드와 결정적 순찰 역할을 섞은 형태다. 지금 상태는 출처마다 다르다. yegge.ai는 "Gas Town is now retired. Its successor is Gas City."라고 하고, Yegge의 2026-04-03 글은 "maintenance mode"라고 하며, GitHub README에는 은퇴 표시가 없다 ([yegge.ai](https://yegge.ai/gastown); [재게시본](https://drss.io/reader/npub1na2ppcvpx7m7dg4d2rqelpq4xdj9z40cxu3avh4qcdq8dtupdcmqahmfge/gas-town-from-clown-show-to-v10)). 후속인 Gas City는 README가 "The open-source platform for building software factories from teams of coding agents"라고 소개하고, order로 formula를 "on a schedule or in response to events" 실행한다 ([gascity README](https://raw.githubusercontent.com/gastownhall/gascity/HEAD/README.md)).

다른 계층형도 같은 뼈대다. Devin은 manager Devin이 큰 작업을 쪼개 child Devin을 띄운다. 자식마다 "a full Devin, running in its own isolated virtual machine"이고, 코디네이터는 자식의 전체 궤적을 읽는다 ([Cognition](https://cognition.com/blog/devin-can-now-manage-devins)). Factory Missions는 사람이 오케스트레이터 Droid와 대화하며 마일스톤과 성공 기준을 세우고 승인한 뒤에 워커가 돈다. 문서는 "not fire-and-forget"이라고 쓰고, 병렬화가 순차보다 나은지는 "open question"이라고 적는다 ([Factory](https://docs.factory.com/cli/features/missions)). Cursor의 연구 하네스는 planner가 sub-planner를 재귀로 띄우고, worker는 서로 조율하지 않고 push하며, 사이클마다 judge가 계속할지 정한다 ([Cursor](https://cursor.com/blog/scaling-agents)). Paperclip은 에이전트를 조직도로 "고용"하고 티켓에 단일 담당자와 실행 락을 두며, 하트비트와 cron routine, 예산 하드 스톱, 승인 워크플로를 갖는다 ([paperclip](https://github.com/paperclipai/paperclip)).

**데몬형에는 리드 LLM이 없다.** OpenAI Symphony의 스펙은 서비스의 일을 "Poll the issue tracker on a fixed cadence and dispatch work with bounded concurrency"로 적는다. 기본값은 폴링 30초, 동시 실행 10, 워커당 최대 20턴, stall 타임아웃 5분, 실패 시 최대 5분의 지수 백오프다. 스케줄러 상태는 "intentionally in-memory"이고, 재시작하면 트래커와 파일시스템에서 복구한다 ([SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md)). 레퍼런스 구현은 Linear 보드를 감시한다("Symphony monitors a Linear board for work"). README는 이것을 "a low-key engineering preview for testing in trusted environments"라고 부른다 ([openai/symphony](https://github.com/openai/symphony)). InfoWorld는 동기를 엔지니어가 세션 3~5개를 넘게 관리하면 컨텍스트 전환이 괴로워진다는 데서 찾는다 ([InfoWorld](https://www.infoworld.com/article/4164173/openais-symphony-spec-pushes-coding-agents-from-prompts-to-orchestration.html)).

**리드 없는 병렬 러너는 2026년에 많이 정리됐다.** Vibe Kanban은 README 첫 줄이 "Vibe Kanban is sunsetting."이고 회사 Bloop이 2026-04-10에 종료를 발표했다 ([vibe-kanban](https://github.com/BloopAI/vibe-kanban); [종료 공지](https://vibekanban.com/blog/shutdown)). Crystal은 2026-02에 지원이 중단됐다 ([crystal](https://github.com/stravu/crystal)). Conductor는 한 비교 글이 "Conductor is winding down."이라며 Conductor Cloud가 11월 13일 읽기 전용, 11월 20일 종료라고 적었지만, 공식 사이트에는 종료 안내가 없어 미확인이다 ([openalternative](https://openalternative.co/blog/best-ai-coding-agent-orchestrators); [conductor.build](https://www.conductor.build/)). Claude Squad는 tmux와 worktree로 세션을 나란히 돌리고 리드도 머지 기능도 없다 ([claude-squad](https://github.com/smtg-ai/claude-squad)). GitHub mission control은 여러 에이전트에 일을 맡기고 추적하는 단일 화면이고, 리드 에이전트 없이 사람이 디스패처 노릇을 한다 ([GitHub](https://github.blog/news-insights/product-news/welcome-home-agents/); [가이드](https://github.blog/ai-and-ml/github-copilot/how-to-orchestrate-agents-using-mission-control/)).

### 조율 매체는 세션 밖의 원장으로 옮겨 갔다

리드가 무엇을 기억하느냐보다 상태가 어디에 사느냐가 구조를 정한다. Gas Town은 작업, 수정, MR, 에이전트 메모를 모두 "bead"로 원장에 남기고, 세션이 죽으면 다음 세션이 bead에서 이어받는다 ([yegge.ai](https://yegge.ai/gastown)). Symphony는 트래커가 원본이라 스케줄러를 메모리에만 둬도 된다 ([SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md)). Claude Code agent teams는 `~/.claude/tasks/{team}/`의 파일 task list와 `~/.claude/teams/{team}/inboxes/{agent}.json` mailbox를 쓰고, 작업 선점에 파일 락을 쓴다 ([agent teams 문서](https://code.claude.com/docs/en/agent-teams)). Claude Code Projects는 트래커 대신 프로젝트 메모리 파일과 Overview 패널을 쓴다. 각 thread는 시작할 때 `MEMORY.md` 인덱스를 읽고, 코디네이터는 전체 기록이 아니라 최근 메시지, 최근 thread, 메모리로 일한다. 그래서 문서는 잊으면 안 되는 것을 메모리에 넣으라고 한다 ([Projects 문서](https://code.claude.com/docs/en/claude-projects)). 원장 중심 설계의 이점은 재시작 복구와 사람이 읽을 수 있는 기록이다. 대가는 원장과 git이 따로 노는 것이다. Beads 초기 버전은 SQLite와 JSONL을 양방향으로 동기화하다 "two sources of truth", 경쟁 조건, 대량 데이터 손실을 겪었고, v1.0에서 Dolt로 옮기며 동기화 로직을 걷어냈다고 Yegge가 썼다(자기보고) ([재게시본](https://drss.io/reader/npub1na2ppcvpx7m7dg4d2rqelpq4xdj9z40cxu3avh4qcdq8dtupdcmqahmfge/gas-town-from-clown-show-to-v10)).

### 머지는 대부분 PR과 사람에게 남고, 직렬 큐는 드물다

워커 결과를 합치는 방식은 정반대의 두 실험과 다수의 기본값으로 나뉜다. Gas Town의 Refinery는 Bors 방식의 이분 탐색 머지 큐이고 "polecats never push directly to main"이다 ([gastown](https://github.com/gastownhall/gastown)). Cursor는 반대로 충돌 해결용 integrator 역할이 병목이 돼서 없앴고 워커가 충돌을 직접 처리하게 했다 ([Cursor](https://cursor.com/blog/scaling-agents)). 나머지는 브랜치·PR, CI, 사람 리뷰에 맡긴다. agent teams에는 머지 기능이 없고 문서가 "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files."라고 경고한다 ([agent teams 문서](https://code.claude.com/docs/en/agent-teams)). mission control 가이드는 같은 파일을 건드리면 머지 충돌이 나므로 의존 작업은 순차로 하라고 한다 ([GitHub](https://github.blog/ai-and-ml/github-copilot/how-to-orchestrate-agents-using-mission-control/)). Projects의 thread는 자기 브랜치에서 일하고, 겹치는 변경의 충돌은 일반 PR처럼 해결한다 ([Projects 문서](https://code.claude.com/docs/en/claude-projects)). Anthropic 내부는 업계 표준인 전역 merge-queue 락을 그 규모에서 재현할 수 없어서, 대신 머지 후·배포 전 자동 테스트에 투자했다고 밝혔다 ([Anthropic](https://www.anthropic.com/research/redesigning-source-control)).

### 반복해서 깨진 다섯 가지

**첫째는 비용이다.** agent teams는 토큰이 팀 크기에 비례해 늘고, 팀메이트가 plan mode로 돌면 "approximately 7x more tokens than standard sessions"다 ([costs 문서](https://code.claude.com/docs/en/costs)). Projects는 PR을 지켜보는 유휴 thread도 깨어날 때 사용량을 쓰고, 1시간 넘게 쉰 thread는 깨어날 때 대화 전체를 다시 읽는다 ([Projects 문서](https://code.claude.com/docs/en/claude-projects)). DoltHub는 Gas Town 피크에 시간당 약 $100을 썼다고 2차 출처가 전한다 ([paddo.dev](https://paddo.dev/blog/gastown-two-kinds-of-multi-agent/)). 오케스트레이터별 비용을 독립적으로 측정한 데이터는 없고, 수치는 모두 자기보고나 일화다.

**둘째는 서로 밟기다.** Cursor는 공유 파일과 락으로 하는 자율 조율에서 "Twenty agents would slow down to the effective throughput of two or three"를 겪었고, 위계가 없으면 에이전트가 어려운 일을 피했다 ([Cursor](https://cursor.com/blog/scaling-agents)). heise는 Gas Town에서 에이전트 3~5개를 병렬로 돌릴 때 중복 작업과 풀리지 않은 머지 충돌이 났고, 한 코드베이스에 로깅 라이브러리가 3~4개 생겼다고 보고했다 ([heise](https://www.heise.de/en/background/Full-Control-Gas-Town-Orchestrates-Ten-or-More-Coding-Agents-11178824.html)). DoltHub 사례에서는 실패한 테스트가 main에 자동 머지돼 복구에 force push가 5번 필요했다 ([paddo.dev](https://paddo.dev/blog/gastown-two-kinds-of-multi-agent/)).

**셋째는 원장의 거짓 상태다.** agent teams 문서는 "Task status can lag: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks."라고 적는다 ([agent teams 문서](https://code.claude.com/docs/en/agent-teams)). Symphony는 재시작하면 재시도 타이머와 라이브 세션이 복원되지 않는다 ([SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md)). Projects는 클라우드 샌드박스가 다시 열리지 않으면 새 클론에서 이어 가므로 커밋하지 않은 변경이 사라질 수 있다 ([Projects 문서](https://code.claude.com/docs/en/claude-projects)).

**넷째는 리드와 컨텍스트다.** agent teams 문서는 리드가 팀메이트를 기다리지 않고 직접 구현하거나, 일이 끝나기 전에 끝났다고 판단하는 문제를 적는다 ([agent teams 문서](https://code.claude.com/docs/en/agent-teams)). Cursor는 planner가 재계획하지 않고, drift를 막으려면 주기적으로 새로 시작해야 하며, "Agents occasionally run for far too long"이라고 썼다 ([Cursor](https://cursor.com/blog/scaling-agents)). Cognition은 코드베이스 맥락이 얕은 manager가 지나치게 지시적이 되고, 에이전트들이 자식과 상태를 공유한다고 착각한다고 했다 ([Cognition](https://cognition.com/blog/multi-agents-working)).

**다섯째는 사람 부담이다.** agent teams는 팀메이트의 권한 프롬프트가 리드 세션으로 몰려서 문서에 "Too many permission prompts" 항목이 따로 있다 ([agent teams 문서](https://code.claude.com/docs/en/agent-teams)). Gas Town은 hands-off가 아니고 계속 조종해야 한다는 사용자 평가가 있다 ([paddo.dev](https://paddo.dev/blog/gastown-two-kinds-of-multi-agent/)). Devin Bots에 대해서도 리뷰어의 처리 용량 문제가 남는다는 지적이 나왔다 ([AlphaSignal](https://alphasignal.ai/news/cognition-s-devin-bots-now-run-parallel-coding-sessions-hitting-2-000-pull)). 알림 과부하를 정면으로 다룬 1차 사용자 보고는 찾지 못했다. 다섯 문제의 뿌리는 대부분 공유 가변 상태이고, 해법도 비슷하게 모인다. 파일·모듈 소유권 분할, 워커마다 worktree, PR과 CI, 결정적 감시자, 하드 예산이다(이 묶음은 출처들을 종합한 해석이다).

## 백로그를 채우는 주기 에이전트는 쓰기 권한 없이 제안만 한다

### gh-aw: 에이전트는 읽기만 하고, 쓰기는 상한이 걸린 별도 job이 한다

"주기적으로 돌며 할 일을 제안하는 에이전트"의 설계가 가장 자세히 공개된 곳은 GitHub Agentic Workflows(gh-aw)다. GitHub Next는 이 범주를 Continuous AI라고 부르고, 이 워크플로들이 완전 자율이 아니라 사람의 감독을 둔다고 밝힌다 ([GitHub Next](https://githubnext.com/projects/continuous-ai/)). 워크플로는 frontmatter가 붙은 `.md` 파일이고 `gh aw compile`이 Actions용 `.lock.yml`을 만든다. 엔진은 Copilot CLI, Claude Code, OpenAI Codex를 지원한다. 기본은 read-only이고, 쓰기는 미리 승인된 safe output으로만 나가며, "pull requests are never merged automatically"다 ([GitHub Blog](https://github.blog/news-insights/product-news/automate-repository-tasks-with-github-agentic-workflows/)).

**핵심은 노이즈를 프롬프트가 아니라 구조로 막는다는 점이다.** 에이전트는 쓰기 권한 없이 구조화된 출력으로 요청만 하고, "separate permission-controlled job"이 그것을 검증해 실행한다. `create-issue`는 기본이 `max: 1`이다. 옵션으로 `title-prefix`와 `labels`(워크플로의 정체성), `expires`(예: `7d`), `close-older-issues`(새 이슈가 만들어진 뒤에만 같은 워크플로의 이전 이슈를 최대 10개까지 "not planned"로 닫고 새 이슈를 링크), `group-by-day`(같은 날 실행은 한 이슈의 코멘트가 됨), `deduplicate-by-title`(정확히 일치하거나 Levenshtein 거리로 판정, 열린 이슈와 최근 30일 안에 닫힌 이슈를 봄)이 있다. `expires`를 쓰면 만료된 에이전트 이슈를 닫는 `agentics-maintenance.yml`이 자동으로 생긴다. `noop`, `report-missing-tool`, `report-missing-data`는 항상 쓸 수 있어서, 에이전트가 일을 지어내지 않고 "할 일 없음"이나 "자료 없음"을 보고할 수 있다 ([Safe Outputs](https://github.github.com/gh-aw/reference/safe-outputs/)). 이슈를 하나만 만들 수 있고 이전 것을 닫는 예약 에이전트는 스팸을 낼 수 없다(해석). 실행 비용은 기본 설정에서 Copilot premium request 2개(에이전트 작업 1, safe-output 검사 1)로 공개돼 있다. 도입 지침은 코멘트, 초안, 보고서 같은 저위험 출력부터 시작하고 PR 생성은 나중에 켜라는 것이다 ([GitHub Blog](https://github.blog/news-insights/product-news/automate-repository-tasks-with-github-agentic-workflows/)).

### 보고서가 사람의 승격을 거쳐 이슈가 되고, 그다음에 PR이 된다

gh-aw 팀은 자기 repo에서 워크플로를 "over 100"개 돌리며 얻은 교훈을 적었다. 전문화된 에이전트가 하나의 큰 에이전트보다 낫다. 다른 에이전트를 지켜보는 메타 에이전트가 값지다. 긴 분석이 늘 더 좋지는 않다. 그리고 "No one can read all these outputs (except, of course, another workflow)"다 ([Agent Factory](https://github.github.com/gh-aw/blog/2026-01-12-welcome-to-pelis-agent-factory/)). 지배적인 패턴은 보고서 → 이슈 → PR 사슬이다. Repository Quality Improver는 날마다 초점 영역을 바꿔 가며 약 20분 분석하고, discussion 59개에서 이슈 30개, PR 40개가 나와 25개가 머지됐다(62%). Typist는 분석만 하고, 사람이 `/plan`을 돌려야 이슈가 생긴다(PR 25개 중 19개 머지, 76%) ([Continuous Improvement](https://github.github.com/gh-aw/blog/2026-01-13-meet-the-workflows-continuous-improvement/)). Discussion Task Miner는 매일 돌며 실행당 이슈를 최대 5개 만들고, 그 사슬로 제안된 PR 105개 중 60개가 머지됐다(57%) ([agentics 문서](https://raw.githubusercontent.com/githubnext/agentics/main/docs/discussion-task-miner.md)). Issue Monster는 30분마다 `cookie` 라벨 이슈를 Copilot에 배정하는데, 병렬 에이전트가 코드베이스에서 부딪히지 않도록 "one at a time"으로 한다 ([Issue Management](https://github.github.com/gh-aw/blog/2026-01-13-meet-the-workflows-issue-management/); [agentics](https://github.com/githubnext/agentics)). **머지율은 표본이 큰 워크플로에서 57~78%이고, 모두 만든 팀이 자기 repo에서 잰 자기보고다.** 표본이 2~9개인 워크플로 중에는 100%도 있다. 그런 튜닝이 없는 repo에서는 더 낮을 것으로 봐야 한다. 며칠에 걸친 작업은 "maintain state across days using repo-memory"로 잇는다 ([Multi-Phase](https://github.github.com/gh-aw/blog/2026-01-13-meet-the-workflows-multi-phase/)).

제품 아이디어 쪽에서 가장 좋은 1차 사례는 Langfuse의 주간 다이제스트 skill이다. 한 주에 지원 티켓 481건, 열린 GitHub 이슈 53건과 최근 닫힌 14건, 회의록 38건을 모아 출처를 가로질러 묶고, 항목마다 근거 링크를 단다. 결과는 제품 영역이 아니라 "다음 단계가 분명한 것"과 "논의가 필요한 것"으로 나눈다. LLM-as-judge로 실행마다 actionability, 출처 표기, 범주 수를 채점하며 9번 고쳤다. 실패도 구체적으로 적었다. 소스 하나가 죽었을 때 말없이 건너뛰었고, 6개월 된 이슈를 최근 코멘트 때문에 현재 문제로 표시했고, 프롬프트를 고친 뒤 설명이 모호해진 회귀를 평가자가 잡았다 ([Langfuse](https://langfuse.com/blog/2026-03-13-weekly-digest-ai-skill)). 이 에이전트도 백로그에 직접 쓰지 않고 사람이 승격할 다이제스트를 낸다. 트래커 벤더도 같은 선을 긋는다. Linear Triage Intelligence는 팀, 담당자, 라벨, 중복·관련 관계를 제안하고, 속성마다 표시·숨김·자동 적용을 팀이 고르게 한다. 중복은 닫지 않고 관계로 제안한다 ([Linear](https://linear.app/docs/triage-intelligence)). 자동 크기 산정이나 우선순위 결정의 성과를 보고한 출처는 찾지 못했다.

### 회사에서는 무엇을 할지를 결정적 계층이 정한다

회사 규모의 주기 에이전트는 대부분 "할 일 찾기"를 에이전트에게 맡기지 않는다. Spotify는 Fleetshift가 대상 선정, 일정, 진행 추적을 맡고 Honk가 변경을 만든다. 자동 유지보수 PR은 누적 250만 건 이상 머지됐고 대부분 안전 검사 뒤 자동 머지다(Spotify 수치를 InfoQ가 보도) ([InfoQ](https://www.infoq.com/news/2026/10/spotify-ai-quality-controls)). Stripe는 CI가 flaky 테스트를 감지하면 minion을 띄우는 버튼이 달린 티켓을 만들고, 글에 예약 실행은 없다 ([Stripe](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents)). GitHub는 2026-04-07부터 Dependabot 알림을 코딩 에이전트에 배정할 수 있게 했고, 에이전트는 draft PR을 연다 ([GitHub changelog](https://github.blog/changelog/2026-04-07-dependabot-alerts-are-now-assignable-to-ai-agents-for-remediation)). Cursor Automations는 cron, Slack 메시지, 새 Linear 이슈, 머지된 PR 같은 트리거로 에이전트를 돌리고, 저위험 PR을 자동 승인하고 위험한 PR에는 리뷰어를 최대 2명 배정하는 "agentic codeowners" 예시를 소개한다(벤더 글) ([Cursor](https://cursor.com/blog/automations)).

### 주기는 일의 성격을 따르고, 노이즈는 생태계 수준의 실패다

공개된 주기는 이렇다. 트리아지는 이벤트로 돈다. 디스패처와 모니터는 30분에서 2시간이다. 상태 보고와 개선 에이전트는 매일 돌며 초점을 돌려 가고 메모리로 반복을 피한다. 다이제스트는 주간이다 ([agentics](https://github.com/githubnext/agentics); [Cursor](https://cursor.com/blog/automations); [Langfuse](https://langfuse.com/blog/2026-03-13-weekly-digest-ai-skill)). Spotify는 2026년 6월 24일 사고에서 변경량이 "outpaced some verification controls" 했다고 보고, 대응의 하나로 **자동 변경을 담당 팀의 근무 시간에 예약**하기로 했다 ([InfoQ](https://www.infoq.com/news/2026/10/spotify-ai-quality-controls)). 실행당 달러 비용, 보고서를 사람이 실제로 읽는 비율, 제안이 낡는 비율을 공개한 곳은 없다. 제안 에이전트의 가장 큰 실패는 받는 쪽의 과부하다. curl은 2026년 1월 하순까지 보안 리포트 20건을 받았고 한 주에 몰린 7건 중 취약점은 0건이었으며, 2019년 4월에 시작한 버그 바운티를 2026-01-31에 끝냈다 ([BleepingComputer](https://www.bleepingcomputer.com/news/security/curl-ending-bug-bounty-program-after-flood-of-ai-slop-reports/); [Stenberg](https://daniel.haxx.se/blog/2026/01/26/the-end-of-the-curl-bug-bounty/)). Jazzband는 2026-03-14에 AI 생성 스팸 PR과 이슈 때문에 열린 멤버십 모델을 유지할 수 없다며 단계적 정리(sunsetting)를 발표했다 ([Jazzband](https://jazzband.co/news/2026/03/14/sunsetting-jazzband)).

## Claude Code는 부품을 다 주지만 예약 실행은 리드로 돌아오지 않는다

Claude Code 문서는 병렬 실행 방법으로 서브에이전트, agent view(research preview), agent teams(실험), Projects(public beta), 동적 워크플로 다섯 가지를 든다. 결과가 돌아오는 길이 서로 다르다. "Subagents report results back to the conversation that spawned them, and agent view sessions report results only to you. Teammates in an agent team message each other directly" ([agents 문서](https://code.claude.com/docs/en/agents.md)). 아래 표들은 상위 세션 구조에 쓸 부품을 성숙도와 실행 위치로 나눈 것이다. 최신 릴리스는 v2.1.329(2026-11-19)다.

### 표가 말해 주는 여섯 가지 제약

**첫째, 지속되는 스케줄러는 리드 세션으로 보고하지 않는다.** 공식 비교에 따르면 클라우드 작업은 기기도 세션도 필요 없지만 로컬 파일이 없고 최소 주기가 1시간이다. Desktop 작업은 컴퓨터가 켜져 있어야 하고, `/loop`는 세션이 열려 있어야 한다 ([예약 문서](https://code.claude.com/docs/en/scheduled-tasks.md)). Desktop과 클라우드의 실행은 매번 새 세션이다 ([Desktop 예약 작업](https://code.claude.com/docs/en/desktop-scheduled-tasks.md); [routines](https://code.claude.com/docs/en/routines.md)). 결과를 모으려면 실행이 공유된 곳(파일, PR, 이슈)에 쓰거나 `SendMessage`를 써야 한다는 것은 이 사실들에서 나온 추론이다. 리드 세션 안의 `/loop`만이 같은 세션에서 발화하지만 7일 뒤 만료되고 세션을 닫으면 멈춘다.

**둘째, 세션 간 메시지는 보고 통로이지 승인 통로가 아니다.** 들어온 메시지는 "can't approve anything", "can't change configuration"이고 그 안의 명령은 실행되지 않는다. 기본 보류 규칙은 양방향이다. 수신 측이 권한을 묻는 세션이면 발신자가 bypass 권한일 때만 보류하고, 수신 측이 bypass 세션이면 모든 메시지를 보류한다. `-p`, VS Code, Desktop은 승인 대화상자를 띄우지 못해 보류된 메시지를 기한(기본 5분) 뒤에 버린다. 무인 워커가 메시지를 받으려면 `crossSessionInbound: accept`를 명시해야 한다 ([세션 간 메시지](https://code.claude.com/docs/en/cross-session-messaging.md)). 클라우드 예약 실행도 같은 선을 긋는다. "The fired prompt is therefore not live user input and can't act as approval or consent" ([routines](https://code.claude.com/docs/en/routines.md)).

**셋째, 백그라운드 세션의 결과물은 브랜치이고 PR은 조건부다.** worktree로 격리된 백그라운드 세션은 묻지 않고 커밋하고 원격이 있으면 자기 브랜치를 push한다. draft PR은 "when the task calls for it"일 때만 열고, 작업·CLAUDE.md·메모리의 git 지시가 우선한다. `main`이나 `master` push, force-push, merge는 하지 않는다 ([agent view](https://code.claude.com/docs/en/agent-view.md)). CLI 세션이 새 백그라운드 세션을 만드는 문서화된 도구는 없고, `claude --bg`를 셸로 부르거나 사용자가 `/fork`를 쓰는 길뿐이다(노트의 관찰). `claude --bg`는 `-p`와 함께 못 쓴다 ([헤드리스](https://code.claude.com/docs/en/headless.md)).

**넷째, 알림 훅 하나에 에스컬레이션을 걸면 안 된다.** `agent_needs_input`과 `agent_completed` 훅은 agent view 알림에 묶여 있고, 그 알림은 agent view가 열려 있을 때만 간다. 닫힌 상태에서 훅이 뜨는지는 문서에 없다 ([agent view](https://code.claude.com/docs/en/agent-view.md)). `TaskCreated`와 `TaskCompleted` 훅은 Task 도구 호출에 걸리는데, Task 도구는 최신 모델의 일반 세션에서 기본으로 빠져 있다. 그런 세션에서는 이 훅이 발화할 계기가 없다(뒤 문장은 추론). 백그라운드 세션과 클라우드 세션은 모델과 상관없이 Task 도구를 받는다 ([훅](https://code.claude.com/docs/en/hooks.md); [도구 레퍼런스](https://code.claude.com/docs/en/tools-reference.md)).

**다섯째, 세션을 백그라운드로 보내면 일부만 따라간다.** 백그라운드 셸 명령, 백그라운드 서브에이전트, `/loop` 작업은 넘어가지만 실행 중인 monitor는 멈추고, 워크플로는 Claude가 다시 띄워야 이어진다 ([agent view](https://code.claude.com/docs/en/agent-view.md)). `claude daemon stop --any`는 `--keep-workers` 없이 쓰면 호스팅 중인 백그라운드 세션도 함께 멈춘다. `-p`와 SDK에서 부모가 백그라운드 자식 서브에이전트를 기다리는지는 문서 본문과 CHANGELOG 2.1.328이 서로 다르게 말하므로, 그 동작에 기대는 설계는 피해야 한다 ([서브에이전트](https://code.claude.com/docs/en/sub-agents.md); [CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)).

**여섯째, 플러그인이 닿는 범위는 넓지만 세션 생성은 호스트의 일이다.** 플러그인은 skills, agents, hooks, MCP, monitors, workflows, channels, `bin/`을 실을 수 있고, 플러그인 훅은 플러그인이 로드되면 항상 발화한다. 루트 `CLAUDE.md`는 로드되지 않으므로 지침은 skill에 넣어야 한다 ([플러그인 구성요소](https://code.claude.com/docs/en/plugins/components.md)). Desktop 예약 작업을 만들거나 Desktop 세션을 여는 것은 호스트 기능이다. 조사 세션의 환경에서는 Desktop 호스트가 세션 시작 제안, 세션 목록과 메시지, 예약 작업 생성용 MCP 도구를 노출하는 것이 관찰됐다. 이는 문서에 적힌 것이 아니라 관찰이고, "Claude가 제안한 세션은 사용자가 Start를 눌러야 시작한다"는 Desktop 문서와는 맞는다 ([Desktop](https://code.claude.com/docs/en/desktop.md)). Desktop 앱 세션 안에서 `claude --bg`와 agent view가 그대로 쓰이는지는 이번 조사에서 확인하지 못했다.

출처는 순서대로 [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system), [Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)·[arXiv 2512.08296](https://arxiv.org/abs/2512.08296), [MAST v3](https://arxiv.org/html/2503.13657v3)·[v2](https://arxiv.org/html/2503.13657v2), [Cognition 2026](https://cognition.com/blog/multi-agents-working), [Cursor](https://cursor.com/blog/scaling-agents), [Harvard PDF](https://fion.ac/jellyfish.pdf), [Dev Interrupted](https://devinterrupted.substack.com/p/your-agents-should-ask-the-factory), [Octoverse](https://github.blog/news-insights/octoverse/octoverse-commits-pushes-reach-new-highs-in-2026-as-developers-build-with-agents/)다.

**이득이 나는 곳은 병렬로 쪼갤 수 있는 읽기다.** Anthropic은 자기 시스템이 잘 맞지 않는 경우로 모든 에이전트가 같은 맥락을 공유해야 하는 작업, 에이전트 간 의존성이 많은 작업, 그리고 병렬화할 하위 작업이 적은 대부분의 코딩 작업을 들었다. 관찰한 실패는 간단한 질문에 서브에이전트 50개를 띄우는 것, 모호한 지시로 두 서브에이전트가 같은 조사를 하는 것, 리드가 서브에이전트 묶음이 끝날 때까지 기다려 가장 느린 하나에 전체가 묶이는 것이었다 ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Kim et al.의 결과도 같은 모양이다. 병렬화할 수 있는 과업에서는 크게 오르고 순차 과업에서는 크게 떨어진다. 버전이 바뀌어도 이 방향은 유지됐다 ([arXiv 2512.08296](https://arxiv.org/abs/2512.08296)).

**쓰기를 나누면 암묵적 결정이 충돌한다.** Cognition의 2025년 글은 "Actions carry implicit decisions"라고 요약하고, 게임을 하위 작업으로 나누면 한 에이전트는 마리오풍 배경을, 다른 에이전트는 어울리지 않는 새를 만드는 예를 든다 ([Cognition 2025](https://cognition.com/blog/dont-build-multi-agents)). 2026년 후속 글은 통하는 패턴을 "writes stay single-threaded"로 정리한다. 추가 에이전트는 행동이 아니라 지능을 보탠다. 리뷰어는 코더의 기록 없이 diff만 보는 깨끗한 맥락에서 더 잘 잡는다. manager Devin이 child Devin을 띄우는 "map-reduce-and-manage"는 쓰지만, 병렬 쓰기 스웜은 "still don't see meaningful adoption"이고, 에이전트들이 임의로 협상하는 비정형 스웜은 "mostly a distraction"이라고 했다 ([Cognition 2026](https://cognition.com/blog/multi-agents-working)). 워커가 동시에 코드를 써야 한다면 파일·브랜치·worktree로 겹치지 않게 나누는 수밖에 없다는 것이 이 출처들과 앞 절의 실패 사례에서 나오는 결론이다.

**오케스트레이터를 두는 이유는 처리량보다 오류 차단이다.** Kim et al.의 v1과 블로그는 오케스트레이터가 "validation bottleneck" 역할을 해서 오류 증폭이 독립형 17.2배에서 중앙집중형 4.4배로 준다고 했다 ([Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)). MAST는 실패의 큰 몫이 조율보다 명세와 검증에 있다고 보여 준다. v2 기준으로 검증자가 있어도 컴파일이나 주석 같은 피상적 검사에 그쳐 ChatDev 정답률이 33.33%였다 ([MAST v2](https://arxiv.org/html/2503.13657v2)). 리드가 하위 결과를 그대로 넘기지 않고 검증 관문 노릇을 해야 한다는 것은 여기서 나온 추론이다.

**리드가 쥘 것과 넘길 것도 출처가 비슷하게 말한다.** 위임할 때는 서브에이전트마다 목표, 출력 형식, 도구와 자료 안내, 작업 경계를 준다. 서브에이전트는 결과를 외부 산출물에 저장하고 리드에는 가벼운 참조만 넘겨 "game of telephone"을 피한다. 리드는 계획을 외부 메모리에 두고, 끝난 단계를 요약해 보관한 뒤 새 맥락의 서브에이전트를 띄운다 ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). 서브에이전트는 수만 토큰을 쓰고 1,000~2,000토큰 요약만 돌려준다. 맥락이 길어질수록 회상이 떨어지는 context rot은 모든 모델에서 나타난다 ([Anthropic, context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). 압축은 초기 지시를 잃을 수 있으므로 지속 규칙은 매 요청에 다시 주입되는 CLAUDE.md에 두라고 Agent SDK 문서는 권한다 ([Agent SDK](https://code.claude.com/docs/en/agent-sdk/agent-loop)). 장기 하네스 글은 다음 세션이 진척을 보고 너무 일찍 완료를 선언하는 실패를 막으려고, 기계가 읽는 기능 목록에서 `passes` 값만 바꾸게 했다 ([Anthropic, harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). 리드 맥락을 몇 토큰에서 압축할지, 워커 요약의 최적 길이가 얼마인지에 대한 실험 데이터는 없다.

## 사람에게는 적은 수의 결정만, 급하지 않으면 묶어서 올린다

### 올릴 결정은 방향, 모호함, 권한 경계, 머지다

Anthropic의 실사용 분석(2026-02-18, 자사 데이터)은 Claude가 스스로 멈춰 묻는 이유를 집계했다. 접근법 선택지 제시 35%, 진단 정보나 테스트 결과 수집 21%, 모호한 요청 명확화 13%, 자격증명·접근 권한 요청 12%, 행동 전 승인 11%다. 가장 복잡한 작업에서는 Claude가 스스로 멈춰 묻는 빈도가 사람이 중단시키는 빈도의 2배를 넘었다. 사용자가 익숙해질수록 전체 자동 승인 세션은 늘지만(50세션 미만에서 약 20%, 750세션쯤에 40% 이상), 턴당 중단율도 약 5%에서 약 9%로 오른다. 숙련자는 더 맡기되 더 자주 끼어든다는 뜻이다. 이 글은 "It's too early to mandate specific interaction patterns"라며, 모든 행동에 승인을 요구하는 방식보다 가시성과 쉬운 개입을 권한다 ([Anthropic](https://www.anthropic.com/research/measuring-agent-autonomy)). auto mode의 차단 범주는 사람에게 올려야 할 행동의 구체적 목록이 된다. 데이터 파괴와 유출(force-push, 대량 삭제), 보안 약화, 신뢰 경계 넘기(외부 코드 실행, 자격증명 찾기), 리뷰 우회와 타인에게 영향을 주는 행동(main 직접 push, 프로덕션 배포)이다 ([Anthropic, auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode)). 여기에 앞선 서베이의 두 게이트(계획 승인, 머지 승인)를 더하면 검수 지점의 목록이 나온다. 이 조합은 출처들을 엮은 해석이다. Cognition의 글에는 사람이 언제 개입해야 하는지에 대한 기준이 없다.

### 도구 호출마다 승인받는 방식은 무너진다

**사용자는 권한 프롬프트의 대부분을 그냥 승인한다.** Anthropic은 2026-03-25 엔지니어링 글에서 93%, 2026-08-07 블로그에서 97%라고 밝혔다. 둘 다 Anthropic의 1차 수치다 ([Anthropic](https://www.anthropic.com/engineering/claude-code-auto-mode); [claude.com](https://claude.com/blog/auto-mode-default-in-claude-code)). 같은 블로그는 유료 전문 테스터 1,053명의 통제 실험에서 사람 검토가 위험 명령의 13.6%를, auto mode가 89%를 잡았다고 했다. 실험 방법의 상세는 그 글에서 확인하지 못했다. auto mode 분류기의 오류율은 실제 트래픽 오탐 0.4%, 실제 과잉행동 미탐 17%(n=52), 합성 유출 미탐 5.7%다. Anthropic 스스로 "not a drop-in replacement for careful human review on high-stakes infrastructure"라고 적었다 ([Anthropic](https://www.anthropic.com/engineering/claude-code-auto-mode)). 이 숫자들은 모두 벤더 자체 측정이다.

독립 근거는 둘이고 둘 다 강도가 약하다. "Habituation at the Gate"는 반복 리뷰어 400명의 리뷰 11,429건을 7개월 추적해, 에이전트 PR 승인율이 30.1%에서 36.8%로 오르고 인라인 코멘트가 22% 줄었다고 보고했다. 저자는 이를 합리적 신뢰 보정보다 "reflexive habituation under growing workload"에 가깝다고 해석한다. 5쪽짜리 워크숍 논문이다 ([arXiv 2606.22721](https://arxiv.org/abs/2606.22721)). "Oversight Has a Capacity"는 피로해지는 리뷰어를 모델링해, 실제 안전성이 에스컬레이션 비율에 대해 역U자형이고 "more human oversight can make a system less safe"라고 주장한다. 단독 저자의 모델링 프리프린트이고 사람 실험이 아니다 ([arXiv 2606.08919](https://arxiv.org/abs/2606.08919)). 방향은 벤더 수치와 같다. 개별 승인을 늘릴수록 승인의 값이 떨어진다.

### 묶어서 전하되, 완전히 끊지는 않는다

알림 묶음의 근거는 에이전트 맥락이 아니라 일반 HCI 연구에서 온다. Fitz et al.(2019)의 237명 무작위 현장 실험에서, 알림을 하루 3번 묶어 받은 집단은 대조군보다 더 주의 깊고 생산적이라고 느꼈으며 스트레스와 방해가 적었다. 매시간 묶음은 이득이 거의 없었다. **알림을 아예 받지 않은 집단은 불안과 FoMO가 높았다** ([Duke Scholars](https://scholars.duke.edu/display/pub1402953); [저자 요약](https://communities.springernature.com/posts/batching-notifications-can-improve-attention-well-being-and-productivity)). 코딩 에이전트에서 다이제스트와 즉시 인터럽트를 직접 비교한 실험은 찾지 못했다. 제품들은 이미 좁히는 쪽을 택했다. Projects의 데스크톱 알림 기본값은 코디네이터가 글을 올릴 때, thread 에러, 입력 필요 세 가지다 ([Projects 문서](https://code.claude.com/docs/en/claude-projects)). agent view에서 예약된 `/loop` 세션은 입력이 필요할 때만 알린다 ([agent view](https://code.claude.com/docs/en/agent-view.md)). gh-aw는 같은 날의 실행을 이슈 하나로 모으고 이전 보고를 닫는다 ([Safe Outputs](https://github.github.com/gh-aw/reference/safe-outputs/)). "막힘은 즉시 알리고 나머지는 묶는다"는 이원화는 이 근거들에서 나온 추론이다. Claude Code에서 `AskUserQuestion`은 v2.1.200부터 답할 때까지 열려 있고, 백그라운드 세션에서는 유휴 타이머가 시작되지 않는다 ([도구 레퍼런스](https://code.claude.com/docs/en/tools-reference.md)). 즉 막힌 하위 세션은 누군가 볼 때까지 그 자리에 서 있고, 사람이 그것을 알게 하는 장치는 따로 있어야 한다.

### 무인 구간은 격리, 하드 상한, 자기 승인 금지로 막는다

상한의 기본값은 "없음"이다. Agent SDK의 `max_turns`와 `max_budget_usd`는 기본이 무제한이고, 예산에는 서브에이전트 비용이 포함된다. 검사가 응답이 도착한 뒤에 일어나므로 응답 하나와 실행 중인 서브에이전트만큼 초과할 수 있다. 문서는 "Setting a budget is a good default for production agents"라고 쓴다 ([Agent SDK](https://code.claude.com/docs/en/agent-sdk/agent-loop)). auto mode는 거부가 연속 3회나 누적 20회에 이르면 모델을 멈추고 사람에게 올리며, 헤드리스에서는 프로세스를 끝낸다 ([Anthropic](https://www.anthropic.com/engineering/claude-code-auto-mode)). 오케스트레이터들도 비슷한 장치를 둔다. Symphony는 워커당 최대 20턴과 stall 타임아웃을 두고 ([SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md)), Factory는 "feature retry limit"을 둔다 ([Factory](https://docs.factory.com/cli/features/missions)). Paperclip의 예산 하드 스톱은 기록된 지출 기준이라 멈추는 데 지연이 있을 수 있다 ([paperclip](https://github.com/paperclipai/paperclip)). 자기 승인을 막는 장치는 여러 층에 있다. 세션 간 메시지와 예약 프롬프트는 승인으로 취급되지 않는다. auto mode는 main 직접 push를 차단 범주에 둔다. v2.1.326부터 격리 worktree의 서브에이전트는 대부분의 모델에서 공유 브랜치를 다시 쓰는 git 명령을 거부한다 ([changelog](https://code.claude.com/docs/en/changelog)). 앞선 서베이가 정리한 원칙인 작성자와 판정자의 분리는 여기서도 그대로 적용된다. 리드가 하위 세션을 강제로 끝내는 킬 스위치의 표준 설계나, 무인 장기 실행의 비용 폭주 사고 통계는 찾지 못했다.

## 원하는 구조에 비춰 본 선택지

이 절은 설계안이 아니라 관찰과 선택지다. 전제는 이렇다. 읽는 사람은 `/task create | start | end` 루프(`docs/backlog`의 백로그 파일 → 승인받는 계획 → 작업 브랜치에서 구현 → 리뷰 → 승인받는 머지)를 가진 플러그인을 유지하고, Claude Code를 주로 Windows의 Desktop 앱에서 쓰며, 다른 도구가 이미 하는 일을 겹쳐 만들지 않는 단순한 skill을 선호한다. 세 요구를 부품에 대면 다음과 같다.

| 요구 | 쓸 수 있는 부품 | 출처가 말해 주는 것 |
|---|---|---|
| (1) 백로그 담당 세션이 주기적으로 돌며 상위 세션에 보고 | Desktop 예약 작업, 클라우드 예약 작업, 리드 세션의 `/loop`, GitHub Actions나 gh-aw | 지속 스케줄러의 실행은 매번 새 세션이고 리드로 돌아오지 않는다. 주기 에이전트는 공유 원장에 제안을 남기고, 사람이 승격한다. 실행당 산출 상한, 굴러가는 보고서 하나, "할 일 없음" 허용, 만료가 노이즈를 막는다 |
| (2) 상위 세션이 작업 세션을 만들어 일을 돌림 | 서브에이전트(worktree 격리), 플러그인 워크플로, 백그라운드 세션과 세션 간 메시지, Desktop 세션, Projects thread | 쓰기는 한 줄이거나 겹치지 않는 범위여야 한다. 리드는 검증 관문이다. 워커는 산출물과 짧은 요약으로 보고한다 |
| (3) 검수가 필요한 지점에서 사용자에게 보고 | `AskUserQuestion`, Desktop OS 알림, `PushNotification`, Projects Overview, 채널 | 올릴 것은 계획 승인, 머지 승인, 되돌릴 수 없는 행동, 막힘이다. 도구 호출 단위 승인은 실효가 낮다. 막힘은 즉시, 나머지는 묶는다 |

**먼저 눈에 띄는 것은 `docs/backlog`가 이미 원장이라는 점이다.** Gas Town의 Beads, Symphony의 트래커, Projects의 메모리 파일이 하는 일(세션이 죽어도 다음 세션이 이어받게 하는 것)을 백로그 파일과 항목 파일의 Implementation Notes, 작업 브랜치의 커밋이 이미 하고 있다. 요구 (1)의 "상위 세션에 보고"는 그래서 메시지 전달보다 "백로그에 무엇을 어떤 형식으로 남기느냐"의 문제에 가깝다. gh-aw와 Langfuse 사례에 비추면, 주기 실행이 백로그 항목을 직접 늘리는 것보다 제안 하나를 굴리는 편이 노이즈에 강하다. 실행마다 제안 수에 상한을 두고, 이전 제안을 대체하고, 근거 링크를 달고, 할 일이 없으면 없다고 쓰고, 사람이 승격한 것만 백로그 항목이 되게 하는 방식이다.

### 선택지 A: 리드는 한 세션, 쓰기는 한 줄, 백로그 정리만 예약한다

구성은 가장 얇다. 백로그 정리·제안은 Desktop 예약 작업(로컬 파일을 보므로 `docs/backlog`를 그대로 읽고 쓴다)이나 리드 세션의 `/loop`로 돌리고, 결과는 백로그 쪽 파일에 남는다. 리드 세션은 시작할 때 그 파일을 읽고, 한 번에 항목 하나를 지금의 `/task start`대로 진행한다. 서브에이전트는 조사와 리뷰에만 쓴다. 사람 게이트는 지금의 두 곳 그대로다. 근거는 가장 탄탄하다. Cognition의 "writes stay single-threaded" ([Cognition](https://cognition.com/blog/multi-agents-working)), Anthropic의 "대부분의 코딩 작업은 병렬화할 하위 작업이 적다" ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)), Willison의 "의미 있는 변경은 하나씩 리뷰" ([simonwillison.net](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/))가 모두 이 모양을 가리키고, Harvard 결과는 워커를 늘려도 리뷰가 상한이라고 말한다 ([논문 PDF](https://fion.ac/jellyfish.pdf)). 새로 만들 것이 거의 없다는 점도 "겹쳐 만들지 않는다"는 선호와 맞는다. 스케줄링과 알림은 호스트가 한다. 대가는 병렬 구현이 없다는 것이다. 열린 위험은 세 가지다. Desktop 예약 작업은 앱이 열려 있고 컴퓨터가 깨어 있을 때만 돌고, 놓친 실행은 최근 1회만 보충한다. `/loop`는 7일 뒤 만료된다. 예약 실행 세션이 리드 세션에 직접 메시지를 보낼 수 있는지는 Desktop 문서의 세션 간 메시지 기능으로는 가능해 보이지만 이번 조사에서 확인하지 않았다. 그리고 주기 실행이 쓴 제안을 사람이 실제로 읽는지는 어느 출처도 수치를 주지 않는다.

### 선택지 B: 리드가 격리된 워커를 병렬로 띄우고 검증 관문이 된다

리드가 서로 겹치지 않는 백로그 항목 몇 개를 골라 항목마다 워커를 띄운다. 워커는 worktree로 격리한 서브에이전트(세션 안에서 살고 결과가 완료 알림으로 돌아온다), 플러그인 워크플로(상한과 진행 화면이 있다), 또는 백그라운드 세션(`claude --bg`, 터미널을 닫아도 살고 `notify_when_idle`로 끝남을 안다) 중 하나다. 워커는 자기 브랜치에 커밋하고 요약을 돌려주고, 리드는 리뷰와 검증을 돌린 뒤 결과를 묶어 사용자에게 올린다. 선례는 Factory Missions(사람이 계획을 승인한 뒤 워커 실행) ([Factory](https://docs.factory.com/cli/features/missions)), 의존성 그래프로 웨이브를 만들어 웨이브 안의 태스크를 동시에 돌리는 Kiro ([Kiro](https://kiro.dev/docs/specs/)), Cursor의 planner–worker–judge다 ([Cursor](https://cursor.com/blog/scaling-agents)). 대가와 위험은 앞 절들이 그대로 말해 준다. 토큰은 워커 수에 비례한다(백그라운드 세션 10개면 쿼터도 약 10배) ([agent view](https://code.claude.com/docs/en/agent-view.md)). 같은 파일을 건드리면 덮어쓰기와 머지 충돌이 난다. 리드가 워커를 기다리지 않고 직접 구현하거나 일찍 끝났다고 판단할 수 있다. 워커의 권한 프롬프트가 리드로 몰린다. 계획 승인도 문제가 된다. 워크플로는 실행 중 사용자 입력을 받지 못하므로, 항목별 계획 승인을 워커를 띄우기 전에 한꺼번에 받거나 워커를 계획 단계와 구현 단계로 나눠야 한다. 무엇보다 워커 N개는 리뷰 대상 N개를 만든다. Zigler의 제안대로라면 동시 워커 수의 상한은 사람이 하루에 검수할 수 있는 양에서 정해진다 ([Dev Interrupted](https://devinterrupted.substack.com/p/your-agents-should-ask-the-factory)). 부품 쪽 위험도 있다. agent view는 research preview이고, Desktop 앱에서의 동작은 확인하지 못했으며, `agent_needs_input` 훅은 agent view가 열려 있을 때만 확실하다. 세션을 백그라운드로 보내면 워크플로는 저절로 이어지지 않는다. agent teams는 실험 기능이고 환경 변수가 필요하므로 플러그인이 기대기 어렵다.

### 선택지 C: 코디네이터를 클라우드에 둔다

상위 세션 자체를 Projects에 맡기는 길이다. 계속 이어지는 대화가 코디네이터가 되고, 작업마다 클라우드 thread가 자기 브랜치에서 일해 PR을 열며, Overview가 Ready for review, Waiting on you 같은 상태로 검수 지점을 보여 준다. 프로젝트 안에서 예약 작업을 요청하면 클라우드 예약 작업으로 만들어져 thread로 돈다. 요구 세 가지가 제품 하나에 이미 들어 있고, 컴퓨터가 꺼져 있어도 돈다. 플러그인을 겹쳐 만들지 않는다는 선호에는 가장 잘 맞는다. 대가는 통제력이다. Projects는 Pro·Max·Ultra의 public beta이고 Team·Enterprise는 지원하지 않는다. 클라우드 thread는 로컬 `.claude/skills/`를 로드하지 않아서 `/task` skill을 쓰려면 Project settings에서 플러그인을 추가해야 한다. 실행은 새 clone에서 시작하므로 `docs/backlog`가 push되어 있어야 보인다. 코디네이터는 전체 기록이 아니라 최근 내용과 메모리로 일한다. 유휴 thread도 깨어날 때 사용량을 쓴다. 클라우드 예약 작업의 최소 주기는 1시간이다 ([Projects 문서](https://code.claude.com/docs/en/claude-projects); [routines](https://code.claude.com/docs/en/routines.md)). 같은 방향의 저장소 중심 변형은 GitHub Actions의 `schedule`이나 gh-aw로 백로그 제안을 이슈나 PR로 받는 것이다. safe output의 상한과 중복 제거를 그대로 얻지만, 원장이 `docs/backlog` 파일에서 GitHub 이슈 쪽으로 기운다.

### 세 선택지에 공통인 관찰

어느 쪽을 택하든 플러그인의 몫으로 남는 것은 좁다(해석). 스케줄링, 세션 생성, 알림은 호스트(Desktop 예약 작업, `/loop`, Projects, agent view)가 이미 한다. 호스트가 하지 않는 것은 세 가지 계약이다. 주기 실행이 백로그에 무엇을 어떤 상한으로 남기는가, 워커가 무엇을 어떤 형식으로 보고하는가(산출물 경로, 짧은 요약, 완료·막힘·질문 상태), 어느 지점에서 사람에게 올리는가다. 앞선 서베이가 `/task` 루프에서 짚은 빈자리도 그대로 따라온다. 작성자가 볼 수 없는 판정 기준(홀드아웃)이 없고, 완료 전 검증이 훅이 아니라 지침이다. 워커가 늘면 이 빈자리의 비용도 워커 수만큼 커진다. Windows에서는 추가로 확인할 것이 있다. Monitor는 Git Bash가 필요하고, 훅의 `bash`가 WSL로 잡힐 수 있으며, WSL 2 세션과 네이티브 Windows 세션은 서로 메시지를 주고받지 못한다.

## 결론

이번 서베이가 바꾸는 그림은 "상위 세션"의 정체다. 공개된 구조들에서 지휘하는 것은 오래 사는 똑똑한 세션이 아니라 세션 밖의 원장이고, 리드 세션은 그 원장을 읽고 쓰는 여러 세션 가운데 하나다. Symphony는 리드 LLM을 아예 두지 않았고, Projects의 코디네이터는 기록 대신 메모리 파일로 일하며, Gas Town은 리드 옆에 결정적 순찰자를 붙였다. Claude Code가 넉 달 사이에 채운 것도 세션들 사이의 통로와 스케줄러이지, 더 오래 기억하는 리드가 아니다. 그래서 "하위 세션이 상위 세션에 보고한다"는 문장은 "하위 세션이 원장에 쓰고, 다음에 깨어난 리드가 읽는다"로 바꿔 읽는 편이 실제 구조에 가깝다.

두 번째 변화는 상한의 위치다. 앞선 서베이는 자동화의 한계를 누가 완료를 판정하느냐에서 찾았다. 이번 근거는 거기에 양을 더한다. 워커를 늘리면 코드와 PR은 늘지만 머지까지 걸리는 시간도 늘고, 승인은 습관이 된다. 벤더들이 저위험 자동 머지와 의도 단위 리뷰로 움직이는 것은 이 상한을 넘으려는 시도이고, 그 결과의 사고율은 아직 아무도 공개하지 않았다. 열린 문제는 분명하다. 다이제스트와 즉시 인터럽트를 코딩 에이전트에서 비교한 실험, 주기 보고서를 사람이 읽는 비율, 오케스트레이터별 비용의 독립 측정, 병렬 작성과 단일 작성을 코딩 과업에서 정량 비교한 연구가 없다. 그때까지는 워커 수를 검수 용량에 맞추는 쪽이 근거가 있는 유일한 기준이다.

## 검수 결과

세 팩트체크 파일이 다섯 노트에서 고른 주장 198개를 공개 페이지와 직접 대조했다. 결과는 **확인 154개, 수정 필요 29개, 확인 불가 14개, 틀림 1개**다. Claude Code 기능 노트는 47개 중 확인 38, 수정 8, 확인 불가 1, 틀림 0이었다. 오케스트레이터·최근 동향 노트는 79개 중 확인 59, 수정 12, 확인 불가 8, 틀림 0이었다. 주기 에이전트·에스컬레이션 노트는 72개 중 확인 57, 수정 9, 확인 불가 5, 틀림 1이었다. 지어낸 출처, 명령, 논문은 발견되지 않았다. 확인한 명령·플래그·도구·환경 변수·한도는 모두 공식 페이지에 그대로 있었고, "Habituation at the Gate"와 "Oversight Has a Capacity"도 arXiv에 실재한다.

이 보고서에 반영한 주요 수정은 다음과 같다. 틀림 1건은 Fitz 2019의 FoMO 귀속이다. FoMO와 불안이 높아진 쪽은 하루 3회 묶음 집단이 아니라 알림을 아예 받지 않은 집단이다. 버전에 따라 수치가 바뀐 논문은 셋이다. Harvard 워킹페이퍼는 2026-11-19 버전의 수치(655개 기업, PR +35.7%, 머지까지 +56.1%)를 기본으로 쓰고 2026-08-04 버전을 따로 밝혔다. Kim et al.은 v1·블로그 수치와 v3 수치를 나눠 적었고, 17.2배 대 4.4배가 v3 초록에 없다는 점을 표시했다. MAST는 v3 값을 쓰고 v2와 다르다는 점을 적었으며, NeurIPS 채택은 확인되지 않아 뺐다. Claude Code 쪽에서는 백그라운드 세션의 draft PR이 무조건이 아니라 조건부라는 것, 세션 간 메시지의 기본 보류 규칙이 양방향이라는 것, `agent_needs_input` 훅이 agent view가 열려 있을 때의 알림에 묶여 있다는 것, 유휴 1시간 뒤에는 프로세스가 일시정지가 아니라 종료된다는 것, `claude daemon stop --any`의 동작, 워크플로 크기 가이드의 Pro 기본값, `-p` 10분 상한의 예외, 중첩 서브에이전트 대기 동작에서 문서와 CHANGELOG가 어긋난다는 것을 고쳤다. 원문에 없던 인용문 셋(Gas City, Symphony, Cursor)은 원문 문장으로 바꿨고, Symphony의 Linear 근거는 SPEC이 아니라 README로 옮겼다. Claude Code Projects는 "재출시"가 아니라 2026-09-17 베타 출시로 고쳤다. Fable 5.1 출시일은 두 1차 출처의 날짜를 함께 적었고, Opus 5.5의 "40% 저렴"은 운영 비용 기준이며 토큰 단가는 20% 낮다고 바로잡았다. v2.1.328의 auto mode 변경은 서드파티 클라우드의 일부 모델에 한정된 것이어서 전체 기본값 변경으로 쓰지 않았다. Anthropic의 merge queue 서술은 "락을 대체했다"에서 "전역 락을 재현할 수 없어 머지 후 테스트에 투자했다"로 고쳤다. 권한 프롬프트 승인율 93%와 97%는 둘 다 Anthropic 1차 수치로 적었고, auto mode 기본값 전환과 1,053명 실험은 1차 출처를 달되 적용일은 단정하지 않았다. gh-aw 머지율은 "57~78%, 표본이 큰 워크플로만의 자기보고"로 통일했다. curl 일화는 출처가 받치는 문장으로 다시 썼고, Jazzband는 1차 글 기준으로 "단계적 정리"라고 적었다. Cognition 2026 글의 "mostly a distraction"은 비정형 스웜에 대한 평가로 바로잡았다. Spotify Fleet Management의 "2022년부터"는 근거가 없어 뺐다.

확인 불가로 판정돼 빼거나 미확인으로 표시한 것도 있다. 뺀 것은 gh-aw Plan Command 머지율, hyrax.dev의 79%, Airflow 일화, Agent HQ의 "지정된 브랜치에만 커밋", Conductor의 투자 배너, Gas City의 Gas Town pack 기본 포함, GPT-6.1 Terra와 Codex 한도, Cursor 9~10월 항목, Factory 투자와 Droid 1.0, Codex `workspace-write`의 `/tmp`와 네트워크 기본값, 백그라운드 서브에이전트의 정확한 도구 목록이다. Conductor 종료 건은 본문에 미확인으로 남겼다.

검수가 닿지 않은 범위도 있다. Claude Code 기능 가운데 GitHub Actions, Agent SDK 세션 API, Desktop 문서의 세션 관리와 Remote Control 세부는 이번에 다시 대조하지 않았다. 릴리스 날짜는 v2.1.139, v2.1.224, v2.1.329 세 개만 릴리스 API로 확인했다. Yegge의 Medium 원문과 DoltHub 원문은 열지 않았고 재게시본과 2차 글로 확인했다. LinearB 보고서 원문은 열지 않았다. Devin Bots는 Cognition 자체 페이지가 아니라 Fortune과 AlphaSignal로만 확인했다. Fitz 2019는 초록과 저자 요약만 읽었다. gh-aw Safe Outputs 페이지의 draft PR 보호와 위협 탐지 구역은 읽지 않았다. 접근이 막힌 페이지(OpenAI 도움말, The New Stack, Axios, DevOps.com)는 우회하지 않았다. 본문에서 "해석"이나 "추론"이라고 표시한 문장과 "원하는 구조에 비춰 본 선택지" 절은 출처의 사실이 아니라 그 사실들을 엮은 판단이다.
