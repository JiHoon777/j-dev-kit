# 최고 실무자들은 Claude Code 스킬을 어떻게 쓰나 (2026-11-23)

질문: 이 분야 최고 실무자들은 Claude Code 스킬(SKILL.md)을 실제 작업에서 어떻게 쓰는가. j-dev-kit 과는 무엇이 다른가.

**읽은 방법**
- 공식 문서·블로그·저장소 파일(A1~A14)은 이 세션에서 원문을 직접 받아 읽었다.

- 결론에 쓰는 문장은 이 세션에서 원문을 다시 열어 확인했다. E1, E2, E3, E4, E5, E10, E11 과 P1, P2, P5, P8, P10, P12, P15 다.
- 확인하지 못한 것은 맨 끝에 적었다.

**인용**
- 인용은 15단어 이하다.
- 라이선스가 열려 있지 않은 글은 원문을 옮기지 않고 풀어 썼으며, 절 이름을 달았다.

## 2. 주제별 발견

### 2.1 스킬, CLAUDE.md, 훅, 서브에이전트, 그냥 프롬프트에 각각 무엇을 두나

#### 판단하는 것과 강제하는 것을 나눈다

- **A2:** 지시는 두 종류다.
  - 프롬프트·CLAUDE.md·스킬은 모델이 판단해서 따른다.
  - 훅·deny 규칙·관리 설정은 하네스가 매번 실행한다.
  - 강조를 계속 더해도 놓치는 줄은 훅으로 옮긴다. 반대로 선호일 뿐인 훅은 지운다.
- **E13:** CLAUDE.md 의 "절대 하지 마" 규칙은 맞지 않는 도구다. 진짜 가드레일은 결정적이어야 한다.

#### 스킬은 절차, CLAUDE.md 는 사실

- **A1:** 같은 지시·체크리스트·절차를 계속 붙여 넣거나, CLAUDE.md 한 절이 절차가 됐을 때 스킬로 만든다. 스킬 본문은 쓸 때만 올라온다.
- **E13:** 배포 워크플로, 릴리스 체크리스트, 리뷰 절차는 스킬에 둔다. CLAUDE.md 는 200줄 이하로 두고 관리할 사람을 정한다.
- **E2:** CLAUDE.md 의 토큰은 대부분 코드베이스의 함정(gotchas)에 쓴다. 검증 스킬을 만들어 CLAUDE.md 에서 가리킨다.
- **E6:** Boris 는 하루에도 여러 번 하는 "inner loop" 일을 명령이나 스킬로 만든다. 하루 한 번 넘게 하는 일이 기준이다. 자기 설정은 "surprisingly vanilla"라고 한다.

#### 적는 기준은 하나

- 저장소를 읽어 알 수 있고 실제로 찾아본다면 적지 않는다(A2).
- A2 는 "The CLAUDE.md rule applies to skills too"라고 적는다.
- Thariq: "A skill that restates what Claude would do by default adds context without adding value."(E1)
- obra 의 분류(P1)
  - 프로젝트 관례는 지시 파일에 둔다.
  - 정규식·검증으로 강제할 수 있는 것은 자동화한다.
  - 문서는 판단이 필요한 것에 쓴다.

#### 결정적인 일은 코드로

- 정렬처럼 코드가 할 일은 스크립트가 싸고 재현된다(A5).
- Huntley 는 Ralph 루프의 핵심을 나쁜 코드에서 루프가 닫히지 않게 하는 결정적 검사로 본다. 그것은 스킬이 아니라 엔지니어링이라고 한다(P15 answer).
- HumanLayer 는 린터가 할 일을 LLM 에 시키지 말라고 한다(**[2025]** Writing a good CLAUDE.md).
- Boris 는 PostToolUse 훅으로 포맷을 맞춘다(E6).

#### 서브에이전트: 역할 분담이 아니다

- HumanLayer 는 "frontend engineer", "backend engineer" 서브에이전트를 해 봤고 안 됐다고 쓴다. 서브에이전트는 컨텍스트 관리용이다(P12 "Sub-Agents Are for Context Control"). Dex 도 같은 말을 한다(P13).
- Boris 는 역할 이름 붙인 서브에이전트가 "too anthropomorphic"하고, 가치는 서로 상관없는 컨텍스트 창에 있다고 한다(E7).
- Sarkis 는 여러 기업 배포를 비교했다(E10).
  - 스킬을 가진 에이전트 하나가 서브에이전트 설계보다 자주 품질이 높았다. 비용과 지연도 낮았다.
  - 조직도를 에이전트 구조로 베끼지 말라고 한다.
- A2 의 정리: 서브에이전트는 같은(또는 작은) 모델이라 더 똑똑한 답을 주지 않는다. 얻는 것은 병렬, 긴 출력 격리, 새 눈의 리뷰, 도구 제한이다.

#### 명령과 이름 붙은 에이전트가 스킬로 들어간다

- obra 는 v5.1.0(2026-04-30)에서 슬래시 명령과 `code-reviewer` 에이전트를 지우고 스킬 안의 프롬프트 템플릿으로 옮겼다(P2).
- Armin 은 명령을 스킬로 옮기는 중이다(P8).
- HumanLayer `.claude/`에는 `commands/`, `agents/`가 없어졌다(P14, 시점은 모름).
- Every 는 리뷰어를 스킬 안의 자산으로 옮겼다(P18).
- Thariq·Delba 는 리뷰와 검증을 스킬로 옮겼다고 쓴다(E2, E9).

#### MCP 대신 CLI

- 모델이 `--help`를 읽으니 CLI 가 토큰을 덜 쓴다(P5).
- Armin 은 MCP 를 스킬로 옮기고 있다(P7).
- 스킬은 전문 지식을, MCP 는 바깥 연결을 준다(E14).
- A2 도 CLI 가 있으면 그게 가장 쉬운 길이라고 한다.

### 2.2 작게 유지하기, 언제 지우나, 효과를 어떻게 재나

#### 작게 시작해 실수로 키운다

- E1
  - 좋은 스킬은 몇 줄과 함정 하나로 시작했다.
  - "The highest-signal content in any skill is the Gotchas section."
  - 너무 많이 하려는 스킬은 여러 범주에 걸쳐 에이전트를 헷갈리게 한다.
- 크기 기준
  - SKILL.md 500줄 이하(A1, A4). 표준은 500줄·5,000토큰(A13).
  - obra 는 자주 불리는 스킬 200단어, 나머지 500단어를 목표로 둔다(P1 discovery.md).
- 지나치게 자세하면 해가 된다(A13).
  - 관련 없는 지시를 따라 헛걸음을 한다.
  - 규칙을 더해도 통과율이 오르지 않으면 지시를 지워 보라고 한다.
- 과잉 제약(E2): Claude Code 팀은 시스템 프롬프트·CLAUDE.md·스킬로 Claude 를 과하게 묶고 있었다고 쓴다. 예시는 탐색 범위를 좁혀서 오히려 묶는다.

#### 반감기

- **Claude Code 시스템 프롬프트(E2, E5):** Claude 5 세대에서 80% 넘게 지웠다. 코딩 eval 에서 잃은 것은 측정되지 않았다(E2).
- **Boris 의 권고(E5 7:02~8:19):** 여섯 달마다 CLAUDE.md·스킬·훅을 지우고 모델이 어떻게 하는지 본다. 같은 데서 거듭 넘어질 때만 다시 넣고, 추측해서 미리 넣지 않는다.
- **팀의 방법(E5 6:14):** 시스템 프롬프트를 통째로 지우고 한 줄씩 되돌리며 줄마다 효과를 잰다(ablation).
- **두 종류의 스킬(A6):**
  - 모델이 못 하던 것을 하게 하는 "capability uplift" 스킬은 모델이 나아지면 덜 필요해진다. 스킬 없이 eval 을 통과하면 더 필요 없다.
  - 팀의 절차를 담는 "encoded preference" 스킬은 오래간다.
- **실무자:**
  - Armin: "I throw skills away if I don't need them."(P8)
  - Huntley 는 모델이 이미 아는 도구에 스킬이 필요 없다고 한다(P15).
  - HumanLayer 는 실패를 본 뒤에만 더하고, 도움 안 되는 건 버린다(P12).
  - obra 는 요즘 에이전트가 이미 따르는 내용을 되풀이하던 표를 지웠다(P2 v6.1.0).
- **지울 때도 잰다:** obra 는 TDD 반박 절을 지웠더니 테스트 먼저 쓰는 행동이 떨어져 되돌렸다. 대조군 8/10 → 지운 쪽 5/10 이고, Claude 와 Codex 둘 다 그랬다(P2 v6.2.0, 2026-07-23).
- **도구:**
  - `/claude-api prompt-audit`(= `/doctor prompt-audit`)는 옛 모델용 지시를 찾는다(A1). Anthropic 실험에서는 "필수 6단계 절차", "두 번 검증" 규칙을 지워 비용을 9% 더 줄였다(E11).
  - `/skill-doctor`는 스킬마다 비용과 사용 빈도를 보여 준다(A1, E10).
  - E3: .md 파일과 검증 단계는 내버려 두면 늘기만 하니 주기적으로 정리한다.

### 2.3 description 과 트리거, 점진적 공개, 스킬 안의 스크립트

#### description 은 트리거 조건이다

- Thariq: "the description field is not a summary, it's a description of when to trigger"(E1)
- obra
  - description 은 "Use when…"으로 언제만 쓴다.
  - 절차를 요약하면 에이전트가 본문 대신 요약을 따른다: "Descriptions that summarize workflow create a shortcut agents will take."
  - 근거 사례: 리뷰를 두 번 하는 스킬에서 에이전트가 한 번만 했다(P1 discovery.md).
- Anthropic 문서는 조금 다르다(A4).
  - "무엇을 하고 언제 쓰나" 둘 다 쓴다. 3인칭으로 쓴다.
  - 핵심 용도를 앞에 둔다. 1,536자에서 잘린다.
  - 스킬이 많으면 덜 쓰는 것부터 description 이 빠진다(A1).
- Hamel 은 "Do NOT use for…"처럼 쓰지 말 때도 적는다(P19).

#### 트리거가 잘 안 될 때와 지나칠 때

- skill-creator 는 Claude 가 덜 부르는 경향이 있으니 조금 "pushy"하게 쓰라고 한다(A7, 2026-03).
- A8 은 Opus 4.5 부터 "CRITICAL: You MUST use this tool" 같은 말이 과잉 트리거를 낸다고 한다.
- 단순한 한 단계 요청에는 description 이 맞아도 스킬을 부르지 않는다(A7).
- 덧붙인 검사가 돌지 않으면 description 이나 앞의 지시가 그 검사를 끌어오지 못하는 것이다(E9).

#### 누가 부르나

- 부작용 있는 워크플로는 `disable-model-invocation: true`로 사용자만 부른다(A1). A1 의 말로는 "You don't want Claude deciding to deploy because your code looks ready."
- 배경 지식은 `user-invocable: false`로 모델만 부른다(A1).
- 스킬은 다른 스킬을 이름으로 가리키기만 해도 모델이 부른다(E1).

#### 점진적 공개

- 메타데이터 → SKILL.md → 보조 파일 3단계다(A5).
- 보조 파일은 한 단계 깊이로만 링크한다. 중첩하면 `head -100`처럼 일부만 읽는다(A4).
- 언제 읽을지를 적는다(A13). 파일 시스템 전체가 컨텍스트 엔지니어링이다(E1).

#### 압축 뒤 살아남기

- 스킬은 한 번 들어오면 다시 읽히지 않는다(A1).
- 압축 뒤에는 스킬마다 앞 5,000토큰만, 다 합쳐 25,000토큰 예산 안에서 다시 붙는다(A1, E13).
- obra 는 압축 뒤 잘린 스킬이 "다섯 번까지" 제한을 잃고, 한 작업에서 18번 고친 사례를 보고 긴 스킬 셋을 줄였다(P2 v7.0.1, 2026-10-21).
- 그래서 A1 은 두 가지를 권한다.
  - 중요한 지시를 위에 둔다.
  - 작업 내내 적용할 것은 상시 지시로 쓴다.

#### 스크립트

- 오류를 모델에 미루지 말고 스크립트가 처리한다("Solve, don't defer", A4).
- 계획 → 검증 스크립트 → 실행 순서로 한다(A4).
- 테스트마다 에이전트가 같은 헬퍼 스크립트를 새로 쓰면 `scripts/`로 묶는다(A7, A13). E14(Barry·Mahesh)는 Claude 가 같은 파이썬 스크립트를 거듭 쓰는 것을 보고 스킬에 저장하게 했다고 한다.
- Thariq: 스크립트와 라이브러리를 주면 Claude 가 턴을 조합에 쓴다(E1).
- 도구가 깔려 있다고 가정하지 말고 설치 명령을 적는다(A4).
- 성공 출력은 한 줄(✓), 실패만 전체 출력한다(P13).
- 스킬에는 그 스킬이 불릴 때만 켜지는 훅을 넣을 수 있다(E1, A1 `hooks`).

### 2.4 하지 말라고 한 것

**강조와 금지문**
- IMPORTANT·대문자·MUST 강조를 더하지 않는다. 지금 모델은 담백한 한 줄을 따르고, 강조하면 규칙을 과하게 적용한다(A2 표, A8).
  - 대문자 ALWAYS/NEVER 는 경고 신호이니 이유를 설명한다(A7).
  - 예외: A4 의 예시는 "MUST filter"를 제안한다. 문서끼리 어긋난다.
- "하지 마" 지시를 줄인다. Claude 에게 매우 강한 충동을 주기 때문이다(Thariq, E15).
  - obra 는 출력 모양 문제에 금지 목록보다 레시피가 낫다는 것을 쟀다. 금지문은 지시 없는 대조군보다 나빠지는 경향이 있었다(P1 "Match the Form to the Failure").
  - 단서 조항도 붙이지 말라고 한다("No nuance clauses.").

**지나치게 정하기**
- 단계를 너무 구체적으로 적지 않는다. "State the goal and the constraints, not every step."(E1)
- Boris(E5 24:21): 흔한 실패는 과잉 명세다. "Don't micromanage how."(E6)
- 예시를 넣지 않는다. 지웠더니 크게 나아졌다(E2, E15).
- 시스템 프롬프트·스킬·사용자 요청이 서로 부딪히게 하지 않는다(E2, E15).

**옛 모델용 문구**
- "think hard", "keep going, don't be lazy"를 쓰지 않는다(A2 표).
- 검증 지시를 덧붙이지 않는다(A9). Opus 5 는 시키지 않아도 스스로 검증한다. "서브에이전트로 검증하라", "double-check" 같은 지시는 과잉 검증을 낳으니 지운다.
- Cat 은 "always verify, verify, verify" 문구를 바꿨다고 한다(E15).

**리뷰**
- 리뷰 프롬프트에 "심각한 것만", "보수적으로"를 쓰지 않는다. Opus 5 는 글자 그대로 따라 덜 보고한다. 전부 보고하게 하고 따로 거른다(A9).
- 리뷰를 지휘하는 쪽이 리뷰어에게 무엇을 무시할지 말하지 않는다. 그렇게 했다가 결함이 실제로 나갔다(P2 v6.0.0).
- 리뷰어를 쌓지 않는다. 두 번째 리뷰어를 얹는 것은 첫 리뷰어를 다듬는 것보다 대개 나쁘다(E3).
  - 보통의 코딩 일에 리뷰어 다섯은 필요 없다(E8).
  - 에이전트가 고치는 쪽이면 잡음이 더 비싸다(E4).

**구조**
- 더 나은 답을 위해 같은 일을 서브에이전트에 넘기지 않는다(A2 표).
- 역할별 서브에이전트, 조직도 같은 구조를 만들지 않는다(P12, P13, P16, E7, E10).

**검사**
- 변경이 자기를 판정하는 검사를 고칠 수 있게 두지 않는다. 리뷰 규칙(REVIEW.md)은 PR 이 아니라 기준 브랜치에서 읽는다(E3).
- 불안정한 테스트를 건너뛰거나, sleep 을 넣거나, 통과할 때까지 재시도하지 않는다(E3).
- 에이전트의 승인은 사람의 승인이 아니다(E4).

**설치**
- 스킬·MCP 를 "혹시 몰라" 잔뜩 깔지 않는다(P12).
- 출처를 모르는 스킬을 설치하지 않는다(A5 보안 절, E14, P8).

**스킬 쓰는 법**
- 선택지를 늘어놓지 않는다. 기본값 하나와 탈출구를 준다(A4, A13).
- 이번 일의 답을 적지 않고 방법을 적는다(A13). 한 번 푼 이야기는 스킬이 아니다(P1).
- 기본 제공 스킬이나 플러그인 스킬을 직접 고치지 않고, 다른 스킬로 이어 붙인다(E9).
- 에이전트가 스스로에게 상시 규칙을 더하게 하지 않는다(P3 The Therapist Pattern).

### 2.5 역할 대신 도구·단계, 바깥 검증, 적대적 검토

#### 역할 문장은 출처가 갈린다

- 역할로 일을 나눈 서브에이전트가 안 된다는 데는 모인다(P12, P13, P16, E7, E10).
- 하지만 "너는 X 다" 한 줄 자체를 지우라는 1차 자료는 Felix Rieseberg(008 에 있음) 말고 찾지 못했다.
- Anthropic 은 아직 역할을 쓴다.
  - A8 "Give Claude a role"("Even a single sentence makes a difference")
  - A14 "You are an expert debugger…"
  - A12 "You are an elite error handling auditor…"(2025-11 커밋)
  - Boris 의 팁 "review it as a staff engineer"(E6)
  - E8 의 "skeptic persona" 리뷰어
- A2 의 리뷰어 예시만 역할 대신 상황을 준다: "You're reviewing code you didn't write."

#### 전문 지식과 전문가 도구를 준다

- Barry·Mahesh: 에이전트는 똑똑하지만 전문 지식이 없다. 세법을 첫 원리부터 알아내게 하지 말고 스킬로 준다(E14 2:18).
- Huntley(P15 answer)
  - Nix, Bazel 처럼 어렵던 고급 도구도 에이전트는 몰고 간다.
  - 그런 도구가 있다는 것을 알고 "Nix 를 써"라고 말하면 된다.
- A2 는 CLI 를 연결하고 처음 보는 CLI 는 `--help`를 가리키라고 한다.
- A4 는 설치 명령을 적으라고 한다.

#### 확인할 것을 준다: 가장 효과 큰 일

- Boris: 확인할 방법을 주면 최종 결과 품질이 2~3배가 된다. 그걸 단단하게 만드는 데 투자하라고 한다(E6).
- Thariq: "Verification skills have had the most measurable impact on Claude's output quality internally." 엔지니어가 일주일 검증 스킬만 다듬을 가치가 있다(E1).
- Addy: 테스트보다 앱을 끝까지 돌려 보는 게 중요하다. Claude 는 커밋 전에 verify 스킬을 쓴다(E3).
  - Claude Code 에는 `/verify`, `/run`, `/run-skill-generator`가 들어 있다(A1).
  - 프로젝트에 `verify` 스킬이 있으면 커밋 전에 돌리라는 지시가 붙는다(A1).
- Mitchell: 실수마다 AGENTS.md 한 줄이나 도구(스크린샷 스크립트, 걸러 돌리는 테스트)로 영구히 고친다(P10 "Engineer the Harness").
- Simon: 돌려 보기 전에는 동작한다고 가정하지 않는다(P6).

#### 증거를 받는다

- "All tests pass" 한 마디가 아니라 명령과 출력을 받는다(A2, E4).
- 글로만 끝난 턴은 완료 증거가 아니라 보고다(A10).
  - 체크리스트를 둔다.
  - 별도의 작은 모델이 완료 조건을 확인한다.
  - 자동 이어 가기는 두세 번에서 멈춘다.
- obra 의 verification-before-completion 은 에이전트의 성공 보고를 믿는 것을 경고 신호로 둔다.

#### 쓴 사람이 아닌 쪽이 판정

- 자기 결과를 더 좋게 보는 편향(self-preferential bias)이 있으니 따로 띄운 에이전트가 기준표로 적대적 검증을 한다(E8).
- `/code-review`는 대화를 못 본 새 서브에이전트로 리뷰한다. 두 번째 세션이 가장 쉬운 독립 리뷰어다(A2).
- Armin 은 새 리뷰 컨텍스트로 가지를 친다(P8).
- obra 는 리뷰어를 읽기 전용으로 만들고, 구현자의 해명에 회의적이게 했다(P2 v6.0.0).
- Every 는 적대적 리뷰를 다른 모델에 맡기는 쪽을 선호한다(P18).

#### 지적을 따로 검증해 거른다

- A11 공식 code-review 는 리뷰어 4개를 병렬로 돌리고, 버그 지적마다 검증 서브에이전트를 띄워 확인된 것만 남긴다.
- E4: 여러 에이전트가 찾고, 다른 무리가 지적마다 투표해 충분히 동의한 것만 올린다. 스타일만의 지적은 버린다.
- A9 도 전부 보고하게 하고 따로 거르라고 한다.
- 어긋나는 곳: A11 은 리뷰어 단계에서도 "확실하지 않으면 올리지 말라"고 한다.

#### 리뷰는 하나를 다듬고, 회차를 이어 간다

- Addy(E3)
  - 리뷰어를 쌓지 않고 REVIEW.md 로 첫 리뷰어가 볼 것을 다듬는다.
  - 신뢰성 체크리스트 39개 항목마다 diff 에서 읽을 수 있는 발동 조건, 검사, 근거가 된 사고·PR 을 둔다.
  - diff 에 맞는 3~10개만 본다.
  - 회차마다 앞 회차와 과거 실패를 입력으로 준다.
- 반복 상한
  - 검사가 세 번 고쳐도 실패하면 Claude 가 멈추고 사람을 부른다(E3).
  - 세 회차 뒤에는 리뷰어가 접근을 다시 생각하라고 한다(E4).
  - A10 도 자동 이어 가기를 두세 번에서 멈춘다.
- 리뷰어는 무엇이든 찾아낸다. 모두 고치면 쓸데없는 추상화가 생기니 "skip style"을 뺄 수 없다(A2). obra 는 리뷰어를 "합리적인 사람" 기준으로 맞춰 리뷰 루프를 멈췄다(P3 6.4).

#### 모델 등급

- 단순한 서브에이전트 일은 Haiku(A2).
- 완료 조건 확인은 더 작은 모델(A10).
- A11 은 일마다 모델을 고른다.
  - 게이트에 Haiku
  - 요약과 CLAUDE.md 준수에 Sonnet
  - 버그 찾기와 버그 검증에 Opus
