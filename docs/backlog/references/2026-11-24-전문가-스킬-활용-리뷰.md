# 검증된 스킬 저장소와 실무자는 스킬을 어떻게 쓰나, 그리고 j-dev-kit 리뷰 (2026-11-24)

질문: 실제로 많이 쓰이고 검증된 스킬 저장소와 최상위 실무자는 SKILL.md 를 어떻게 쓰고, 고치고, 지우는가. 그 공통분모에 지금 main(`36e3a0e`)의 j-dev-kit 을 대면 무엇이 맞고 무엇이 어긋나는가.

앞 서베이 `docs/backlog/references/2026-11-23-전문가-스킬-활용.md`(아래 "앞 서베이")를 끝까지 읽고 시작했다. 같은 것을 다시 모으지 않았다. 이번에는 GitHub 저장소의 실물(SKILL.md 원문, 테스트, 커밋 기록, 릴리스 노트, 기여 규칙)을 더하고, 앞 서베이의 주장을 실물로 확인했다. 앞 서베이의 A·E·P 번호는 그대로 쓴다. 이번에 더한 출처는 G 번호다.

## 0. 누구를 왜 넣었나 ("검증된"의 기준)

**넣은 기준(셋 다 맞아야 넣었다)**
1. 쓴 사람이나 조직이 실명이고, 그 분야 이력을 1차 자료로 확인할 수 있다.
   - Anthropic 은 Claude Code·Agent Skills 를 만든 곳이다.
   - Trail of Bits(보안 감사), Sentry, Vercel, Every 는 자기 제품·업무에 스킬을 쓰는 회사다.
   - Jesse Vincent(obra), Matt Pocock, Addy Osmani(Claude Code 팀, 앞 서베이 E3·E4 저자), Hamel Husain(eval 교육)은 저장소 커밋과 본인 글이 1차로 남아 있다.
2. 실사용 흔적이 있다. 별·포크 수뿐 아니라 이슈·PR 이 실제로 오가고, 사용자 제보로 고친 기록이 커밋과 릴리스 노트에 남아 있다.
3. 무엇을 왜 바꿨는지 저장소 안에 근거가 있다. 측정, 이슈 번호, 실패 사례 중 하나 이상이다.

**뺀 것**
- 별은 많지만 쓴 사람의 이력을 1차로 확인하지 못한 저장소는 뺐다. 예: morluto/rea ★475,935, affaan-m/ECC ★309,703, multica-ai/andrej-karpathy-skills ★235,342(이름과 달리 Karpathy 본인 저장소가 아니다), DietrichGebert/ponytail ★197,631.
- 모음집(awesome-claude-skills 등)은 큐레이션이지 실천이 아니라서 뺐다.
- openai/skills(★29,047)는 README 첫 줄이 deprecated 라서 구조만 보고 뺐다. hamelsmu/evals-skills 도 deprecated 지만 작성 지침(`meta-skill.md`)은 1차 자료라 썼다.
- 2차 요약, 블로그 모음, 검색 결과의 요약은 근거로 쓰지 않았다.

**읽은 방법**
- 저장소는 스크래치패드에 `git clone --filter=blob:none`으로 받아 원문과 `git log`, `git show`를 직접 봤다. 요약 도구나 하위 에이전트에 맡기지 않았다.
- 공식 문서는 내장 브라우저로 받아 해당 절을 원문 그대로 찾아 읽었다.
- 별·포크는 GitHub API 값이고, 확인 시각은 2026-11-24 06:01 UTC 다.
- 인용은 15단어 이하로 했다.

### 2.1 Anthropic 은 자기 스킬을 이렇게 줄였다 (G1, G2)

- **문서 스킬을 85% 줄였다.** `docx` SKILL.md 는 590줄(2026-02-24)에서 91줄(2026-07-16, `fa0fa64`)이 됐다. `xlsx`는 291줄에서 99줄이 됐다.

### 2.3 Matt Pocock: 고칠 때의 문턱 (G4)

- **바꾸려면 실제 실패가 있어야 한다(SCOPE.md).** 이슈는 실제 세션에서 무엇을 돌렸고, 스킬이 무엇을 했고, 무엇을 기대했는지를 적어야 열려 있다. "it would be better if…"는 문턱을 못 넘는다.
- **기존 스킬로 조합되면 새 스킬을 만들지 않는다**(`.out-of-scope/new-skills.md`).
- **질문 개수 상한을 넣지 않는다(`.out-of-scope/question-limits.md`).** 계획에 따라 질문은 셋일 수도 쉰일 수도 있다. 쓸데없는 질문은 개수 문제가 아니라 프롬프트 문제라고 한다.
- **서브에이전트 재귀 방지는 스킬에 쓰지 않는다**(`.out-of-scope/subagent-recursion.md`). 하네스가 할 일이라고 본다. obra v6.3.0 과 반대다.
- **`writing-for-agents`(작성 지침)**
  - description 은 "context pointer"다. 핵심 단어를 앞에 둔다. 갈래마다 트리거 하나를 두고, 같은 갈래의 동의어는 합친다.
  - 단계마다 완료 조건이 있어야 한다. 흐린 완료 조건은 서둘러 끝내게 한다.
  - 금지문은 금지한 행동을 오히려 떠올리게 한다. 원하는 행동을 긍정형으로 쓴다.
  - 환경(`package.json`, 설정, `--help`)을 다시 적은 문서는 "cache"다. 에이전트가 찾아볼 수 없는 것만 적는다.
  - 기본으로 이미 하는 지시("no-op")는 문장째 지운다. no-op 인지는 토론이 아니라 돌려 보고 정한다.
- **실제로 바꾼 것(CHANGELOG)**
  - `resolving-merge-conflicts` 스킬을 지웠다(1.3.0). 이제 필요 없고 대체하는 것도 없다.
  - 다른 스킬을 부를 때 "Call the Skill tool with …"로 도구 이름을 적게 했다(#878). 이름만 쓰면 잘 불리지 않았다고 한다.
  - `diagnosing-bugs`는 빨강을 믿기 전에 강제한 변형을 원본과 diff 로 비교한다(#1209). 아무것도 바꾸지 않은 편집이 실패하는 테스트로 통과하지 못하게 하려는 것이다.
  - 서브에이전트는 새 컨텍스트로 띄우라고 했다(#1341).
  - `retro`는 기계적 위반을 결정적 검사로, 판단이 필요한 것만 CODING_STANDARDS.md 로 둔다(1.3.0).
  - 콜론 뒤 공백이 있는 따옴표 없는 description 이 YAML 을 깨서 여섯 스킬이 목록에서 빠졌다(#911).

### 2.4 Every: 스킬 설계 교훈 48개를 저장소에 남긴다 (G6)

`docs/solutions/skill-design/`에서 읽은 9개(파일 이름은 각 절에):
- **`confirmations-filter-by-salience-not-length-caps.md`.** 확인 요약이 길어지자 단어·불릿 상한을 넣었지만 Claude 를 다스리지 못했다. 상한이 있든 없든 약 370단어였다. 넣을지를 정하는 내용 규칙으로 바꿔서 고쳤다. 같은 글에 "Agents copy examples more closely than they follow prose."가 있다. 그래서 예시는 자기 규칙을 지켜야 한다.

  - 필요한 지점에 이름을 적은 필수 읽기는 잘 따른다. 멀리서 한 번 말한 참조는 안 따른다.

### 2.5 Trail of Bits: 기여 규칙이 검사기로 강제된다 (G7)

AGENTS.md 의 "Quality Standards", "Before committing", "Scripts a plugin ships", "Working effectively" 절:
- 스킬은 Claude 가 이미 가진 지식을 되풀이하지 않는다. 명세를 붙여 넣지 말고 언제 어떻게 찾아볼지 가르친다(DWARF 예).
- 지시의 엄격함은 일의 위험에 맞춘다. 보안 감사는 엄격하게, 탐색·문서는 유연하게.

  - plugin.json 과 marketplace.json 의 이름·설명·버전이 맞는지.
  - 플러그인을 바꾸면 버전을 올렸는지.
  - `: `나 ` #`가 든 따옴표 없는 YAML 값이 없는지. 그러면 메타데이터 전체가 빠진다.
  - 에이전트는 `tools:`, 스킬은 `allowed-tools:`인지. 잘못 쓰면 로더가 조용히 무시한다.

- 자기 일을 검증하려고 서브에이전트를 띄우지 않는다. 한 일을 여러 에이전트로 쪼개지 않는다.
