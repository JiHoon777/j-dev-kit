## 1. pstack 은 어떻게 짜여 있나

### 층 구조

| 층 | 무엇 | 하는 일 |
| --- | --- | --- |
| 진입 | `poteto-mode` | 사용자가 직접 치는 스킬이다(`disable-model-invocation: true`). 필수 규칙, 원칙 색인, 자율성 규칙, 하위 에이전트 모델 기본값, 답 쓰는 법, 플레이북 목록이 들어 있다 |
| 하위 에이전트 규칙 | `worker.md` | 띄우는 모든 에이전트가 맨 먼저 읽는다. 내용: 지시문의 기준이 전부다, 묻는 도구를 쓰지 않는다, 되돌릴 수 있는 일은 정하고 이유를 말한다, 멈추는 건 배포·삭제·공유 브랜치 강제 푸시·바깥 메시지뿐이다, PR 형식 |
| 절차 | 플레이북 22개 | 작업 종류별 단계 목록이다. 할 일 목록에 그대로 옮겨 따른다. 모든 코드 플레이북은 Opening a PR 로 끝난다 |
| 판단 기준 | 원칙 24개 | 한 줄 규칙 하나씩이다. poteto-mode 가 색인을 들고 있고, 적용할 때 원문을 읽는다. 답에 "어느 원칙이 어느 결정을 바꿨나"를 적어야 한다 |
| 도구 스킬 | 약 30개 | 이해(how, why, teach, recall), 설계(architect, arena, swarm, interrogate), 만들기·정리(tdd, no-comments, unslop), 검증(검증 스킬 생성·유지, 형식 검증, benchmark-checklist, blast-radius), 기록·보고(show-me-your-work, ketchup), 자기 개선(reflect, correct, automate-me), 프롬프트 다듬기(sharpen, reframe, in-your-own-words, bro) |
| 바깥 의존 | Cursor 생태계 | `cursor-team-kit`(control-ui·control-cli·deslop), Cursor Projects·클라우드 에이전트, Automations, `/loop`, 다른 회사 모델 패널(Gemini) |

### 일의 흐름

1. 사용자가 `/poteto-mode <목표, 끝 조건, 보고 싶은 증거, 아는 것, 제약>`을 친다(가이드 02 "What goes in a prompt").
2. 첫 답에서 목표와 가장 작은 변경을 되짚고 바로 진행한다.
3. 플레이북 하나를 골라 그 단계를 할 일 목록에 옮긴다. 맞는 게 없으면 figure-it-out 이 그 일에 맞는 절차를 짠다.
4. 설계가 필요하면 architect 가 두 모양을 그려 고른다. 갈리는 선택은 프로토타입으로 정한다.
5. 구현은 하위 에이전트에 맡긴다. 메인은 설계·리뷰·검증만 한다.
6. 실제 화면에서 검증한다. "확인 못 함"은 통과가 아니다.
7. 작은 커밋으로 정리하고 PR 을 연다. 머지는 코드를 쓰지 않은 검증자의 판정이 있어야 한다(Shipping).

### pstack 에 없는 것

- 계획 스킬이 없다. 가이드 04 에 "plan through code"라고 쓰여 있다. 글로 된 계획은 여러 PR 에 걸친 일에만, 설계가 굳은 뒤에 쓴다.
- 백로그가 없다. 할 일은 프롬프트에 쓰거나 외부 트래커에 둔다.
- 무엇을 할지 조사해 고르는 스킬도 없다.

## 2. pstack 은 언제 묻나 (전수)

pstack 전체(`docs/harness` 제외)에서 ask, approval, confirm, pause, go 같은 표현을 grep 으로 찾아 하나씩 읽었다.

### 묻는 때

| 언제 | 어디 |
| --- | --- |
| 되돌릴 수 없는 일: 공유 브랜치 강제 푸시, 배포, 데이터 삭제, 고객·바깥 메시지 | `poteto-mode` Autonomy, `worker.md`, 원칙 never-block-on-the-human |
| 실험으로 정할 수 없는 제품·취향 결정 | multi-phase-plan 2, autonomous-run 4, sharpen |
| 계획을 실행하기 전 "가" | multi-phase-plan 5, autopilot-full 1("계획을 말하라는 요청은 가가 아니다") |
| 의도가 불분명할 때 | interrogate Frame |
| 직접 끝까지 해 봐도 재현이 안 될 때. 구체적인 이유를 대고 | bug-fix 1 |
| 기준선이 틀려 보일 때(고치지 않고 묻는다) | visual-parity 2 |
| 커밋 안 된 작업이 지워질 때 | worktree-cleanup 4 |
| 스킬을 고치기 전 | reflect, no-comments 5(제약을 코드로 옮길지) |
| 개인 설정을 정할 때 | automate-me 2, setup-pstack |
| 몇 시간짜리 실행을 시작하기 전 한 번 | figure-it-out Phase A |

### 묻지 않으려고 쓰는 장치

이 부분이 핵심이다. pstack 은 그냥 덜 묻는 게 아니라, 질문을 다른 것으로 바꾼다.

1. **실험으로 바꾼다.** 돌려 보면 답이 나오는 갈림길은 프로토타입으로 정한다(poteto-mode 필수 규칙, 가이드 04).
2. **기록과 사후 검토로 바꾼다.** 되돌릴 수 있는 결정은 정하고 진행한다. 정한 것과 이유를 남긴다(show-me-your-work 의 결정 로그). 사람은 나중에 검토한다. 로그 끝에는 다른 모델이 짚은 "Attention" 절이 붙는다.
3. **몰아서 한 번에 묻는다.** ketchup 의 형식은 이렇다.
   - 첫 줄에 사람을 기다리는 게 무엇인지 쓴다.
   - 결정마다 링크, 사용자에게 바뀌는 것, 추천, 근거, 위험을 붙인다.
   - 답만 읽고 결정할 수 있게 쓴다.
   - 내가 할 수 있는 일은 결정거리로 올리지 않는다.
4. **사용자가 미리 답한다.** 프롬프트의 "커밋 전에 묻지 마", "나 잔다" 같은 말로 미리 허락을 받는다(가이드 07).
5. **사람에게 확인을 떠넘기지 않는다.** "Never hand the human a check you could run"(poteto-mode 답 쓰기).
6. **솔직하게 아니라고 한다.** 제안받은 범위가 값을 못 하면 아니라고 말한다("No is an acceptable answer").

## 4. 계획 승인은 사용자가 정할 일이다

계획 승인은 지금 항목마다 늘 받는다. 하위 세션도 플랜 모드로 받는다. 이건 012 에서 사용자가 직접 정한 것이다(`docs/done/012-…md:72-77`, "C. 하위 세션도 공식 플랜 모드로 계획 승인", 2026-11-24 추가).

pstack 처럼 없애면 질문이 가장 크게 줄어든다. 하지만 이전 결정을 뒤집는 것이라 사용자가 고른다. 선택지는 셋이다.

- **(가) 지금처럼 늘 받는다.** 질문은 덜 줄어든다.
- **(나) 갈리는 선택이 있거나 큰 항목일 때만 받는다.** 그 밖에는 계획과 가정을 항목 파일에 적고 바로 구현한다. start 끝 보고에서 함께 보여 준다. 갈리는 선택은 구조, 라이브러리, 데이터 모델 중 돌려 봐도 정해지지 않는 것이다. 큰 항목은 지금 start 3 의 "큰 항목" 기준(여러 모듈, 새 구조)과 같다.
- **(다) 받지 않는다.** pstack 과 같다. 검증이 튼튼해야 성립한다.

추천은 (나)다. 끝난 항목 기록의 "사용자가 바로잡은 것 (start)"(008, 011, 013)을 보면 바로잡은 것은 모두 갈리는 선택이었다. 리뷰 모델, 테스트를 돌릴 범위(계획 질문에서), eval 방식, 판정 규칙이다. 다만 이 중 어느 것이 계획 승인 화면에서 나왔는지는 기록으로 가리지 못했다.

**F 의 모양 (가져올 부분만)**

- 사용자가 직접 치는 스킬로 둔다(poteto-mode 처럼 `disable-model-invocation: true`). `/task`는 지금처럼 Claude 가 알아서 부를 수 있다.
- 첫 답에서 목표와 가장 작은 변경을 되짚고 바로 진행한다(poteto-mode 필수 규칙 첫 줄).
- 요청 종류별로 짧게 나눈다.
  - 항목 일 → `/task`
  - 버그 → 직접 재현부터, 싼 테스트 길이 있으면 실패하는 테스트 먼저(bug-fix, tdd)

  - 작은 수정 → 바로 고치고 검증
- 묻는 기준 A 를 따른다.
- "됐다" 전에 검증을 새로 돌리고 증거를 보인다(prove-it-works). 사람에게 확인을 떠넘기지 않는다.
- 아니라고 말해도 된다. 범위를 넓히자는 제안에 값을 못 하면 그렇게 말한다.

## 6. 결론

- pstack 이 질문을 줄이는 방식은 "덜 묻기"가 아니다. 질문을 세 가지로 바꾼다: 실험, 기록 후 사후 검토, 몰아서 한 번에 추천과 함께 묻기. 우리도 이 셋을 가져오면 된다(A~E).
- 가장 큰 결정 하나(계획 승인)는 012 에서 사용자가 정한 것이라 사용자가 다시 고른다(4절).
- 모드 스킬(F)은 가져올 가치가 있다. 다만 superpowers 와의 경계, Claude Code 에서 모드를 켜 두는 방법을 먼저 조사한다.
- 항목으로 나누면 이렇다.
  - **016 묻는 기준과 몰아 묻기:** A~E, 그리고 3절 표의 "묻지 않는다"·"줄인다" 줄. 계획 승인 방식은 이 항목 계획에서 정한다.
  - **017 모드 스킬:** F. `create --survey`로 위 조사를 먼저 한다. 016 이 정한 기준을 쓰므로 016 에 의존한다.
