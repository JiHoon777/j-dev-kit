# `/until-done`은 왜 안 쓰였나

조사일: 2026-11-26 · 016 인수인계 "더 조사할 것" 2번(`docs/backlog/references/2026-11-26-016-인수인계.md:73-75`)

질문: `/until-done`이 안 쓰인 이유가 (a) 따로 켜야 써서인가, (b) 규칙 자체가 맞지 않아서인가, (c) 다른 이유인가.

## 결론

**(a)와 (c)가 섞여 있다. (b)는 근거가 없고, 그렇다고 반증된 것도 아니다.** 확신은 중간 정도다.

- `/until-done`은 실제 작업에서 한 번도 불리지 않았다(이 맥의 기록 기준). 그래서 규칙이 맞았는지 틀렸는지 보여 줄 사용 기록이 없다. "쓰다가 불편해서 버렸다"가 아니라 "켜 보지도 않은 채 지워졌다"에 가깝다.
- 켜는 비용이 컸다. 사용자가 직접 슬래시로 쳐야 했고, 끝나는 조건을 인자로 줘야 했고, `/goal` 한 줄을 따로 붙여 넣어야 했다. 같은 006 에서 `/task`도 "쳐야만 돈다"를 문제로 보고 Claude 가 알아서 부르게 바꿨다. 이것이 (a)를 받친다.
- 다른 이유(c)도 있다. 있던 기간이 약 43시간이었다. 006 은 여섯 가지를 한꺼번에 지운 정리였다. 그 사이 사용자는 다른 방식으로 일했다. 말로 부모 세션에 지휘를 맡기고, 머지·푸시·시안 고르기만 짧게 답했다.
- 016 에 주는 뜻: 기본값을 바꾸는 방향은 이 선례와 부딪히지 않는다. 다만 `/until-done`의 규칙은 실제로 검증된 적이 없으니 선례로 016 을 정당화할 수도 없다. 016 AC #11 의 실제 사례 측정이 유일한 검증이다.

## 추론

- **(a)를 받치는 것.** 켜는 데 세 가지가 필요했다. 직접 슬래시 입력(`:5`), 끝나는 조건 인자(`:19`), `/goal` 한 줄(`:21-27`). 사용자는 슬래시보다 말로 일했다(5절). 006 이 `/task`에서 "쳐야만 돈다"를 문제로 짚은 것(`006:18`)과 같은 문제를 `/until-done`도 더 무겁게 갖고 있었다.
- **(c)를 받치는 것.** 있던 기간이 약 43시간으로 짧았다. 그 사이 사용자의 일은 말로 하는 지휘였고, 그 방식은 008 이후 `/task`의 하위 세션 지휘로 흡수됐다. 출발점부터 "모드 없이도 자율적으로 된다"는 관찰이었다(4절 L4). 그러니 모드가 따로 할 일이 적었을 수 있다. 006 은 일괄 정리라서 개별 평가 없이 지워졌다.
- **(b)는 근거가 없다.** 실제로 돌지 않았으니 `Ruling`을 사용자가 뒤집은 기록도 없다. 사용자는 묻지 않는 규칙을 명시적으로 지지했다(4절 L800). 다만 반증된 것도 아니다. 실제 저장소에서 확인한 적이 없다(`004:116`).
- **(b)가 숨어 있을 수 있는 곳.** 사용자가 직접 고른 것은 시안(5절)과 머지·푸시였다. `/until-done`은 이 둘 중 시안 고르기와 머지를 스스로 정하게 했다. 실제로 썼다면 이 지점에서 맞지 않았을 수 있다. 016 은 둘 다 묻는 쪽에 남겨 이 위험을 피한다.
- **확인하지 못한 것.** 006 을 한 다른 컴퓨터(Windows)의 세션 기록이다. 016 인수인계도 그 컴퓨터에 기록이 있다고 적었다(`016-인수인계:71`). 거기서 `/until-done`을 썼다면 결론이 바뀔 수 있다. 이 맥의 기록은 2026-11-17 부터다.

## 016 과 `/until-done`의 차이

| 질문 지점 | `/until-done` | 016 |
| --- | --- | --- |
| 켜는 법 | 사용자가 직접 침, 끝나는 조건 인자, `/goal` 따로 입력 | 기본값. 켜지 않는다 |
| 항목(AC) 승인 | 묻지 않음(시험에서 `Ruling: create 승인`, `004:92`) | 묻는다(`016:29`, AC #4) |
| 계획 승인·플랜 모드 | 묻지 않음 (`:40`) | 묻지 않음(AC #2) |
| 리뷰 지적 처리 | 묻지 않고 정함 (`:40`) | 타당한 🔴·🟡 는 고치고 알림. AC·정한 것과 부딪히는 것과 "나중" 후보만 묻는다(AC #6) |
| 머지 | 묻지 않고 로컬 머지 (`:40`, `004:92`) | 묻는다. 정한 것, 질문, 머지 방식을 한 메시지로(AC #1, #6) |
| 시안 개수·방향 | 정함 (`:40`) | 기본 3개, 방향 표는 보여 주기만(AC #10) |
| 시안 고르기(취향) | 정함 (`:40`) | 묻는다: 코드로 정할 수 없는 취향(AC #1, #10) |
| 무엇을 할지 고르기 | 다루지 않음 | 묻는다(AC #1) |
| 푸시·배포·삭제·밖 변경 | 묻는다. 목표에 있으면 안 묻고, 머지된 브랜치 삭제도 안 묻는다 (`:60-67`) | 묻는다(AC #1) |
| superpowers 스킬의 숨은 질문 | 다루지 않음 | 부르는 쪽이 미리 답을 넘긴다(AC #9) |
| 끝 판정 | 끝나는 조건을 명령이나 새 에이전트로, `/goal`로 이어 감 (`:51-56`) | 다루지 않음. 기존 `/task end` 리뷰·검증 그대로 |
| 정한 것 기록 | `Ruling:` 줄을 항목 Implementation Notes 나 끝 보고에 (`:43-46`) | 항목 파일에 적고, start 끝 보고와 end 머지 전 질문에서 보인다(`016:23`) |

요약하면 016 은 `/until-done`보다 덜 묻지 않는다. AC 승인, 머지, 취향, 고르기를 사람에게 남긴다. 대신 켜는 비용을 없애 기본값으로 만든다. `/until-done`의 끝 조건 확인과 `/goal` 이어 가기는 016 에 없다.

## 016 에 주는 뜻

1. 기본값으로 바꾸는 방향은 이 선례가 "켜지 않아서 안 쓰였다"는 쪽과 맞는다. 모드를 새로 만들지 않는다는 016 의 범위(`016:41`)도 맞다.
2. 선례에는 실제 사용 기록이 없다. 그래서 "묻지 않는 규칙이 이 사용자에게 맞다"는 근거로 쓸 수 없다. AC #11(실제 사례로 멈춘 횟수 세기)이 유일한 검증이다.
3. AC #5(simplify 질문 두 개 없애기)는 사용자가 이틀 전 직접 넣은 질문을 없앤다(7절). start 전에 사용자에게 이것만 따로 확인할 만하다.
4. 사용자가 실제로 직접 고른 것은 시안과 머지·푸시였다(5절). 016 은 이 둘을 묻는 쪽에 둔다. 머지와 푸시를 한 번에 묻는 것은 사용자의 요청(5절 L9812)과 맞는다.
5. 다른 컴퓨터의 기록을 볼 수 있으면 1번 조사(멈춘 횟수)와 함께 `/until-done` 호출도 grep 해 본다.
