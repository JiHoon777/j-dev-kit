## 1. pstack 은 언제 묻나

**멈추고 묻는 곳 [직접]**
- 되돌릴 수 없는 일: 공유 브랜치 force-push, 배포, 데이터 삭제, 외부 메시지 (`poteto-mode/SKILL.md:78`, `worker.md:117`, `principle-never-block-on-the-human/SKILL.md:13`)
- 어떤 실행으로도 가릴 수 없는 제품·선호 결정 (`playbooks/multi-phase-plan.md:6`, `autonomous-run.md:9`, `sharpen/SKILL.md:16`)
- 진짜 막다른 길 (`autonomous-run.md:9,11`)
- 개별 플레이북의 정지점:
  - 재현은 도구로 닿지 않을 때만 사용자에게 부탁한다 (`bug-fix.md:7`)
  - 기준 스크린샷이 이상해 보이면 묻는다 (`visual-parity.md:6`)
  - 커밋 안 된 worktree 를 지우기 전 (`worktree-cleanup.md:6`)
  - 다단계 계획은 "go"를 받은 뒤에야 실행한다 (`multi-phase-plan.md:9`), 상호작용을 바꾸는 PR 은 머지 전 리뷰 (`:8`)
  - babysit: 소유자 승인은 기다린다 (`babysit.md:10`). autopilot-stack 은 검증된 PR 을 넘기고 멈춘다 (`autopilot-stack.md:5`)
  - 여러 시간짜리 작업은 시작 전 체크포인트 한 번 (`figure-it-out/SKILL.md:23`)
  - 의도가 불분명하면 묻는다 (`interrogate:13`), 스킬 수정 전 승인 (`reflect:15`), 설정 질문 (`setup-pstack:32,40`), 리뷰 코멘트 중 새롭거나 보안·데이터 관련은 묻는다 (`references/bugbot-triage.md:11,75`)
- 묻지 않는 경우: Claude Code 에 없는 기능은 한 줄 적고 건너뛴다 (`docs/harness/claude-code.md:61`). "going to bed" 같은 말은 질문을 끈다 (`SKILL.md:80`, `docs/guide/07-overnight.md:31,34`).

**질문 대신 쓰는 것 [직접]**
- 일단 하고, 무엇을 왜 골랐는지 말한다 (`worker.md:117`, `principle-never-block:11`)
- 돌려서 가릴 수 있는 갈림길은 시제품으로 가린다 (`SKILL.md:21`, `prototype.md`)
- 첫 메시지에 목표와 가장 작은 변경을 다시 말해, 잘못 읽은 것을 초기에 드러낸다 (`SKILL.md:19`, `guide/02-poteto-mode.md:67`)
- 판정 가능한 끝 조건을 두고, 만든 쪽이 아닌 검증자가 판정한다 (`autonomous-run.md:5`, `shipping.md:5`)
- 결정 기록 TSV 를 남기고, 다른 회사 모델이 그 기록을 다시 본다 (`show-me-your-work:9-74`)
- 사람이 정할 일을 모아 각각 추천과 함께 한 번에 보인다 (`ketchup:17-31`), 열린 결정을 보고에 적는다 (`feature.md:21`)
- 계획 스킬은 일부러 두지 않았다 (`guide/04-design.md:97`)

## 3. 계획 승인을 없애려면 필요한 것

**대신할 장치 [추론, 근거 병기]**
1. **질문 한 턴만 남긴다.** 질문이 있으면 아무것도 고치지 않고 묻고 멈춘다. 없으면 멈추지 않는다. 플랜 모드가 막아 주던 "읽기 전용"을 이 규칙이 대신한다 (`start.md:45,58`).
2. **계획은 보여 주되 기다리지 않는다.** 저장소 안에 선례가 있다: `create.md:162`가 "보여 주고 승인을 기다리지 않고 … 끼어들어 고치면 따른다". 하위 세션은 사용자가 직접 대화하는 세션이라 끼어들 수 있다.
3. **스스로 정한 것을 적고 끝에 모아 보인다.** Implementation Notes 에 "정한 것"을 적고, end 보고와 머지 질문에 함께 싣는다. 004 의 `Ruling:`(`004:7,104`), pstack `worker.md:117`, `feature.md:21` 과 같은 방식이다.
4. **AC 가 유일한 승인 계약이 된다.** create 승인은 유지한다. 계획 단계의 범위 변경은 "범위가 커지면 멈춤"(`start.md:78`)으로 잡는다.
5. **정지 목록을 명시한다.** 지금 계획 승인이 함께 승인하던 것들이다: 전역 설치·설정 변경, 새 의존성(사용자 영역 밖), 마이그레이션, 데이터 삭제, 푸시. (`start.md:43`, pstack `SKILL.md:76-78`)
6. **딸린 문구를 고친다.**
   - `docs/review-principles.md:8`: "승인된 계획이 정한 것은 버그로 보지 않는다"가 근거를 잃는다. "AC 와 사용자가 답한 것"으로 좁히고, 계획의 가정은 리뷰 대상으로 둔다.
   - "승인된 계획" 문구가 남은 곳: `create.md:115`, `start.md:3,58`, `start.md:68`(4단계 2), 백로그 014·015 템플릿 줄.
   - 부모 세션의 전달 규칙: `SKILL.md:44,47`, 메모리 "하위 세션은 내가 지휘".

**위험**
- 잘못 읽은 항목을 구현하는 비용. 브랜치 안이라 되돌릴 수 있지만 eval 이 큰 항목(008·012)에서는 비싸다. 첫 메시지에서 목표를 다시 말하면 줄어든다 (`SKILL.md:19`).
- 012 에서 사용자가 직접 "하위 세션도 플랜 모드"를 정했다 (`012:270`). 이번 결정이 그것을 바꾼다는 것을 항목에 적어야 한다.
- 판정·리뷰 에이전트가 사용자가 확인하지 않은 계획 가정을 사용자 결정으로 오인할 수 있다 (6번 참조).

## 4. pstack 에서 가져올 것

**가져올 것**
- 되돌릴 수 있으면 묻지 않고, 정지 목록만 둔다 (`SKILL.md:74-80`, `principle-never-block:9-15`). 004 AC #4 가 이미 같은 규칙이었다 (`004:34`).
- 돌려 보면 답이 나오는 것은 묻지 않는다 (`multi-phase-plan.md:6`, `sharpen:16`).
- 고른 것과 이유를 말하고, 열린 결정은 끝에 모은다 (`worker.md:117`, `ketchup:17-31`). end 의 리뷰 결과·스스로 정한 것·머지 질문을 한 메시지로, 추천과 함께.
- 첫 메시지에서 목표를 다시 말한다 (`SKILL.md:19`).
- 돌릴 수 있는 확인을 사람에게 넘기지 않는다 (`SKILL.md:104`). 대상: `server-end-check:36`.
- 리뷰 지적은 기본값으로 처리하고 알린다. 근거: 위 기록 (🔴🟡 지금, ⚪ 그대로, 🔁 막기는 묻지 않음). 바꾸고 싶은 지적만 사용자가 말한다.

**보류**
- show-me-your-work 의 TSV 와 다른 회사 모델 검토 (`show-me-your-work:15-74`). 기존 Implementation Notes 로 충분하다. Gemini 가 없어 Claude Code 에서는 다른 회사 모델 검토가 안 된다 (`harness/claude-code.md:36`) **[CC 불가]**.
- 시제품으로 결정하기 (`prototype.md`). 원칙 한 줄로는 충분하다. UI 는 이미 캔버스 시안이 한다.
- 질문을 끄는 말 ("going to bed", `SKILL.md:80`). 004 에서 만들었다가 006 에서 쓰지 않아 지웠다 (`006:14`). 써 본 근거가 없다.

**가져오지 않을 것**
- 원칙 24개 읽기·인용 의무, 플레이북 22개 (`SKILL.md:15,33,110`). 단순한 스킬을 원한다는 메모리와 006 의 축소 방향에 어긋난다.
- 모델 슬러그와 setup-pstack (`SKILL.md:88-96`). Cursor 전용이다 **[CC 제한]** (`harness:35`).
- arena·interrogate 다중 모델 패널. Gemini 를 쓸 수 없고 **[CC 불가]**, 008 에서 리뷰어를 더해도 탐지는 같고 비용만 1.7배였다 (`008:154`).
- Shipping·babysit·autopilot·Automations·Bugbot. Cursor 전용이거나 PR 흐름이다 **[CC 불가]** (`harness:61-68`). j-dev-kit 은 로컬 머지를 쓴다.
- 문체 규칙 (unslop 등). 015 writing 항목의 범위다.

## 6. 가장 중요한 세 가지

1. **질문 규칙을 모드가 아니라 기본 절차에 넣는다.**
   - `/until-done` 이 만들어졌다가 지워졌다 (004 → 006).
   - 하위 세션에 규칙이 닿는 경로는 task 스킬뿐이다 (pstack 은 worker.md 우회가 필요했다).
   - 진입 스킬은 길만 고르게 한다.
2. **계획 승인을 빼면 사람 게이트는 세 곳으로 옮는다**: create 의 AC 승인, start 의 질문 한 턴, end 의 "스스로 정한 것 + 머지" 한 메시지.
   - 계획 승인이 몰래 맡던 것(도구 설치, 의존성, 리뷰 원칙 8 의 "승인된 계획")은 정지 목록과 문구 수정으로 메워야 한다.
3. **기록상 질문의 대부분은 답이 늘 같았다.**
   - 계획 승인: 기록이 있는 7건 중 5건이 수정 없이 승인
   - simplify: 거절 0번
   - 🟡: 대부분 지금
   - 🔁 막기: 4번 모두 거절
   - 그래서 기본값으로 하고 알린다. 남기는 정지점은 데이터 손실, 선호 결정, 막다른 길, 머지뿐이다.
