# arch design: 구조와 스택 설계

새 프로젝트, 새 기능의 구조, 구조 변경, 새 부품의 스택을 설계한다. **코드는 고치지 않는다.** 결과는 개요 문서, ADR, 리서치 파일이고, 쓰기 전에 승인을 받는다.

설계할 것: `design` 뒤의 인자(`--research` 뺌). 비어 있으면 무엇을 설계할지 묻는다.

## 1. 읽기

- 개요 문서와 ADR(위치는 `references/docs.md`). `accepted` ADR 은 제약이다.
- CLAUDE.md, 매니페스트(`package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml`, `*.csproj`, `pubspec.yaml` 등), 최상위 폴더 구조.
- 리서치 폴더의 파일 이름과 날짜.
- 새 프로젝트(코드가 거의 없음)면 여기까지.
- 기존 프로젝트면 설계할 것과 이어지는 코드를 읽는다.
  - 작은 범위(모듈 한두 개): 직접 읽는다.
  - 큰 범위(여러 모듈, 새 구조): `Explore` 에이전트를 최대 2개, 서로 다른 영역으로 한 메시지에서 띄운다. 비슷한 기존 기능과 이어지는 코드를 따라가 꼭 읽을 파일을 돌려받고, 그 파일을 직접 읽는다.

## 2. 앱 종류와 품질 목표

1. **앱 종류:** `references/stack.md` 2절의 종류 중 무엇인가(여럿일 수 있다).
2. **품질 목표 3~5개**를 순위대로 정한다. 각각 확인할 수 있는 시나리오로 쓴다(예: "가입 요청의 95% 가 300ms 안에", "새 결제 수단을 모듈 하나만 고쳐 추가").
3. **질문:** 코드·문서로 답할 수 없고 설계를 바꾸는 것만, 한꺼번에 최대 3개. 예: 예상 규모, 숙련된 언어, 배포 환경, 꼭 써야 하는 것. 나머지는 합리적으로 정하고 가정으로 적는다. 답을 받기 전에는 설계를 확정하지 않는다.

## 3. 정할 것 목록

이번 설계에서 정할 결정을 나열하고, 결정마다 나눈다.

- **한 방향 문**(되돌리기 어렵다): 언어·런타임, 주 데이터베이스, 렌더링 방식, 모듈 경계와 의존 방향, 공개 API·데이터 형식, 배포 형태(서버, 서버리스, 정적, 앱 스토어)
- **양방향 문**(되돌리기 쉽다): 대부분의 라이브러리, 내부 폴더 이름, 바꿔 끼울 수 있는 도구

기존 프로젝트에서 이미 정해진 것(기존 스택, `accepted` ADR)은 목록에 넣지 않는다. 바꿀 이유가 있으면 "다시 볼 것"으로 따로 적는다.

## 4. 서베이

- **스택 결정이 있으면 항상:** `references/stack.md` 5절과 `references/research.md`대로 `architecture-researcher`를 띄운다. 서로 다른 결정은 에이전트를 나눠 한 메시지에서 동시에(최대 3개).
- **구조 지침은 `--research`일 때만:** 이 앱 종류와 스택의 최신 구조 지침(공식 문서의 권장 구조, 프레임워크의 프로젝트 구조 가이드)을 같은 에이전트로 조사한다. `--research`가 없으면 리서치 폴더의 기존 파일을 쓰고 날짜를 밝힌다. 기존 파일도 없으면 `references/criteria.md`만으로 설계하고, 보고 끝에 "`--research`로 최신 지침을 확인할 수 있음"이라고 적는다.
- 서베이 결과를 받으면 [공식]·[표준] 출처가 없는 숫자는 쓰지 않는다.

## 5. 설계

`references/criteria.md`의 기준과 `references/stack.md`의 요인표로 정한다.

- **한 방향 문:** 대안 2~3개를 비교하고 하나를 추천한다. 비교표(`references/stack.md` 6절 형식)와 추천 이유 두세 문장.
- **양방향 문:** 한 줄로 정한다. 대안을 늘어놓지 않는다.
- **구조:**
  - 모듈 지도(경로 → 책임 → 공개 인터페이스 → 무엇 때문에 바뀌나), 의존 방향.
  - 흔한 변경 2~4개에 대해 "새 X 추가하는 법": 어느 모듈, 어느 파일.
  - 각 층·모듈·추상화가 어느 품질 목표에 기여하는지 하나씩 대응시킨다. 대응하는 목표가 없으면 뺀다.
  - 혁신 토큰 수(`references/stack.md` 4절).
- **강제:** 중요한 규칙마다 `references/enforce.md`대로 검사를 제안한다.
- 프레임워크가 정한 구조가 있으면 그것을 따르고, 그 위에 필요한 것만 더한다.

## 6. 보여 주고 승인받기

한 번에 보여 준다.

```markdown
### 앱과 품질 목표
- 종류: …
- 품질 목표: 1. … 2. … 3. …
- 가정: …

### 스택
<결정마다 비교표와 추천 (한 방향 문)>
- <양방향 문 한 줄씩>
혁신 토큰: N개 (…)

### 구조
<모듈 지도 표, 의존 방향>
<새 X 추가하는 법>

### 강제할 규칙
- …

### 쓸 문서
- 개요: <경로> (새로 / 고침)
- ADR: NNNN-…, NNNN-…
- 리서치: <파일 이름>

### 다시 볼 것 (있으면)
- …
```

묻는 것: "이대로 문서를 쓸까요? 바꿀 결정이 있으면 말씀해 주세요." 답을 받기 전에는 아무 파일도 쓰지 않는다. 사용자가 결정을 바꾸면 그 부분만 다시 비교하고 다시 보여 준다.

## 7. 문서 쓰기

`references/docs.md` 형식으로 쓴다.

1. 리서치 파일(서베이를 했으면).
2. 한 방향 문 결정마다 ADR(`accepted`). "결정" 절에서 리서치 파일을 링크한다.
3. 개요 문서: 새로 만들거나, 있으면 바뀐 절만 고친다. 다른 절은 건드리지 않는다.

## 8. 처음 읽는 사람 점검

`general-purpose` 에이전트를 하나 띄운다. 이 대화를 볼 수 없으니 지시문에 넣는다.

- 읽을 것: 방금 쓴 개요 문서와 ADR 경로, 그리고 저장소.
- 할 일: 개요 문서의 "새 X 추가하는 법"마다 실제 코드에서 단계를 따라가 본다(새 프로젝트면 문서만으로 구조를 그려 본다). 파일을 고치지 않고 명령을 돌리지 않는다.
- 돌려줄 것: 막힌 단계(경로가 없거나, 예시 파일이 다르거나, 어디에 넣을지 모호함)와 문서로 답할 수 없는 질문. 확인한 것만.

돌려받은 것으로 문서를 보강한다. 설계 결정을 바꿔야 하는 질문이면 고치지 말고 사용자에게 묻는다.

## 9. 마무리

1. 개요 문서를 새로 만들었으면 CLAUDE.md 에 한 줄을 넣을지 묻는다(`references/docs.md` 5절).
2. 보고: 쓴 파일, 결정 목록(한 방향 문은 ADR 번호), 제안한 검사, 가정, 확인 못 한 것. 커밋은 사용자가 요청할 때만.
