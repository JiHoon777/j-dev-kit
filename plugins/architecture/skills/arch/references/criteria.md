# 좋은 아키텍처의 기준

design 과 review 가 함께 쓴다. 출처가 있는 기준만 적었다. 여기 없는 원칙으로 지적하려면 출처를 붙인다.

**AI 근거** 줄은 코딩 에이전트에 대한 연구 근거가 있을 때만 있다. [R] 은 논문·대규모 데이터, [V] 는 업체 연구다. AI 근거가 없는 항목도 기준으로서의 무게는 같다.

기준 묶음: ISO/IEC 25010:2023 유지보수성(모듈성, 재사용성, 분석성, 수정성, 시험성) — [arc42 요약](https://quality.arc42.org/articles/iso-25010-update-2023). 아래 1~8 은 이것을 확인 가능한 형태로 푼 것이고, 9~10 은 적합성과 확장성이다.

## 1. 모듈성과 경계

- **무엇:** 모듈은 바뀔 수 있는 결정 하나를 감춘다(정보 은닉). 공개 인터페이스는 작고 구현은 깊다. 호출하는 쪽은 내부를 몰라도 된다.
- **확인:**
  - 모듈의 공개 표면(export, public, 진입 파일)과 그 뒤의 구현량을 비교한다. 거의 그대로 넘기기만 하는 얕은 모듈이 많으면 비용이다.
  - **삭제 테스트:** 이 모듈을 지우면 복잡도가 사라지는가, 아니면 호출하는 곳 여러 군데로 퍼지는가. 퍼지면 제 몫을 하는 모듈이다. 사라지면 필요 없는 층이다.
  - 다른 모듈의 내부 파일을 직접 import 하는 곳.
- **출처:** Parnas, [On the Criteria To Be Used in Decomposing Systems into Modules (1972)](https://dl.acm.org/doi/10.1145/361598.361623); Ousterhout, *A Philosophy of Software Design* (깊은 모듈).

## 2. 결합도와 응집도

- **무엇:** 함께 바뀌는 것은 함께 두고, 따로 바뀌는 것은 떼어 둔다. 의존은 한 방향으로 흐르고 순환이 없다. 안정적인 것(도메인 규칙)이 자주 바뀌는 것(UI, 프레임워크, 외부 서비스)에 의존하지 않는다.
- **확인:**
  - import 그래프의 순환. 도구가 있으면 그것으로(`references/enforce.md`), 없으면 import 문을 grep 해서.
  - `git log`로 늘 함께 바뀌는데 서로 멀리 있는 파일 쌍(`references/review.md`의 측정).
  - 도메인 코드가 프레임워크·DB·HTTP 타입을 직접 쓰는 곳.
- **출처:** Constantine & Yourdon, *Structured Design* (결합도·응집도); Robert C. Martin, *Clean Architecture* (의존 규칙, 순환 없는 의존 원칙); Khononov, *Balancing Coupling in Software Design* (강도·거리·변동성으로 결합을 평가).

## 3. 변경 국소성

- **무엇:** 흔한 변경(기능 하나 추가·수정)이 적은 파일과 한두 모듈 안에서 끝난다.
- **확인:** 최근 커밋당 바뀐 파일 수의 중앙값과 상위 10%. 기능 커밋 몇 개를 골라 몇 개 층·폴더를 건드렸는지 본다. 한 기능이 매번 5~6개 층을 가로지르면 비용이다.
- **출처:** 위 1·2 와 같은 원칙의 결과. 핫스팟 분석: [Tornhill, *Your Code as a Crime Scene*](https://pragprog.com/titles/atcrime2/your-code-as-a-crime-scene-second-edition/), [요약](https://understandlegacycode.com/blog/focus-refactoring-with-hotspots-analysis/).
- **AI 근거 [R]:** 고쳐야 할 파일 수가 늘수록 에이전트 성공률이 크게 떨어진다. SWE-bench-Live 에서 1파일 소규모 수정은 48%, 3파일 이상은 10% 미만이다([arXiv 2505.23419](https://arxiv.org/abs/2505.23419)).

## 4. 분석성: 읽고 찾기

- **무엇:** 이름이 도메인을 말하고, 경로가 예측 가능하고, 호출 관계를 검색으로 따라갈 수 있다.
- **확인:**
  - 같은 개념을 부르는 이름이 여러 개인가, 이름이 하는 일과 다른가.
  - 문자열로 만든 이름, 리플렉션·데코레이터 기반 자동 등록, 전역 이벤트처럼 검색으로 연결을 찾을 수 없는 곳. 프레임워크의 표준 방식이면 지적하지 않는다. 같은 일을 프로젝트가 따로 마법처럼 만든 곳만 본다.
  - 파일·폴더 이름만 보고 어디에 무엇이 있는지 짐작할 수 있는가.
- **출처:** ISO 25010 분석성; Evans, *Domain-Driven Design* (보편 언어).
- **AI 근거 [R]:** 식별자 이름을 가리거나 잘못 지으면 LLM 의 코드 이해가 크게 떨어진다([arXiv 2510.03178](https://arxiv.org/abs/2510.03178), [arXiv 2307.12488](https://arxiv.org/abs/2307.12488)).

## 5. 시험성과 피드백 루프

- **무엇:** 모듈을 따로 시험할 수 있고, 프로젝트에 한 번에 돌리는 검증 명령(린트, 타입, 테스트, 빌드)이 있고, 그 결과가 빠르고 매번 같다. 외부 입력은 경계에서 파싱·검증하고, 안쪽은 검증된 타입을 쓴다.
- **확인:**
  - CLAUDE.md, package.json·Makefile·justfile 등의 검증 명령. 명령은 돌리지 않는다.
  - 테스트가 모듈 안쪽을 직접 건드리지 않고 공개 인터페이스로 시험하는가. 외부 의존을 바꿔 끼울 자리가 있는가.
  - 정적 타입이나 스키마 검증을 끄는 곳(`any`, 무시 주석)이 많은가.
- **출처:** ISO 25010 시험성; Feathers, *Working Effectively with Legacy Code* (seam); [Parse, don't validate](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/).
- **AI 근거 [R]:** LLM 이 만든 TypeScript 컴파일 오류의 94% 가 타입 오류이고, 타입 검사로 이끌면 오류가 줄어든다([arXiv 2504.09246](https://arxiv.org/abs/2504.09246)). 타입 검사기가 고칠 신호를 준다는 근거이지, 타입 언어가 전반적으로 낫다는 근거는 아니다.

## 6. 일관성

- **무엇:** 같은 일(데이터 접근, 오류 처리, 설정 읽기, 로깅, HTTP 호출)을 하는 방식이 하나다. 공용 코드가 있는 곳이 정해져 있다.
- **확인:** 같은 목적의 라이브러리가 둘 이상인가(ORM 둘, HTTP 클라이언트 둘). 비슷한 코드가 여러 곳에 복사돼 있는가.
- **출처:** ISO 25010 재사용성·수정성; Hunt & Thomas, *The Pragmatic Programmer* (DRY 는 코드가 아니라 지식의 중복을 말한다).
- **함께 볼 것:** 따로 바뀔 가능성이 큰 작은 중복은 결합보다 낫다. 같은 지식(규칙, 불변식)의 중복만 지적한다.

## 7. 규칙의 강제 (피트니스 함수)

- **무엇:** 중요한 아키텍처 결정(의존 방향, 모듈 경계, 금지된 import)이 문서에만 있지 않고 자동 검사(린트 규칙, 아키텍처 테스트)로 있다. 검사가 실패하면 무엇을 어떻게 고칠지 알려 준다.
- **확인:** `references/enforce.md`의 도구 설정이 있는가. 개요 문서·ADR 의 규칙 중 검사가 없는 것.
- **출처:** Ford, Parsons, Kua, Sadalage, *Building Evolutionary Architectures* 2판 (피트니스 함수).
- **AI 근거 [R]:** 에이전트는 테스트를 통과하면서도 프로젝트의 설계 제약을 자주 어긴다. 테스트 통과와 설계 준수는 거의 상관이 없다([arXiv 2604.05955](https://arxiv.org/abs/2604.05955), [arXiv 2603.27745](https://arxiv.org/abs/2603.27745)).

## 8. 결정 기록

- **무엇:** 되돌리기 어려운 결정은 ADR 로 이유와 대안이 남아 있다. 개요 문서는 짧은 지도이고, 코드를 읽으면 알 수 있는 것을 다시 쓰지 않는다. CLAUDE.md 는 짧다.
- **확인:** ADR 폴더, 개요 문서, CLAUDE.md 길이. 문서와 실제 코드가 어긋난 곳.
- **출처:** Nygard, [Documenting Architecture Decisions (2011)](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions); [MADR](https://adr.github.io/madr/); [arc42](https://arc42.org/overview).
- **AI 근거 [R]:** 저장소의 컨텍스트 파일은 성공률을 거의 올리지 못하고 비용을 20% 넘게 늘렸으며, LLM 이 만든 것은 오히려 떨어뜨렸다. 짧게, 사람이 쓴 꼭 필요한 것만 둔다([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)).

## 9. 적합성

- **무엇:** 구조와 스택이 이 프로젝트의 품질 목표, 규모, 팀에 맞다. 지금 필요 없는 것을 미리 만들지 않았고, 새롭거나 덜 검증된 기술을 꼭 필요한 곳에만 썼다.
- **확인:**
  - 품질 목표 3~5개(arc42 1.2)를 순위대로 적고, 각 구조적 선택이 어느 목표에 기여하는지 묻는다. 기여하는 목표가 없는 층·서비스·추상화는 과한 설계다.
  - 규모에 비해 무거운 것(사용자 몇 명인데 마이크로서비스, 이벤트 소싱, 다중 DB).
  - 새롭거나 덜 검증된 기술의 수(`references/stack.md`의 혁신 토큰).
- **출처:** [arc42 품질 목표](https://docs.arc42.org/section-1/); McKinley, [Choose Boring Technology](https://mcfunley.com/choose-boring-technology); Fowler, [Yagni](https://martinfowler.com/bliki/Yagni.html); Bezos 2015 주주 서한(Type 1/Type 2 결정 — [요약](https://fortune.com/2017/05/11/jeff-bezos-shareholder-letter/)).

## 10. 확장성

- **무엇:** 앞으로 생길 변경의 종류(새 화면, 새 엔드포인트, 새 결제 수단, 새 데이터 소스)마다 넣을 자리가 정해져 있다. 그 변경이 한 곳에서 끝나고, 기존 코드를 여기저기 고치지 않아도 된다. 모든 것이 거쳐 가는 신(god) 모듈이 없다.
- **확인:**
  - 모듈마다 **변동성**을 적는다: 무엇 때문에 바뀌는가, 얼마나 자주 바뀌는가. 자주 바뀌는 것이 안정적인 것 깊숙이 섞여 있으면 비용이다.
  - "새 X 추가하는 법"을 실제 코드에서 따라가 본다. 몇 개 파일, 몇 개 모듈을 고쳐야 하는가.
  - 줄 수와 변경 빈도가 모두 높고, import 하는 곳이 아주 많은 파일.
  - 바꿔 끼울 자리(seam)는 구현이 둘 이상 있거나 곧 생길 때만 정당하다. 구현이 하나뿐인 인터페이스는 가설이다.
- **출처:** Parnas (변경 가능성으로 모듈 나누기); Khononov (변동성); Ford 외 (진화적 아키텍처); Feathers (seam).

## 지적하지 말 것

- 도메인이 원래 복잡해서 생긴 복잡도
- 프레임워크가 강제하거나 권장하는 구조(그 프레임워크 공식 문서의 방식)
- 취향: 폴더 이름 스타일, 따옴표, 줄 길이, 문법 선택
- 출처 없는 원칙, 유행하는 패턴이라서(클린 아키텍처, 헥사고날, 마이크로서비스를 "안 썼다"는 것만으로)
- 폴더 모양만 보고 내린 판단. 코드나 측정으로 확인한 것만
- 이번 범위 밖에 있고 측정으로도 비용이 보이지 않는 오래된 코드
- 확정된 ADR 이 이미 정한 것. 그 결정을 다시 볼 이유(ADR 의 "다시 볼 때")가 생겼을 때만 새 ADR 을 제안한다

## AI 근거를 기준으로 쓰지 않는 것

실천가 의견만 있는 주장(파일 줄 수 상한, 특정 폴더 구조가 AI 에 좋다 등)은 기준으로 쓰지 않는다. `--research`로 새 연구를 찾았으면 리서치 파일에 출처와 함께 적고, 이 파일의 기준과 다른 점만 보고에 표시한다.
