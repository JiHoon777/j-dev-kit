# Maintain a verification skill

> 원문: `cursor/plugins`의 `pstack/skills/maintain-verification-skill/SKILL.md` (MIT, Lauren Tan). Cursor 이름을 Claude Code 것으로 바꾸고 가져오지 않은 스킬을 가리키는 줄을 뺐다.

**언제:** 프로젝트의 검증 스킬과 기능 지도가 실제 앱과 맞는지 주기적으로 점검할 때, 또는 "verify 스킬을 점검해 줘" 같은 요청에 쓴다. 기능마다 소스를 읽는 에이전트를 나란히 띄우고, 실행 세션 하나로 모든 기능을 몰고, 증명된 수정을 많아야 한 번 낸다.

기능 지도는 앱이 바뀌는 순간부터 낡는다. 이 스킬은 `create-verification-skill` 스킬로 만든 스킬(또는 기능 지도가 있는 프로젝트 전용 검증 스킬)을 유지하는 절차다. 꼼꼼함의 단위는 문장 하나하나가 아니라 기능이다. 모든 기능 파일을 소스로 확인하고 모든 기능을 실제로 몰아 본다. 글머리표 하나하나를 끝까지 판정하지는 않는다.

## 결과

하나를 고르고 어느 것인지 말한다.

- **clean:** 모든 기능을 소스와 실행으로 확인했고 낼 것이 없다. 커밋도 PR 도 없다.
- **changed:** 증명된 문서, harness, 지도 수정을 한 번에 커밋한다. 프로젝트가 PR 을 쓰면 PR 하나로 낸다.
- **blocked:** 확인을 끝내지 못했거나 증명된 수정을 안전하게 낼 수 없었다. 무엇이 막았는지 정확히 말한다.

## 고치는 범위

검증 스킬의 폴더(SKILL.md, features/, 그 스킬이 가진 harness 스크립트)만 고친다. 실행 중에 제품 코드를 고치지 않는다. 지도에 적힌 동작을 앱이 더는 하지 않으면 doc drift 이거나 제품 회귀다. doc drift 면 지도를 고친다. 제품 회귀면 보고하고, 문서로 덮지 않는다.

## 절차

0. **대상을 찾는다.** 유지할 검증 스킬을 찾는다. 본문에 launch/drive 섹션과 기능 지도가 있는 프로젝트 전용 스킬이다(대개 `.claude/skills/verify-*/`). 후보가 여럿이면 어느 것인지 묻는다. 없으면 대상을 지어내지 말고 멈추고 `create-verification-skill` 스킬을 알려 준다.

1. **색인 정리.** 기능 지도 README 를 읽고 같은 폴더의 파일을 glob 으로 본다. 빠진 항목, 남는 항목, 겹친 항목, 죽은 항목을 고친다. 가볍게 한다. 목록을 따로 생성하지 않는다.

2. **소스 읽기.** 기능 파일마다 `Explore` 에이전트 하나를 동시에 띄운다. 지시문에 "파일을 고치지 않는다"를 넣는다. 에이전트마다 "이 사용자 기능은 어떻게 동작하나?"를 소스로 설명하고, doc drift 로 보이는 것을 인용과 함께 짚고, 간결한 실행 검증 방법 하나를 돌려준다. 하위 에이전트는 앱을 몰지 않고 파일을 고치지 않는다. 돌려주는 모양: 기능 요약 / 소스 진입점 / drift 로 보이는 것 또는 없음 / 검증 방법 하나.

3. **맞추기.** 모든 기능 파일에 돌려받은 요약이 있어야 한다. 겹치는 검증 방법을 되도록 적은 수의 앱 상태로 합친다. 인용된 drift 는 골라서 확인한다. 깨끗하다는 주장은 다시 증명하지 않는다. 최근 변경을 훑어 지도에 빠진 사용자 접점을 찾는다. 빠졌다고 하려면 구체적인 소스 경로가 있어야 한다.

4. **실행.** 소스가 깨끗해 보여도 꼭 한다. 모는 일은 모두 조율하는 쪽이 맡는다. 검증 스킬의 launch 방식을 따른다. 서버와 UI 는 오래 사는 인스턴스 하나를 차례로 몰고, 금방 끝나는 CLI 는 drive 마다 새 격리 세션을 쓴다(이 문서가 아니라 그 스킬의 Launch 섹션이 정한다). 모든 기능을 한 번 이상 써 본다. 어떤 실패가 나든 실행 내내 세 가지를 지킨다.
   - (1) 마지막으로 뜻밖의 일을 한 뒤 health check 를 하지 않은 인스턴스는 몰지 않는다. 첫 drive 전에 doctor 를 돌린다. 세션이 단위면 새 세션마다 doctor 를 돌린다. 실패한 drive 뒤에는 다시 doctor 를 돌린다. doctor 가 실패를 볼 수 없으면(멀쩡한 프로세스에서 굳어 버린 UI 상태) 요행을 바라지 말고 알려진 상태로 되돌리거나 다시 띄운다.
   - (2) 지금까지 남긴 증거는 cleanup 을 할 때마다 살아남는다. 짐작하지 말고 밝힌 위치에서 확인한다.
   - (3) drive 가 시작한 것은 그 drive 에 쓸모가 있는 동안만 남는다. 실패한 시도의 찌꺼기는 세션이 멈췄든 끝났든 함께 쓰는 것이든 치운다(함께 쓰는 인스턴스면 인스턴스가 아니라 찌꺼기를 치운다).

   스킬 drift 탓에 doctor 가 실패하면 그것도 drift 다. 고치는 범위 안에서 고치고 한 번 다시 해 본 뒤에야 `blocked`라고 한다. 다시 할 때는 고친 것 때문에 무효가 된 것만 다시 시작한다. 닿을 수 없는 기능은 구체적인 전제 조건(인증, 권한, OS, 외부 상태)과 시도한 경로가 있을 때만 `verified-unreachable`이다. 지도에 그 전제 조건이 빠져 있으면 그것이 drift 다. 분류에서 나온 harness 수정은 내기 전에 실제로 다시 몰아 본다. 마지막 teardown 은 그 다시 하는 증명까지 포함해 실행의 마지막 drive 뒤에 한다. 실행이 끝난 뒤에 남는 것이 없게 한다(증거는 스킬이 정한 대로 남는다).

5. **분류.** 사용자 관점의 설명이 틀렸거나 빠졌으면 doc drift 다. 고친다. 동작은 되는데 harness 가 몰지 못하면 harness gap 이다. 고친다. harness 수정은 스킬을 만들 때와 같은 helper 규칙을 따른다(스크립트는 실행 가능하고 부르는 방법이 스킬 본문에 있다). 앱 동작이 실제로 망가졌으면 product gap 이다. 사용자에게 알릴 것으로 적어 두고 이번 수정에는 넣지 않는다.

6. **내거나 멈춘다.** changed 면 바뀐 파일을 모두 다시 읽은 뒤 증명된 수정을 한 번에 커밋한다. 프로젝트가 PR 을 쓰면 PR 하나로 낸다. clean 이나 blocked 면 커밋도 PR 도 없이 결과와 확인한 범위를 정직하게 보고한다.

간결한 실행 노트(확인한 기능, 닿지 못한 기능의 전제 조건, 확인된 drift, 결과)를 임시 위치에 둔다. 커밋하지 않는다.
