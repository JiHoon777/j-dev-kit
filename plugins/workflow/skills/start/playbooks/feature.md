# Feature

> 원문: `cursor/plugins`의 `pstack/skills/poteto-mode/playbooks/feature.md` (MIT, Lauren Tan). Cursor 이름을 Claude Code 것으로 바꾸고 가져오지 않은 스킬을 가리키는 줄을 뺐다.

**언제:** 새 동작을 더하는 항목. 설계는 내가 정하고, 구현은 맡기고, 실제 화면이나 명령으로 검증한다.

**설계의 주인은 나다. 계획하고, 리뷰하고, 검증한다.** 구현은 맡긴다. 주도권은 놓지 않는다.

1. 영향받는 하위 시스템을 따라가 본다.
2. `architect` 스킬로 모양을 정한다.
3. 처리량 점검을 할 일 네 개로 적는다. 정말 해당하지 않는 것(파일 하나, 나눌 것이 없음)도 빼지 말고 `해당 없음: <이유>`로 남긴다.
   - **먼저 막는 단계.** 관문은 나눠 맡기기 전에 돈다.
   - **독립된 작업 줄기.** 파일, 서비스, 층이 겹치지 않으면 함께 돌린다. 같은 곳에 쓰는 일은 차례로 한다.
   - **함께 쓰는 바뀌는 상태.** 기본은 대상을 나누는 것이다(`principle-separate-before-serializing-shared-state` 스킬). 진짜 불변 조건이 있을 때만 차례로 한다.
   - **가장 작게 안전하게 나누기.** 한 명이 하는 것이 최선이면 왜 그런지 적는다.
4. 코드 쓰기는 범위를 구체적으로 정해 하위 에이전트에 맡긴다. 범위에는 파일 경로, 이름 붙인 데이터 모양과 그것을 담는 구조, 성공 기준을 넣는다. 구조는 `principle-model-the-domain` 스킬을 따라 맡기기 전에 고른다: 흩어진 불리언 대신 상태 기계, 분기 대신 표나 레지스트리, 되풀이되는 모양 가정 대신 타입 있는 모델. 구현에 타당한 모양이 여럿이면(오류 처리, 추상화 층, 테스트 구조) `architect` 스킬로 두 안을 그려 고른다. 하위 에이전트를 띄울 수 없으면 직접 쓰되, 리뷰는 쓴 쪽이 아닌 에이전트가 한다. 맡긴 에이전트를 기다리기만 하는 답을 하지 않는다. 고칠 곳만 고친다. 위쪽에서 온 파일은 원본에 다시 대어 본다. 공용 부품을 고쳤으면 쓰는 곳 모두에 옮기고 하나씩 확인한다. 자주 커밋한다.
5. 맞는 표면에서 검증한다. "결론 없음"이나 다른 표면에서 한 확인은 통과가 아니다. 그렇다고 알린다.
6. 작고 순서 있는 커밋으로 정리한다. 뒤따르는 일은 그 위에 쌓는다.
   `principle-sequence-verifiable-units` 스킬을 따라, 작은 단위마다 만들고, 확인하고, 커밋한 뒤 다음으로 간다.
7. `start` 절차의 마무리로 간다.

코드로 묶인 일(기능 하나, 이전 하나)은 한 명이 맡고 처리량 점검을 그 안에 둔다. 그 한 명이 막는 단계 뒤에 안에서 나눠 맡긴다. 부모 쪽에서 나눠 맡기는 것은 서로 독립된 결과물을 내는 조각(감사, 여러 하위 시스템 조사, 겨루는 실험)일 때다. 단계가 바뀔 때 처리량 점검을 다시 쓴다. 끼어들기를 이어 붙이지 말고 새로 맡긴다.

**보고:** 무엇을 만들었나, 무엇을 골랐고 왜 그랬나, 처리량 점검, 열려 있는 결정. 설계 대안은 표로.
