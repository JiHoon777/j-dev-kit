# Hillclimb

> 원문: `cursor/plugins`의 `pstack/skills/poteto-mode/playbooks/hillclimb.md` (MIT, Lauren Tan). Cursor 이름을 Claude Code 것으로 바꾸고 가져오지 않은 스킬을 가리키는 줄을 뺐다.

**언제:** 한 가지 수치를 목표까지 거듭 끌어올리는 일. 한 번 고치고 끝나는 일이면 `playbooks/bug-fix.md`나 `playbooks/perf-issue.md`를 쓴다.

**수치와 실험의 온전함은 내가 책임진다. 감독하고 리뷰한다. 시도는 맡긴다.** 잴 수 있는 한 가지를 목표에 맞춰 꾸준히, 거듭 개선하는 일에 쓴다. 한 번 고치는 일은 `playbooks/bug-fix.md`나 `playbooks/perf-issue.md`다. 이것은 반복이다.

핵심 규율: 하나 바꾸고, 한 번 재고, 남기거나 되돌린다. 시험하지 않은 변경을 쌓지 않고, 코드를 읽은 것만으로 이겼다고 하지 않는다(`principle-prove-it-works` 스킬).

1. 수치를 고르기 전에 작업 부하와 구조부터 파악한다. 대상을 추적하고, 결과를 움직일 수 있는 현실적인 작업 부하 차원(데이터 크기, 이력, 상태, 동시성)을 짚고, 사용자의 불만을 재현하는 사례를 고른다. 재현하는 사례가 없으면 hillclimb 을 하지 말고 재현부터 고친다. 그다음 수치 하나, 어느 쪽이 더 나은 방향인지, 확인할 수 있는 정지 조건을 정한다. 정지 조건은 목표에 시도 횟수의 하한을 묶어, 운 좋은 이른 성공으로 실행이 끝나지 않게 한다("기준선보다 50% 이상 좋아지고 10번 이상 반복"이 이런 모양이다). 사용자가 준 숫자가 있으면 그것을 쓰고, 없으면 합의한다.
2. 측정 하네스를 만들고, 민감도를 증명하고, 그다음 고정한다(`principle-build-the-lever` 스킬). 대비되는 현실적인 작업 부하를 돌려, 목표 사례는 증상을 재현하고 더 쉬운 사례는 예상대로 갈리는지 확인한다. 하네스가 둘을 구별하지 못하면 작업 부하나 수치를 고친다. 고정하기 전에 `benchmark-checklist` 스킬로 하네스를 따져 보고, 하네스가 오류 수와 한 일의 수를 찍게 한다. 고정한 뒤에는 되풀이할 수 있는 명령 하나가 수치를 내고, 잡음을 넘을 만큼 표본을 뜬다(한 번 실행이 아니라 N 번의 중앙값). 무엇이든 바꾸기 전에 기준선 수치와 회귀 관문(계속 통과해야 하는 테스트)의 통과 실행을 기록한다.
3. 결정 기록을 항목 파일 `Implementation Notes`의 "정한 것" 줄로 연다. 한 시도에 한 줄이고, 가설, 바꾼 것, 전, 후, 차이, 테스트, 남김/되돌림을 적는다. 시도하기 전마다 이 줄들을 읽는다.
4. 가설마다 1단계의 구조 모델에 근거를 둔다. 그래야 가설이 "뭔가 메모이즈해 본다"가 아니라 구체적인 메커니즘("X 가 첫 페인트를 막으니 부팅 경로에서 뒤로 미룬다")을 짚는다. 성능 수치면 `playbooks/perf-issue.md` 2단계의 성능 주문 순서로 가설을 줄 세운다. 순서만 빌리고 그 단계의 정지 규칙은 빌리지 않는다.
5. 반복한다. 한 번에 가설 하나다.
   - 변경은 범위를 좁게 정해 하위 에이전트에 넘긴다. 직접 치지 말고 감독하고 diff 를 리뷰한다(`principle-guard-the-context-window` 스킬). 서로 독립인 가설이 여럿 살아 있으면 병렬 하위 에이전트에 나눠 주고, 각자 자기 워크트리에서 하게 한다(`principle-separate-before-serializing-shared-state` 스킬).
   - 고정한 하네스로 전과 후를 재고, 회귀 관문을 돌린다.
   - 수치가 잡음을 넘어 움직이고 관문이 통과할 때만 받아들인다. 아니면 변경을 통째로 되돌린다. "도움이 될지도 모르는" 손질은 남기지 않는다.
   - 받아들인 수정 하나에 커밋 하나다. 바꾼 파일만 스테이징한다(`git add <files>`, `-A`는 쓰지 않는다). 남겼든 되돌렸든 줄을 적는다.
   반복마다 확인으로 끝내고 나서 다음을 시작한다(`principle-sequence-verifiable-units` 스킬).
6. 첫 정체 구간을 넘어선다. 거절이 여러 번 이어져 막히면, 언덕을 다 올랐다고 결론짓기 전에 범주를 바꾸거나, 아깝게 놓친 것들을 합치거나, 소스를 다시 읽거나, 더 과감한 것을 해 본다. 정확성과 단순함이 숫자보다 앞선다. 동작을 깨는 성공은 되돌리고, 숫자를 지키는 단순화는 남긴다(`principle-laziness-protocol` 스킬).
7. 정지 조건을 채웠거나, 남은 아이디어가 미미해 비용만큼의 값이 없으면 멈춘다. 조건을 채우려고 조건을 느슨하게 하지 않고, 값싼 미시도 가설이 남아 있는데 그만두지 않는다. 막혔으면 헛돌지 말고 알린다.
8. 받아들인 커밋을 들어간 순서대로 쌓은 채 `start` 절차의 마무리로 간다.

**보고:** 수치와 목표, 기준선에서 최종까지와 퍼센트 차이, 돈 반복 수(남김과 되돌림), 받아들인 수정마다 한 줄, 시도 줄이 있는 항목 파일의 경로, 더 밀어붙인다면 다음에 해 볼 가장 좋은 아이디어.
