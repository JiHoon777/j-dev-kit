# Bug fix

> 원문: `cursor/plugins`의 `pstack/skills/poteto-mode/playbooks/bug-fix.md` (MIT, Lauren Tan). Cursor 이름을 Claude Code 것으로 바꾸고 가져오지 않은 스킬을 가리키는 줄을 뺐다.

**언제:** 버그를 고치는 항목. 직접 재현하고, 실행 증거로 원인을 좁히고, 증거가 뒷받침하는 가장 작은 변경만 낸다.

**이 일의 주인은 나다. 계획하고, 리뷰하고, 검증한다.** 조사와 수정은 하위 에이전트에 맡기고 주도권은 놓지 않는다.

과학적으로 한다. 내보내는 줄은 모두 실행 증거로 거슬러 올라갈 수 있어야 한다. "도움이 될지도 모르는" 이중 안전장치는 가설이지 수정이 아니다. 내보내지 않는다. 증거가 가설을 반박하면 그 가설 때문에 넣은 것을 되돌린다. 증거가 뒷받침하는 가장 작은 변경만 내보내고 그 이상은 내보내지 않는다.

1. 버그가 난 표면에서 `control-ui` 스킬이나 `control-cli` 스킬로 직접 재현한다. 디버그 절차나 계측 절차가 사용자에게 재현을 부탁하라고 해도 직접 한다. 사용자에게 부탁하는 것은 그 도구로 대상에 닿을 수 없는 구체적인 이유를 댈 수 있을 때뿐이고, 갈 수 있는 데까지 몰아 본 뒤여야 한다. 바로 재현되지 않으면 재현될 때까지 유발 조건을 만들어 내거나, 조건을 좁히거나, 계측을 넣는다.
2. 원인을 이분 탐색한다. 후보 가설을 세우고 하나만 남을 때까지 지워 나간다. 가설은 문제가 난 하위 시스템을 추적한 결과와 `why` 스킬로 본 회귀 이력에서 시작한다. 매번 남은 문제 공간을 가장 많이 잘라 내는 쪽으로 나누고, 실행 증거를 얻고, 지운다. 프로그램 상태가 불분명하면 계측이나 로그를 넣고 코드가 도는 동안 읽는다. 추측하지 않는다. 길거나 잘 잡히지 않는 추적은 Claude Code 의 `/loop` 명령으로 돌린다. 3단계의 `architect` 스킬로 가기 전에, 살아남은 *메커니즘*을 실행 증거로 확인한다.
3. 수정을 계획한다. 함수 경계를 넘으면 `architect` 스킬을 먼저 한다. 구현은 범위를 구체적으로 정해 하위 에이전트에 맡긴다.
4. 같은 표면에서 검증한다. 처음의 재현이 이제 통과해야 한다. "결론 없음"이나 다른 표면에서 한 확인은 통과가 아니다. 그렇다고 알린다. 단위 테스트는 분기의 동작을 보여 줄 뿐, 버그가 없다는 것을 보여 주지 않는다.
5. 실패하는 재현이 수정보다 먼저 git 이력에 들어가도록 커밋을 나눈다. 버그에 값싼 로컬 테스트 경로가 있으면 실패하는 테스트를 먼저 쓰는 순서는 `start` 절차의 테스트 규칙을 따른다. 테스트가 비싸거나, 통합에 크게 기대거나, 불분명하면 건너뛴다.
   이것이 `principle-sequence-verifiable-units` 스킬의 전형이다. 실패하는 테스트가 먼저 오고 수정이 그 위에 온다.
6. `start` 절차의 마무리로 간다.

**보고:** 무엇이 깨져 있었나, 근본 원인, 수정, 어떻게 검증했나. 실패하다가 통과하는 재현 출력을 그대로 붙인다.
