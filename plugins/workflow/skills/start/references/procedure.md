# start 절차: 항목 하나를 구현해 머지까지

백로그 항목 **하나**를 계획하고, 구현하고, 리뷰하고, 마무리한다. 멈추고 묻는 곳은 `SKILL.md`의 묻는 기준에 드는 것뿐이다. 나머지는 정하고 항목 파일에 적으면서 끝까지 간다.

요청한 항목: 인자.

아래에서 "`<이름>` 스킬을 따른다"는 말은 `SKILL.md` 색인의 안내대로 그 스킬의 본문 파일(`<이 스킬 폴더>/../<이름>/SKILL.md`)을 Read 도구로 읽고 따른다는 뜻이다. 플레이북은 `<이 스킬 폴더>/playbooks/<이름>.md`다.

명령은 모두 저장소 루트(`git rev-parse --show-toplevel`)에서 돌린다. 워크트리에서 일하면 그 워크트리의 루트다. 프로젝트 CLAUDE.md 에 PR·푸시 규칙이 있으면 따른다.

## 1. 시작할 수 있는지

`git branch --show-current`, `git status --short`, `git branch --list 'w/*'`, `git log --oneline <기준>..HEAD`로 상태를 본다.

| 확인 | 해당하면 |
| --- | --- |
| 기준 브랜치에 커밋이 없다 | 첫 커밋이 필요하다고 말하고 멈춘다 |
| 커밋하지 않은 변경이 있다 | 보여 주고 어떻게 할지 묻는다. 스스로 버리지 않는다 |
| 이 항목의 `w/` 브랜치에 있다 | 묻지 않고 이어 간다(아래 "이어 가기") |
| 이 항목을 위해 막 딴 워크트리에 있다 | 그대로 진행한다: 워크트리 안이고(`git rev-parse --path-format=absolute --git-dir --git-common-dir`의 두 줄이 다르면) 브랜치에 기준 브랜치 이후 커밋이 없다. 이름이 `w/<이름>`이 아니면 4단계에서 바꾼다 |
| 이 항목의 `w/` 브랜치가 이미 있고 지금 그 브랜치가 아니다 | 그 브랜치에서 일하던 세션이 있으면 거기서 이어 가라고 알린다. 없으면 여기서 이어 간다: 그 브랜치가 다른 워크트리에 있으면(`git worktree list`) `EnterWorktree`에 그 경로를 줘서 옮기고(도구가 없거나 거부하면 이후 명령을 그 폴더에서 돌린다), 없으면 `git switch w/<이름>` |
| 기준 브랜치도, 이 항목의 브랜치도 아닌 곳에 있다 | 다른 항목이나 다른 세션의 것일 수 있다. 건드리지 않고 어떻게 할지 묻는다 |

항목 찾기: 인자를 `docs/backlog/`에서 찾는다(`README.md`와 `_`로 시작하는 파일은 항목이 아니다). 없거나 여럿이면 `To Do` 항목을 번호와 제목으로 보여 주고 고르게 한다. 항목 파일을 끝까지 읽고, `dependencies`가 모두 `docs/done/`에 있는지 확인한다.

**이어 가기:** 항목 파일의 `Implementation Plan`, 체크된 Acceptance Criteria, `Implementation Notes`를 읽고 남은 단계부터 한다.

- 구현이 남았다 → 5단계
- AC 가 모두 체크됐다 → 7단계(리뷰)
- 항목이 이미 `docs/done/`에 있다 → 12단계(머지)

## 2. 기준선과 스택 점검

0. **워크트리 준비:** 워크트리면
   - 프로젝트에 의존성 설치가 필요하면(예: `package.json`과 잠금 파일) 기준선보다 먼저 설치한다. 새 워크트리에는 설치된 것이 없어, 설치 전에 잰 기준선은 진짜 실패를 가린다.
   - 워크트리가 기준 폴더 안에 있고(예: `.claude/worktrees/`) 테스트·린트·타입 검사 도구가 그 폴더까지 읽으면 기준 폴더의 검증이 다른 항목의 코드까지 돈다. 그 도구 설정에서 빠져 있지 않으면 알린다.
1. **기준선:** 검증 명령을 한 번 돌린다. 이미 실패하는 것(명령, 실패한 테스트·파일 이름)만 적어 둔다. 작업을 막지는 않고 알린다. 뒤의 검증은 이것과 견줘 새 실패만 본다.
2. **스택 점검:** 쓸 수 있는 스킬 중 이름이 `-start-check`로 끝나는 것을 전부 Skill 도구로 부른다(예: `server:server-start-check`). 해당하지 않는 점검은 "해당 없음"만 돌려준다. 돌려받는 것:
   - **지킬 것:** 구현 중 따를 규칙과 부를 스킬
   - **계획 전에 할 것:** 계획에 앞서 끝낼 일(예: 시안). 3단계로 가기 전에 한다
   - **플랜에 넣을 것:** 이 항목에 해당할 때만
   - **물을 것:** 판단할 수 없는 것이 있을 때만. 3단계의 착수 전 질문에 합친다

## 3. 계획

계획 승인을 받지 않는다. 플랜 모드에 들어가지 않는다.

1. **되짚기:** 첫 메시지에서 목표와 그것을 채우는 가장 작은 변경을 한두 문장으로 되짚는다.
2. **읽기는 크기에 맞춘다.**
   - 작은 항목(파일 몇 개, 새 구조 없음): 에이전트 없이 관련 코드를 직접 읽는다.
   - 큰 항목(여러 모듈, 새 구조): `Explore` 에이전트를 서로 다른 영역으로 한 메시지에서 띄운다. 꼭 읽을 파일을 돌려받고, 그 파일을 직접 읽는다.
3. **플레이북:** `SKILL.md` 색인에서 항목의 성격에 맞는 플레이북을 고르고, 그 단계를 할 일 목록에 옮긴다. 맞는 것이 없으면 이 절차의 5단계가 기본 흐름이다.
4. **도구와 단계:** 이 항목의 일이 어느 분야의 일이고, 그 분야 최고 실무자는 어떤 도구(이름, 명령)와 단계로 하는지 정한다. 역할을 상정하지 말고 도구와 단계를 적는다. 모르면 문서나 웹에서 찾는다. 스택 점검이 준 도구는 그대로 쓰고 모자란 것만 더한다.
5. **설계:** 직접 정한다. 함수 경계를 넘는 변경이면 `architect` 스킬을 따른다. 돌려 보면 정해지는 갈림길은 `playbooks/prototype.md`로 정하고 결과와 근거를 적는다.
6. **AC 의 빈틈:** 항목을 읽다가 AC 끼리 모순되거나 사람만 정할 결정이 빠져 있으면 착수 전 질문에 넣는다.
7. **착수 전 질문:** 묻는 기준에 드는 것이 있을 때만, 한 번에 묻는다. 스택 점검의 "물을 것"과 프로젝트당 한 번 묻는 것(공식 스킬 설치, 검증 스킬 만들기)을 여기에 합친다. 선택지에는 추천과 이유를 붙인다. 물을 것이 없으면 멈추지 않는다.
8. **계획을 쓴다.** 4단계에서 항목 파일에 적는다. 넣을 것:
   - 무엇을 하나: 한두 문장, 이번에 빼는 것
   - 고른 플레이북, 도구와 단계(설치할 것 포함)
   - 바꿀 파일과 각각의 일, 먼저 쓸 테스트, 순서
   - 성공 기준: Acceptance Criteria 마다 어떻게 확인하나(명령, 화면, 판정 에이전트)
   - 스택 점검의 "플랜에 넣을 것"
   - 정한 것

사용자가 "계획을 보자"고 하면 계획을 보여 주고 기다린다.

## 4. 기록

1. 작업 브랜치 `w/<.md 를 뺀 항목 파일 이름>`(아래 `<이름>`)을 둔다.
   - 기준 브랜치에 있으면 `git switch -c w/<이름>`.
   - 이 항목을 위해 딴 워크트리에 있고 브랜치 이름이 다르면 `git branch -m w/<이름>`. 검증 Stop 훅이 `w/` 브랜치에서만 돈다.
   - 웹 포트나 서버 포트가 설정돼 있으면 항목 포트를 `기준 포트 + 항목 번호`로 정한다(예: 웹 5000, 항목 007 → 5007). 적은 것만 정한다.
     - 포트마다 `bash <scripts>/pick-port.sh <기준 포트> <항목 번호>`를 돌려 첫 줄의 포트를 쓴다. 0 이 아닌 값으로 끝나면 출력한 이유를 알린다.
     - 정하자마자 항목 파일에 적는다. 동시에 시작한 다른 세션이 볼 수 있게 하려는 것이다.
2. 항목 파일: `status: In Progress`, `updated_date` 오늘, 계획을 `Implementation Plan`에, 기준선을 `Implementation Notes`의 `### Baseline` 아래에, 정한 포트를 `### 포트` 아래에(`- 웹: 5007`처럼 한 줄씩), 정한 것을 `### 정한 것` 아래에.
3. 커밋: `chore(backlog): <번호> start`

## 5. 구현

- 고른 플레이북의 단계, 계획의 도구와 단계, 스택 점검의 지킬 것을 따른다.
- **테스트:** 싸고 분명한 테스트 길이 있으면 실패하는 테스트를 먼저 쓰고, 고치기 전에 그 테스트가 의도한 이유로 실패하는지 돌려 본다. 그런 길이 없으면(넓은 하니스가 필요하다, mock 이 깨지기 쉽다, 느린 e2e 뿐이다, 문서나 설정만 바뀐다) 억지로 쓰지 않는다. 가장 가까운 실행 확인(명령, 스크립트, 브라우저)을 쓰고 그렇게 한 이유를 적는다. 나쁜 테스트보다 테스트 없음이 낫다. 테스트는 보이는 동작을 단언한다(`principle-test-behavior-not-implementation` 스킬).
- 통과시키려고 기존 테스트를 지우거나 약하게 고치지 않는다(삭제, skip, 시간 제한 늘리기, 스냅샷 갱신). 테스트가 틀렸다고 보면 멈추고 묻는다.
- Acceptance Criteria 에 있는 것만 한다. 주변 코드를 다듬지 않는다. 필요해 보이는 다른 일은 적어 두었다가 10단계의 "나중" 후보로 올린다.
- **범위가 커지면 멈춘다.** 아래 넷 중 하나면 멈추고 묻는다. 그 밖의 달라진 것은 정하고 적는다.
  - AC 에 없는 동작을 더해야 한다
  - 새 의존성이나 도구를 설치해야 한다
  - 스키마나 공개 API 를 바꾸거나 무언가를 지워야 한다
  - CLAUDE.md 나 설정을 바꿔야 한다
- AC 를 하나 끝내면 바깥 증거(명령 출력)가 있는 것만 바로 체크한다. 판정자가 필요한 AC 는 6단계에서 한 번에 판정받는다.
- 묻지 않고 정한 것은 그때그때 `### 정한 것`에 적는다. 계획에서 바뀐 것도 `Implementation Notes`에 적는다.
- 의미 있는 단계마다 작업 브랜치에 커밋한다. 커밋 전에 `deslop` 스킬을 따른다. 기준 브랜치에 커밋하지 않는다.

## 6. 마무리 점검

1. **정리:** 기준 브랜치 대비 diff 에 `deslop` 스킬을 따른다. 묻지 않고 고치고, 동작은 바꾸지 않는다. 고친 것을 한 줄로 적는다.
2. **검증:** 검증 명령을 새로 돌리고 결과를 보여 준다. 기준선에 없던 실패가 있으면 고친다. 앞서 통과했다는 기억으로 대신하지 않는다.
3. **화면 확인:** 스택 점검이 돌려준 지킬 것에 브라우저 확인이 있고 UI 가 바뀌었으면 한다. 프로젝트에 `verify-*` 스킬이 있으면 그 스킬과 기능 지도를 따른다. 한 일과 본 것을 `Implementation Notes`에 적는다. 도구가 없어 못 하면 멈추지 않는다. "확인 못 함"으로 적고 계속하고, 10단계 메시지에 모은다.
4. **AC 판정:** 구현한 세션이 스스로 판정해 체크하지 않는다. 아래 중 하나가 있는 것만 체크한다.
   - 바깥 증거: 결과를 보여 주는 명령(테스트, grep, CLI)과 그 출력을 `Implementation Notes`에 남겼다.
   - 구현 세션이 아닌 판정자: UI 는 3의 화면 확인, 그 밖은 새 general-purpose 판정 에이전트가 통과라고 했다. 판정 에이전트에는 항목 파일 경로와 `git diff <기준>...HEAD` 범위만 넘기고, 어떻게 구현했는지는 넘기지 않는다. 지시문: "파일을 고치지 않는다. AC 마다 통과 / 실패 / 확인 못 함과 근거(`file:line`, 명령 출력)를 쓴다. 애매하면 통과로 두지 않는다."

   "실패"는 고치고 다시 판정받는다. 같은 AC 가 세 번 고쳐도 실패하면 더 고치지 않고 멈추고, 실패한 AC 와 시도한 것을 알린다. 전제가 틀렸을 수 있다(`principle-attack-the-premise` 스킬). "확인 못 함"은 체크하지 않고 10단계 메시지에 올린다. Definition of Done 도 같은 방식으로 체크하고 커밋한다. 커밋하지 않은 변경을 남기지 않는다.

묻지 않고 7단계로 간다.

## 7. 리뷰 준비

1. **스택 점검:** 쓸 수 있는 스킬 중 이름이 `-end-check`로 끝나는 것을 전부 Skill 도구로 부른다(예: `server:server-end-check`). 각 점검은 변경이 그 영역을 건드렸을 때만 검사 도구를 돌리고 돌려준다.
   - **실패:** 판정을 거치지 않고 9단계의 지적 목록에 🔴 로 넣는다. 검사 도구의 출력이 근거다.
   - **리뷰에 넣을 에이전트:** 8단계에 더한다(근거와 함께).
   - **고친 뒤 할 것:** 9단계에서 한다.
2. **테스트가 고친 것을 증명하나:** 리뷰 전에 이번 브랜치에서 더하거나 바꾼 테스트를 기준 브랜치의 소스에 대고 돌린다. 스크립트가 파일을 잠시 바꾸니 리뷰 에이전트와 함께 돌리지 않는다.
   - 테스트 파일 하나를 돌리는 명령을 프로젝트(CLAUDE.md, package.json 스크립트, 테스트 설정)에서 정하고, 파일 자리를 `{}`로 둔다(예: `pnpm vitest run {}`, `pytest {}`, `bash {}`).
   - `bash <scripts>/base-tests.sh <기준> '<그 명령>'`. 테스트 파일을 이름으로 못 고르는 프로젝트면 파일을 뒤에 붙이고, 이름 규칙 밖의 테스트 도우미(예: `src/testing/`)가 있으면 `BASE_TESTS_KEEP='<경로 정규식>'`을 앞에 붙인다.
   - 출력의 `기준에서도 통과: <파일>`은 판정을 거치지 않고 지적 목록에 🟡 "고친 것을 증명하지 못함. 고친 코드 없이도 통과한다"로 넣는다.
   - 출력이 `바뀐 테스트 없음.`(끝 값 2)이면 이름 규칙 밖의 테스트 파일을 붙여 다시 돌리고, 그런 파일이 없으면 10단계 메시지에 "확인 못 함. 이 브랜치의 테스트를 찾지 못했다"로 올린다.
   - 명령을 정할 수 없거나 그 밖의 이유로 끝 값이 2 면 "확인 못 함"과 이유를, `HEAD 에서 실패: <파일>` 줄은 끝 값과 상관없이 그 테스트를 "확인 못 함"으로 `Implementation Notes`에 적고 넘어간다.
3. 작은데 넓게 닿는 변경이면 `blast-radius` 스킬을 따르고, 찾은 것을 지적 목록에 넣는다.

## 8. 리뷰 (에이전트, 한 메시지에서 동시에)

| 에이전트 | 언제 | 하는 일 |
| --- | --- | --- |
| general-purpose | 항상 | `code-review` 스킬을 부른다. 대상은 현재 브랜치. `--fix`, `--comment` 없이, 노력 수준은 주지 않는다 |
| general-purpose | 인증·인가, 입력 처리, 비밀 값, 외부 호출, 파일·명령 실행이 바뀌었을 때 | `security-review` 스킬을 부른다. 띄우기 전에 `git symbolic-ref refs/remotes/origin/HEAD`가 실패하면 `git remote set-head origin -a` |
| 스택 리뷰 에이전트 (`frontend:frontend-reviewer`, `frontend:design-reviewer`, `server:api-reviewer`, `server:supabase-reviewer`) | 7단계가 돌려줬을 때 | 그 에이전트의 기준대로 |

**모델:** 이 세션이 Fable 이면 위 에이전트 모두에 Agent 도구의 `model`을 한 단계 낮은 최신 모델(지금은 `opus`)로 준다. Opus 이하면 `model`을 주지 않는다.

에이전트는 이 대화를 볼 수 없으니 지시문에 넣는다.

1. 범위: `git diff <기준>...HEAD`, 항목 파일 경로, CLAUDE.md. 스택 리뷰 에이전트에게는 점검이 함께 돌려준 근거도.
2. 파일을 고치지 않고 커밋하지 않는다. 원격·운영 환경에 닿지 않는다. general-purpose 에이전트는 서버를 띄우지 않고 빌드·검증 명령을 돌리지 않는다(리뷰어들이 같은 폴더에서 동시에 돈다). 스택 리뷰 에이전트의 서버 띄우기, 도구 설치, 로컬 재현은 그 에이전트의 기준이 허락할 때만 한다.
3. 원칙: `docs/review-principles.md`가 있으면 그 내용. 원칙에 어긋나 보이는 지적도 보고하되, 어느 원칙과 부딪히는지 함께 적는다.
4. 사용자가 정한 것은 Acceptance Criteria 와 사용자가 답한 것뿐이다. 항목 파일의 `### 정한 것`과 `Implementation Plan`은 Claude 가 정한 것이니 검토 대상이다.
5. 보고: 찾은 문제를 모두, 확인한 것과 확인 못 한 것을 나눠서 `file:line — 문제 — 고칠 방법`. 점수는 쓰지 않는다.
6. 스킬을 부를 수 없으면 대신 지어내지 말고 그렇다고 보고한다.

## 9. 판정하고 고치기

모두 돌아오면 이 세션은 지적을 고르지 않는다. 보고서 원문 전부를 새 general-purpose **판정 에이전트** 하나에 넘긴다. 모델은 이 세션과 같다. 지시문:

- 범위: 8단계의 1과 4, 그리고 `docs/review-principles.md`.
- "파일을 고치지 않는다. 중복을 합치고, 지적마다 코드에서 확인해 타당 / 틀림을 근거(`file:line`)와 함께 판정한다. 원칙에 어긋나는 지적은 틀림이다. 이 변경 전부터 있던 문제는 기존 문제로 따로 센다. 타당한 것은 🔴(확인된 버그, 보안 문제, 데이터 손실, AC 위반, 스택 점검 실패) / 🟡(실제 문제지만 머지를 막지는 않음) / ⚪(사소함)로 나눈다. 타당한 지적 가운데 Acceptance Criteria 나 사용자가 답한 것과 부딪히는 것, 고칠 방법이 제품·취향 결정에 달린 것은 '사람이 정할 것'으로 표시한다. 이번 항목의 범위를 넘는 것은 '나중 후보'로 표시한다. 같은 종류가 `docs/done/` 항목의 Final Summary `리뷰에서 고친 것`에 있거나 이번 보고서들에서 여러 곳에 나오면 🔁 와 근거(항목 번호나 위치들)를 붙인다."

**타당한 🔴·🟡 는 묻지 않고 고친다.** "사람이 정할 것"과 "나중 후보"는 고치지 않고 10단계로 넘긴다. ⚪ 는 고치지 않고 개수만 적는다. 에이전트가 권한, CLAUDE.md, `.claude/` 설정을 바꾸자고 하면 바꾸지 않고 10단계에 제안으로 올린다.

고치는 법:

- 지적을 코드에서 직접 확인한 뒤 고친다. 확인해 보니 틀린 지적은 이유를 적고 고치지 않는다.
- 동작을 바꾸는 수정은 5단계의 테스트 규칙을 따른다.
- 판단이 필요한 수정(설계를 바꾸거나 여러 파일에 걸치는 것, 고칠 방법이 정해지지 않은 것)은 이 세션이 직접 고친다.
- 위치와 고칠 내용을 지적이 정확히 말해 판단이 남지 않는 기계적인 수정은 모아 에이전트 하나(Agent 도구 `model: sonnet`, `effort: high`)에 맡길 수 있다. 맡기면 지시문에 그 지적 목록, 항목 파일 경로, "목록 밖의 것은 고치지 않고 커밋하지 않는다"를 넣는다.
- 고친 뒤 판정은 고친 쪽의 보고로 하지 않는다. 검증 명령을 돌리고, 고친 지적마다 고쳐졌는지는 새 general-purpose 판정 에이전트에 항목 파일 경로, 고친 지적 목록, `git diff HEAD`와 `git status --short`만 넘긴다. 지시문: "파일을 고치지 않는다. 지적마다 고쳐짐 / 안 고쳐짐과 근거(`file:line`)를 쓴다. 애매하면 고쳐짐으로 두지 않는다." UI 는 7단계의 "고친 뒤 할 것"이 판정한다.
- 같은 지적이 세 번 고쳐도 남으면 더 고치지 않고 멈추고, 그 지적과 시도한 것을 알린다.
- 7단계의 "고친 뒤 할 것"을 고친 부분에 대해 한다. 수정이 스택 점검 영역을 건드렸으면 그 `*-end-check`를 다시 부른다.
- 고친 것과 본 것을 `Implementation Notes`에 적고 커밋한다.

## 10. 마지막 메시지 (한 번)

여기서 한 번 멈춘다. 머지는 늘 묻는다. 남은 결정을 모두 이 메시지 하나에 담는다. `git diff <기준>...HEAD -- CLAUDE.md`에서 검증 명령 줄이 바뀌었으면 "이 브랜치가 검증 명령을 바꿨다(이전 → 새). 검증 Stop 훅은 머지 전까지 기준 브랜치의 명령으로 판정한다"도 넣는다.

쓰는 법:

- 첫 줄에 사용자를 기다리는 것이 무엇인지 쓴다.
- 그다음 한 일을 짧게: 무엇이 바뀌었나, AC 별 결과, 리뷰에서 고친 것(🔴·🟡 개수와 한 줄씩), 판정에서 뺀 것 N건, 기존 문제 N건, ⚪ N건.
- 결정마다 추천, 근거, 위험을 붙인다. 답만 읽고 정할 수 있게 쓴다.
  - 사람이 정할 지적: 지적, 고르는 선택지, 추천
  - "나중" 후보: 새 항목으로 만들지. 후보마다 제목과 AC 초안을 붙인다
  - 머지 방식: 로컬 머지 / PR / 그대로 두기. 기준 브랜치를 푸시할지도 함께
  - 권한·설정 변경 제안이 있었으면 그것
- 정한 것 가운데 틀렸을 때 비용이 큰 것과 확인하지 못한 것은 결정이 아니라 알림으로 적는다.
- Claude 가 스스로 할 수 있는 일은 질문으로 올리지 않는다.
- 쉬운 말과 짧은 문장으로 쓴다. 해시, 경로, 명령은 사용자가 행동하는 데 필요할 때만 넣는다.

답을 받으면:

- 사람이 정할 지적은 정한 대로 고치고 9단계의 방법으로 다시 확인한다.
- "나중"으로 고른 후보는 `backlog` 스킬을 `<지적과 근거> --here`로 불러 새 항목을 만든다. AC 초안을 이미 보였으니 다시 승인받지 않는다.
- 애매한 답("괜찮아 보여")은 머지 허락으로 치지 않는다. 머지 방식만 다시 묻는다.

## 11. 검증하고 항목 닫기

1. 검증 명령을 새로 한 번 돌린다. `### Baseline`에 없던 실패가 있으면 멈추고 알린다.
2. 항목의 `Final Summary`를 쓴다: 바뀐 것, 리뷰에서 고친 것, 미룬 것(새 항목 번호), 그대로 둔 지적과 이유, 사용자가 바로잡은 것(한 줄씩).
3. **원칙:** 그대로 둔 이유나 사용자가 바로잡은 것이 다른 항목에도 통하면 `docs/review-principles.md`에 한 줄로 더한다(`- 원칙 — 이유 (항목 번호)`). 같은 원칙이 이미 있으면 더하지 않는다. 글 대신 검사로 막을 수 있으면 그쪽이 낫다(`principle-encode-lessons-in-structure` 스킬).
4. 모두 갖춰야 닫는다. 하나라도 빠지면 멈추고 알린다.
   - [ ] Acceptance Criteria 모두 체크
   - [ ] Definition of Done 모두 체크
   - [ ] `Final Summary`를 썼다
5. 작업 브랜치에서:

```bash
# 항목 파일의 status: Done, updated_date 를 오늘로 바꾼 뒤
git mv docs/backlog/<파일> docs/done/<파일>
git add -A docs/
git commit -m "docs(backlog): <번호> done"
git status --short   # 비어 있어야 한다
```

## 12. 머지

사용자가 10단계에서 고른 방식대로 한다.

- **로컬 머지:**
  - 워크트리에서 일했으면 기준 브랜치는 기준 폴더(`git worktree list`의 첫 줄)에 있다. 머지는 `git -C <기준 폴더> merge …`처럼 거기서 돌린다. 머지 전에 기준 폴더가 기준 브랜치에 있고(`git -C <기준 폴더> branch --show-current`) 깨끗한지(`status --short`) 보고, 아니면 멈추고 알린다.
  - 기준 브랜치에 upstream 이 있으면 먼저 `git pull`로 맞춘다. 없으면 건너뛴다.
  - 충돌이 나면 `fix-merge-conflicts` 스킬을 따른다.
  - 머지한 뒤 기준 브랜치에서 검증 명령을 다시 돌린다. 실패하면 푸시하지 않고 알린다.
  - 세션이 워크트리 안에 있으면 워크트리와 브랜치는 이 세션에서 지우지 않는다. 세션을 보관하면 앱이 워크트리를 정리하고, 그렇지 않으면 기준 폴더에서 `git worktree remove <워크트리 경로>`와 `git branch -d w/<이름>`을 돌리면 된다고 알린다. 워크트리를 쓰지 않았으면 `git branch -d w/<이름>`으로 브랜치를 지운다.
- **PR:** 작업 브랜치를 푸시하고 PR 을 연다. PR 을 만들 수 없으면(CLAUDE.md 에 그렇게 적혀 있거나 `gh auth status`가 실패하면) 그렇다고 말한다. 워크트리는 남긴다.
- **그대로 두기:** 아무것도 하지 않는다. 워크트리와 브랜치를 남긴다.

기준 브랜치와 배포 브랜치는 사용자가 푸시하자고 했을 때만 푸시한다. 강제 푸시하지 않는다.

끝나면 보고한다: 머지된 커밋, 옮긴 항목 파일, 새 항목, 남은 `To Do` 항목(`README.md`와 `_`로 시작하는 파일은 항목이 아니다).
