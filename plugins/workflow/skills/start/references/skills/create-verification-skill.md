# Create a verification skill

> 원문: `cursor/plugins`의 `pstack/skills/create-verification-skill/SKILL.md` (MIT, Lauren Tan). Cursor 이름을 Claude Code 것으로 바꾸고 가져오지 않은 스킬을 가리키는 줄을 뺐다.

**언제:** 프로젝트에 UI, CLI, 서비스의 동작을 증명할 스크립트화된 방법이 없을 때, 또는 "이 저장소의 control 스킬을 만들어 줘" 같은 요청에 쓴다. 사용자가 쓰는 방식대로 앱을 모는 프로젝트 전용 검증 스킬을 만든다. 언어, 프레임워크, 플랫폼을 가리지 않는다.

제대로 된 프로젝트에는 실제 앱을 몰아 동작을 증명하는 스크립트화된 방법이 있어야 한다. 앱을 띄우고, 사용자가 하듯 기능을 써 보고, 증거를 남기는 방법이다. 이 스킬은 그 방법을 저장소에 맞춘 프로젝트 전용 스킬(`.claude/skills/verify-<app>/`)로 만든다. 만든 결과물은 사람이 아니라 다음 에이전트가 읽는다. 그 에이전트는 앱을 본 적이 없고, 일하는 도중에 아무 맥락 없이 읽는다.

## 1. 사용자가 아니라 저장소에 묻는다

아래 질문의 답은 코드베이스에서 찾는다. 볼 수 없는 것만 사용자에게 묻는다.

- **접점(Surface):** 사용자가 실제로 만지는 것은 무엇인가? 웹 UI, CLI/TUI, 데스크톱 앱, API, 모바일 앱, 라이브러리 중 무엇인가? 저장소 하나에 여럿일 수 있다. 주된 것을 고르고 나머지는 적어 둔다.
- **실행(Run):** 앱을 로컬에서 어떻게 띄우나? 저장소가 문서로 밝힌 dev 명령(package scripts, Makefile, README quickstart)을 먼저 쓴다. 포트, 환경 변수, seed 데이터, 인증을 적어 둔다.
- **몰기(Drive):** 에이전트가 앱을 프로그램으로 어떻게 다루나? 이미 있는 harness 가 먼저다. Playwright/Cypress spec, expect 스크립트, PTY helper, curl 로 부를 수 있는 endpoint, debug 포트가 그것이다. 없을 때만 일반 방법을 고른다. 웹과 Electron 은 브라우저/CDP, CLI/TUI 는 tmux/PTY harness, 서비스는 그냥 HTTP 다.
- **관찰(Observe):** 어떤 증거를 남길 수 있나? 스크린샷, 터미널 기록, 응답 본문, 로그, 종료 코드, DB 상태.
- **격리(Isolate):** 인스턴스 둘을 나란히 띄울 수 있나(포트, 데이터 폴더, 프로필)? 없으면 만든 스킬에 그렇게 적는다. 함께 쓰는 인스턴스를 겹쳐 몰기를 거절하는 편이 사용자의 세션을 망가뜨리는 것보다 낫다.

checkout 이 그대로는 빌드되지 않거나 뜨지 않으면 스킬을 만들기 전에 그것부터 고친다(또는 정확히 보고한다). 망가진 바탕 위에 쓴 스킬은 틀린 단계를 가르친다. 상관없는 asset 이 없어서 시작이 막히면(API 가 내보내지 않는 static 폴더, 샘플 config) 만든 스킬이 그것을 만들어도 된다. 검증용 임시물이라고 뚜렷이 표시하고 cleanup 에서 지운다.

## 2. 스킬을 만든다

`.claude/skills/verify-<app>/SKILL.md`를 쓴다. YAML frontmatter 를 넣는다. `name: verify-<app>`과, 앱, 접점, 언제 쓰는지를 밝힌 `description`이다. frontmatter 가 없으면 스킬이 등록되지 않는다. 아래 섹션을 넣고, 섹션마다 1단계에서 실제로 찾은 것에 근거해 쓴다(placeholder 를 남기지 않는다).

- **Launch:** 검증하려고 앱을 띄우는 정확한 명령과, 준비됐는지 아는 방법(로그 한 줄, 프롬프트). Launch 는 빈 데이터 폴더에서 시작해 쓸 수 있는 상태까지 가야 한다. migration 과 seed 데이터도 포함한다. 준비됐다는 것은 쓸 수 있다는 뜻이지 프로세스가 응답한다는 뜻이 아니다. DB health check 는 init 스크립트가 아직 도는 중에도 통과할 수 있다. teardown 을 넣는다. 금방 끝나는 CLI 나 TUI 에는 살려 둘 서버가 없다. 이때 launch 는 바이너리를 한 번 빌드하고(또는 의존성을 설치하고), drive 마다 격리된 PTY 나 tmux 세션에서 따로 시작하는 것이다.
- **Doctor:** "이 인스턴스는 몰 만한가?"에 답하는 읽기 전용 확인 하나. 프로세스가 떠 있는지, 버전과 빌드가 맞는지, 포트를 우리가 쥐고 있는지, 인증이 유효한지 본다. 무언가 이상해 보이면 에이전트가 이것부터 돌린다.
- **Drive:** 예시가 아니라 이 저장소의 실제 selector 와 명령으로 쓴 harness 사용법. 좌표나 탭 순서보다 안정된 손잡이(ARIA label, data attribute, 프롬프트 문자열, route 경로)를 쓴다.
- **Evidence:** 증명하려면 무엇을 남기고 어디에 두는지. 증명 기준을 적는다. 내부 setter 나 테스트 전용 endpoint 가 아니라 실제 사용자 경로를 쓴다. 마지막 화면만이 아니라 동작과 그 결과 상태를 남긴다. 보이는 것과 함께 부수 효과(쓰인 파일, 들어간 행, 보낸 메시지)를 확인한다. mock 은 운영 경계가 이미 외부 시스템을 떼어 놓은 곳에만 쓴다. 안전한 경로가 dry-run 이나 test mode 면, 이름을 믿지 말고 실제로 무엇을 건너뛰는지 관찰(파일, 네트워크, git ref)로 확인한다. 어떤 dry-run 은 네트워크를 건드리거나 브라우저를 연다.
- **Cleanup:** 이번 실행이 만든 인스턴스를 내리는 방법. 프로세스 이름으로 죽이지 않는다. 자기가 띄운 것만 죽인다. Cleanup 은 인스턴스와 임시 상태를 지우고 증거는 지우지 않는다. 증거 산출물은 스킬이 밝힌 위치에 teardown 뒤에도 남는다.
- **Helpers:** 스킬에 딸린 스크립트는 모두 실행 가능하고, 부르는 방법이 스킬 본문에 나와 있다. 읽는 쪽이 뜯어봐야 쓸 수 있는 helper 는 helper 가 아니다.

## 3. 기능 지도의 첫 내용을 넣는다

`.claude/skills/verify-<app>/features/README.md`와, 찾을 수 있는 사용자 기능마다 파일 하나를 만든다(처음에는 route, 명령, 메뉴, 문서에서 찾은 상위 3~5개를 노린다). `skills/feature-map-example/`의 모양을 따른다. README 색인 하나와 기능마다 파일 하나다. 파일마다 사용자 관점에서 네 가지에 답한다. 기능이 무엇인지, 어떻게 거기에 가는지, harness 로 어떻게 모는지, 어떤 관찰 가능한 끝 상태가 동작을 증명하는지다. H2 넷은 `Sub-features`, `How to get to it (user POV)`, `Driving it with <harness>`, `Gotchas`다. seed 데이터에 journey 가 필요로 하는 전제 조건이 없으면 journey 는 실패를 보고하고, 그 까닭은 그 기능의 `Gotchas`에 적는다. 통과시키려고 journey 를 약하게 만들지 않는다. 지도는 저장소가 관리하는 검증의 원본이다. 지도에 다른 진입점이 있는데 편한 진입점 하나만 몬 증명은 덜 된 것이다.

## 4. 넘기기 전에 만든 스킬을 증명한다

만든 스킬의 지시를 처음부터 끝까지 한 번 돌린다. launch, doctor, 지도에 있는 기능 하나의 drive(하나면 된다. 나머지는 나중 실행이 다루라고 지도가 있다), 증거 남기기, cleanup 순이다. cleanup 뒤에 증거가 밝힌 위치에 그대로 있는지 확인한다. 증거를 지우는 cleanup 은 이 단계에서 실패다. 실패한 것을 고치고, 실패한 시도 뒤에도 매번 만든 cleanup 을 돌려 망가진 시도가 프로세스와 포트를 남기지 않게 한다. 한 번도 실행하지 않은 스킬은 초안이지 결과물이 아니다. 실제 대상의 대역(새 VM 대신 컨테이너, 원격 스택 대신 로컬 스택)에서 증명했으면, 대역이 해 줬지만 실제 대상은 하지 않을 준비 단계를 모두 적는다. 그 단계들은 실제 대상에서 돌려 확인할 때까지 검증되지 않은 것이다.

## 5. 유지 절차를 알려 준다

앱이 바뀌어도 지도가 사실과 맞도록 `skills/maintain-verification-skill.md`를 사용자에게 알려 준다. 주기는 사용자가 물을 때만 제안한다.
