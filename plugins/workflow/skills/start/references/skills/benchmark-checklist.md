# Benchmark checklist

> 원문: `cursor/plugins`의 `pstack/skills/benchmark-checklist/SKILL.md` (MIT, Lauren Tan). Cursor 이름을 Claude Code 것으로 바꾸고 가져오지 않은 스킬을 가리키는 줄을 뺐다.

**언제:** 벤치마크를 돌리거나, 직접 잰 속도 향상이나 회귀를 보고할 때 쓴다. 성능 측정값을 보고하거나 그 값을 근거로 움직이기 전에 제한 요인, 튜닝, 한계, 오류, 반복성, 관련성, 일이 실제로 일어났는지를 따진다.

성능 숫자를 낼 때 쓴다. PR 의 전후 비교, 회귀 주장, hillclimb harness, 라이브러리나 설정 선택이 그런 때다. 질문마다 코드를 보고 한 짐작이 아니라 실행에서 나온 증거로 답한다.

사용자가 대략의 값만 물었으면 한 번 돌리면 된다. 그래도 질문 4와 7은 확인하고, 한 번 돌린 값이라고 말한다. 그 실행이 이상해 보이지 않으면 나머지는 건너뛴다. 여러 안 중에서 고르는 일은 대략의 값으로 하지 않는다.

## 돌리기 전에

- 하려는 주장을 내보낼 말 그대로 적는다("60k 행 데이터셋에서 export 가 p50 기준 30% 빠르다"). 아래 질문은 그 문장을 시험한다.
- 측정 스크립트를 읽는다. 무엇을 재고, 무엇을 세고, 무엇을 무시하는지 적어 둔다.
- `uptime`으로 load average 를, `nproc`으로 코어 수를 확인한다. 기계가 바쁘면 무엇이 돌고 있는지 찾는다. 멈출 수 없으면 두 쪽을 번갈아 돌려 같은 잡음을 겪게 하고, 보고에 그렇게 했다고 적는다.

## 질문

1. **왜 두 배가 아닌가?** 제한 요인(limiter)의 이름을 댄다. 프로파일은 보고하지 않을 실행에서 한다. 프로파일러와 트레이서가 일을 느리게 하기 때문이다. 프로세스별 CPU(`top`, `pidstat`), 런타임 프로파일러(`node --cpu-prof`, `py-spy`, `perf`), I/O 대기, syscall 수(Linux 의 `strace -c`)를 쓰고, 시간이 몰리는 곳을 소스에서 짚는다. 부하 생성기도 본다. 부하 생성기가 먼저 포화하면 잰 것은 부하 생성기다. 변경이 숫자를 움직이지 않았으면 제한 요인이 그 까닭을 설명한다. 그러니 변경이 쓸모없다고 말하기 전에 제한 요인을 찾는다.
2. **튜닝했나?** 모든 쪽을 운영에서 도는 방식대로 돌린다. release 빌드, 운영 플래그와 환경 변수, 배치와 트랜잭션 설정, 커넥션 풀, 운영이 겪는 만큼 데워졌거나 식은 캐시, 같은 버전과 데이터를 쓴다. 한쪽이 기본값으로 돌면 구현이 아니라 설정을 비교한 것이다. 제한 요인이 설정(행마다 커밋, debug 빌드, 빠진 인덱스)이면 그쪽은 튜닝되지 않은 것이다. 이긴 쪽을 고르기 전에 튜닝하고 다시 잰다. 튜닝할 수 없으면 그 실행으로 이긴 쪽을 고르지 않는다. 사용자가 무엇을 도입할지 고르는 중이면, 주장을 오늘 배포된 코드로 좁혀도 해결되지 않는다. 사용자가 도입하는 것은 그 안이지 오늘의 설정이 아니기 때문이다.
3. **한계를 넘었나?** 셈을 한다. 초당 바이트를 디스크와 네트워크 대역폭과 견준다. 초당 연산 수에 연산당 비용을 곱한 값을 코어 수와 견준다. 줄어든 시간을 바뀐 부분이 쓰던 시간과 견준다. 실행의 10%를 쓰던 부분을 없애면 실행은 많아야 약 11% 빨라진다. 한계를 넘은 결과는 그 일이 아닌 다른 것을 잰 것이다. 캐시, no-op, 버그 같은 것이다.
4. **오류가 났나?** 실패와 성공이 아닌 응답을 센다. 출력이 있는지만 보지 말고 맞는지 확인한다. 거절은 흔히 빠르고, timeout 과 재시도는 느리다. 스크립트가 오류를 세지 않으면 세게 고친다.
5. **재현되나?** 쪽마다 5번 이상, 번갈아(A, B, A, B 순으로) 돌린다. warmup, 지연 초기화, 캐시, drift 가 어느 쪽도 편들지 않게 하려는 것이다. 중앙값과 범위를 보고한다. 실행 사이의 변동보다 작은 차이는 잴 수 있는 차이가 없는 것이다. 판정이 아슬아슬하면 rank-sum test 나 harness 자체의 통계를 쓴다.
6. **중요한가?** micro 결과 옆에는 사용자가 기다리는 end-to-end 경로를 실제와 같은 데이터 크기와 동시성으로 재서 둔다. micro 결과는 전체에서 차지하는 몫으로 보고한다. 요청의 1%를 쓰는 helper 는 아무리 빨라져도 요청을 많아야 1% 빠르게 한다.
7. **일이 일어나기는 했나?** 재는 구간 안에서 일이 돌았는지 확인한다. 요청이 서버에 닿았는지, 행이 쓰였는지, 바이트가 읽혔는지, 코드가 결과를 썼는지 본다. 게으른 코드(아무도 순회하지 않는 generator, 아무도 await 하지 않는 promise, JIT 이 버릴 수 있는 결과)와 timeout 은 일어나지 않은 일의 숫자를 만든다.

## 보고

- 판정부터 쓴다. 빠르다, 느리다, 잴 수 있는 차이 없음, 결론 못 냄 중 하나다.
- 숫자에 단위, 실행 횟수, 범위, 제한 요인을 붙인다. 예: "p50 41 ms → 33 ms, 쪽마다 7번 돌린 중앙값, 바꾼 뒤 범위 32~35 ms, 한 코어의 JSON 파싱에 묶임."
- 차이를 주장하지만 제한 요인의 이름을 대지 못할 때, 한쪽이 튜닝 없이 돌았을 때, 질문 4와 7을 확인하지 못했을 때는 판정을 결론 못 냄으로 한다. 무엇이 빠졌는지 적는다.
- PR 본문에는 대표 숫자 하나만 둔다. 실행 기록, 범위, 제한 요인의 증거는 링크한 산출물이나 노트 파일에 둔다.

## 다른 성능 자료

- `playbooks/perf-issue.md`의 baseline 은 플레이북이 그 값으로 계획하기 전에 이 목록으로 따진다. 그 뒤의 숫자도 모두 따진다.
- `playbooks/hillclimb.md`의 harness 는 고정하기 전에 따진다. 고정한 harness 는 오류 수와 한 일의 수를 출력한다. 그래서 유지할지 되돌릴지 정할 때마다 질문 4와 7이 저절로 확인된다.
