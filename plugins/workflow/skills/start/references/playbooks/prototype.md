# Prototype

> 원문: `cursor/plugins`의 `pstack/skills/poteto-mode/playbooks/prototype.md` (MIT, Lauren Tan). Cursor 이름을 Claude Code 것으로 바꾸고 가져오지 않은 스킬을 가리키는 줄을 뺐다.

**언제:** 돌려 보면 정해지는 갈림길이나 화면·상호작용 결정. 묻지 않고 프로토타입을 만들어 정한다.

**내가 책임지는 것은 설계 결정이지 코드가 아니다. 프로토타입은 쓰고 버리는 도구다. 진짜 구현은 `start` 절차의 기본 흐름을 따른다.**

Laziness Protocol(`principles/laziness-protocol.md`)의 "가장 작은 변경"과 검증 기준이 뒤집히는 플레이북은 이것 하나다. 다듬기보다 속도가 먼저고, 코드 품질은 중요하지 않고, 계획도 하지 않는다. 엄밀함은 맞는 설계를 값싸게 고르는 데 쓴다. 사용자가 요청하지 않은 변형도 제안하고, 한 접근을 버리고 다른 접근을 해 본다.

1. 프로토타입이 내려야 할 결정의 범위를 정한다. 어느 배치인지, 어느 상호작용인지, 어느 밀도인지를 정하고, 돌려 봐야 아는 갈림길이면 어느 동작, 타이밍, 접근인지를 정한다. 결정할 것이 없으면 프로토타입도 없다. `start` 절차의 기본 흐름으로 간다.
2. 설계 공간이 열려 있으면 참고 자료를 모은다. 선례를 찾고, 주제, 팔레트, 배치를 무드보드로 요약하고, 만들기 전에 사용자가 방향을 고르게 한다. 방향이 정해져 있으면 건너뛴다.
3. 프로덕션 소스와 떨어진 격리된 임시 폴더에 버릴 것으로 만든다. 시각 결정이면 바닐라 HTML/CSS/JS 나 그 아이디어를 그려 낼 가장 가벼운 스택, CDN 의존성, 핫 리로드가 되는 개발 서버를 쓴다. 동작이나 타이밍 결정이면 그 질문을 돌려 보는 가장 작은 스크립트를 쓴다. 프로덕션 프레임워크, 테스트, 추상화는 쓰지 않는다.
4. 대안을 비교할 때는 전환기 하나(버튼이나 키 입력) 뒤에 모아 만들고 변형마다 이름표를 붙인다. `principles/exhaust-the-design-space.md`를 값싸게 하는 방법이다.
5. 맞는 표면에서 검증한다. 시각 결정이면 `skills/control-ui.md`로 변형마다 스크린숏을 찍고 상호작용을 직접 해 본다. 동작이나 타이밍 결정이면 타이밍을 로그로 남기거나, 출력을 찍거나, 렌더링을 지켜봐서 정하려는 그것을 관찰한다. 여기서는 단언이 아니라 관찰이 테스트다.
6. 대안, 장단점, 추천을 보여 준다. 산출물은 결정과 버릴 결과물이지, 내보낼 코드가 아니다. 고른 방향은 진짜 구현을 하도록 `start` 절차의 기본 흐름에 넘긴다(모양은 `skills/architect.md`에 넘긴다).

**보고:** 살펴본 변형, 증거(시각 결정이면 스크린숏, 동작 결정이면 관찰한 출력이나 타이밍), 장단점, 추천, 임시 폴더 경로. 프로토타입은 버릴 것이라고 분명히 말한다.
