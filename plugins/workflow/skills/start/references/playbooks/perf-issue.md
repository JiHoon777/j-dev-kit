# Perf issue

> 원문: `cursor/plugins`의 `pstack/skills/poteto-mode/playbooks/perf-issue.md` (MIT, Lauren Tan). Cursor 이름을 Claude Code 것으로 바꾸고 가져오지 않은 스킬을 가리키는 줄을 뺐다.

**언제:** 잰 숫자가 있는 성능 문제. 수정은 모두 측정에 묶는다.

**측정 이야기의 주인은 나다. 계획하고, 리뷰하고, 숫자를 검증한다.** 수정은 모두 측정에 묶는다. 재는 대신 소스를 읽지 않는다.

1. `skills/control-ui.md`와 `skills/control-cli.md` 중 표면에 맞는 것으로 기준선 트레이스를 뜬다. 기준선과 그 뒤의 숫자 하나하나를 `skills/benchmark-checklist.md`로 따져 본다.
2. 코드를 추적해 가설의 근거를 댄다. 돌려 보지 않고 성능 한계를 주장하지 않는다.
   성능 주문(mantra)을 값싼 것부터 순서대로 해 본다.
   1. 하지 않는다. 결과를 아무도 쓰지 않는 일은 싸게 만들지 말고 멈춘다.
   2. 하되 다시 하지 않는다.
   3. 덜 한다.
   4. 나중에 한다.
   5. 보고 있지 않을 때 한다.
   6. 동시에 한다.
   7. 더 싸게 한다.

   앞선 주문으로 목표에 닿으면 멈춘다.
3. 트레이스를 바탕으로 수정을 계획한다. 함수 경계를 넘으면 `skills/architect.md`를 먼저 한다. 구현은 하위 에이전트에 맡긴다. diff 를 리뷰한다. 수정 뒤 트레이스를 뜬다.
   `principles/sequence-verifiable-units.md`를 적용해, 시도 하나를 검증한 뒤에 다음을 해 본다.
4. 결과물을 파싱해 비교한다(JSON 을 sqlite 로, diff). "결론 없음"이나 다른 표면에서 한 확인은 통과가 아니다. 그렇다고 알린다.
5. 측정값을 커밋 메시지에 적는다. 프로젝트가 PR 을 쓰면 PR 에도 적는다.
6. `start` 절차의 마무리로 간다.

한 번 고치고 끝나는 일이 아니라 한 수치를 꾸준히 끌어올리는 일이면 `playbooks/hillclimb.md`를 쓴다.

**보고:** 기준선 숫자, 수정 뒤 숫자, 차이, 결과물 경로.
