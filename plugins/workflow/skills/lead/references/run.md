# lead run: 작업 세션을 띄우고 지휘하기

항목 만들기, 구현, 리뷰와 머지는 `/task`의 절차 파일을 그대로 따른다. 이 모드가 더하는 것은 나누기와, 작업 세션이 사용자에게 물을 것을 대신 받아 올리는 일뿐이다.

| 일 | 따르는 절차 | 누가 |
| --- | --- | --- |
| 항목 만들기 | `${CLAUDE_SKILL_DIR}/../task/references/create.md` | 상위 세션 |
| 계획과 구현 | `${CLAUDE_SKILL_DIR}/../task/references/start.md` | 작업 세션 |
| 리뷰, 고치기, 항목 닫기 | `${CLAUDE_SKILL_DIR}/../task/references/end.md` 1~6단계 | 작업 세션 |
| 마무리(머지) | 같은 `end.md` 7단계 | 상위 세션 |

`/task`는 사용자만 부를 수 있어 Skill 도구로 부르지 않는다. 절차 파일을 Read 도구로 끝까지 읽고 따른다.

돌릴 항목: `run` 뒤의 번호들. 없으면 3단계에서 고른다.

## 1. 상태 읽기

- `docs/backlog/`의 항목(`README.md`와 `_`로 시작하는 파일은 항목이 아니다)과 각 항목의 `status`, `dependencies`
- `docs/backlog/_proposals.md`(없으면 건너뛴다)
- "현재 상태"의 작업 브랜치와 워크트리: 이미 돌고 있거나 멈춰 있는 작업

기준 브랜치가 아니거나 커밋하지 않은 변경(제안함 파일은 뺀다)이 있으면 멈추고 알린다.

## 2. 제안 승격

제안함에 제안이 있으면 한 번에 보여 주고 묻는다: 승격 / 기각 / 그대로 둠.

- **승격:** `create.md`를 읽고 그대로 따라 항목을 만든다. 만들 것은 그 제안의 제목과 근거다. 만든 뒤 제안함에서 그 줄을 지운다.
- **기각:** 제안함의 `## 기각`에 제목, 날짜, 이유를 적고 원래 줄을 지운다.
- 사용자가 승격하지 않은 제안으로는 작업을 시작하지 않는다.

## 3. 나누기

- 후보: `status: To Do`이고 `dependencies`가 모두 `docs/done/`에 있는 항목. `In Progress`인데 돌고 있는 세션이 없는 항목은 이어 갈지 묻는다.
- 한 번에 "동시 작업 세션" 수까지 고른다. 무엇을 함께 돌릴지는 직접 판단한다. 같은 곳을 고치는 항목을 함께 돌려도 된다. 충돌은 6단계에서 푼다.
- 고른 항목을 번호와 제목으로 한 줄씩 보여 주고 바로 시작한다.

## 4. 작업 세션 띄우기

항목 하나에 세션 하나. 기준 브랜치에서 갈라진 자기 워크트리에서 돌게 한다.

- 세션을 새로 시작하는 도구가 있으면 그것을 쓴다(사용자가 열어 보고 직접 말할 수 있다).
- 없으면 워크트리로 격리한 백그라운드 서브에이전트를 쓴다. 서브에이전트에는 Stop 훅(Definition of Done 을 체크하면 검증 명령을 돌리는 훅)이 돌지 않는다. 그 검증은 작업 세션이 절차대로 돌리는 검증(start 6단계, end 6단계)과 6단계의 머지 전후 검증이 덮는다.

작업 세션은 이 대화를 볼 수 없으니 지시문에 넣는다:

1. 항목 파일 경로, 기준 브랜치, 검증 명령, 문서 언어.
2. `start.md`와 `end.md`의 절대 경로. `start.md`를 끝까지 읽고 그대로 따르고, 끝나면 `end.md`를 끝까지 읽고 1~6단계를 그대로 따른다. 달라지는 것은 아래 넷뿐이다.
3. **사용자에게 묻거나 승인을 받으라는 곳**(start 의 질문과 계획 승인, end 4단계의 지적 결정, 멈추고 알리라는 곳)에서는 직접 묻지 않는다. 물을 내용을 보고하고 멈춘다. 답은 상위 세션이 사용자의 말을 전한다. 계획은 플랜 모드 대신 보고로 올리고, 승인을 받으면 start 4단계부터 한다.
4. **브랜치 확인:** 이 세션은 기준 브랜치에서 막 갈라진 자기 워크트리다. start 1단계의 브랜치 확인은 건너뛴다. 다른 `w/` 브랜치는 다른 작업 세션의 것이니 건드리지 않는다.
5. **새 항목:** 절차가 새 백로그 항목을 만들라는 곳에서는 만들지 않고 보고에 적는다(번호가 다른 세션과 겹친다).
6. **머지:** end 7단계는 하지 않는다. 푸시하지 않는다.
7. **보고 형식:** 첫 줄에 상태(`계획 승인 대기` / `질문` / `리뷰 결정 대기` / `막힘` / `머지 준비`)와 항목 번호. 이어서 브랜치 이름, 물을 내용이나 한 일 몇 줄, 확인하지 못한 것.

## 5. 보고를 확인하고 올리기

보고는 그 세션의 주장이다. 올리기 전에 직접 본다.

| 상태 | 확인할 것 | 사용자에게 |
| --- | --- | --- |
| 계획 승인 대기 | 계획이 start 3단계가 요구한 것을 담았고, 항목의 Acceptance Criteria 를 다 덮고 그 밖의 일을 넣지 않았는지 | 계획 요약, 승인 / 고칠 점 |
| 질문·막힘 | 코드와 문서로 답할 수 있으면 직접 답해 돌려보낸다 | 답할 수 없는 것만, 바로 |
| 리뷰 결정 대기 | 지적이 end 4단계 형식(🔴 / 🟡 / ⚪)인지, 🔴 가 코드에서 맞는지 | end 4단계의 질문 그대로 |
| 머지 준비 | `git diff --stat <기준>...<브랜치>`, 항목 파일이 `docs/done/`에 있고 AC·DoD 가 체크됐는지, `Final Summary`, 검증 결과 | 6단계 |

- 같은 때 온 것은 묶어서 한 번에 올린다. 질문과 막힘은 기다리지 않고 올린다.
- 사용자의 답은 그 말을 그대로 인용해 해당 세션에 전한다. 답이 없으면 기다린다.
  - 백그라운드 서브에이전트로 띄운 작업 세션은 보고하고 멈춰 있다. 새로 띄우지 않고, 띄울 때 받은 에이전트 ID 로 같은 에이전트에 이어서 보낸다(SendMessage). 그래야 읽은 것과 한 일을 이어 간다.
- 보고가 실제와 다르면 사용자에게 올리지 않고 무엇이 다른지 적어 돌려보낸다.
- 작업 세션이 보고한 "새 항목"은 사용자에게 보여 주고, 만들기로 하면 `create.md`대로 만든다.

## 6. 마무리 (한 번에 하나)

머지 준비가 된 브랜치마다 `end.md` 7단계를 상위 세션이 한다. 그 단계가 사용자에게 받는 답이 머지 승인이다.

- 7단계가 부르는 스킬에 더 알려 준다: 마무리할 브랜치는 `w/<항목 파일 이름>`이고 작업 세션의 워크트리에 있다. 상위 세션은 기준 브랜치에 있다.
- **머지 전에:** 작업 세션의 워크트리에서 작업 브랜치에 최신 기준 브랜치를 반영하고(`git merge <기준>`) 검증 명령을 돌린다. 앞서 머지한 항목과 겹치는 것(같은 버전으로 올린 것 등)이 여기서 드러난다. 실패하면 머지하지 않고 출력과 함께 그 작업 세션에 돌려보낸다.
- 한 번에 브랜치 하나만 마무리한다. 하나가 끝난 뒤 다음으로 간다.
- 충돌이 나면 두 항목의 의도를 보고 푼다. 어느 쪽을 살릴지 판단할 수 없으면 멈추고 묻는다.
- 머지할 때마다 검증 명령을 새로 돌린다. 실패하면 다음 머지를 멈추고 알린다. 스스로 되돌리지 않는다.
- 머지한 항목의 작업 세션과 워크트리를 정리하자고 제안한다.

## 7. 다음

- 자리가 났고 후보가 남았으면 3단계로 돌아간다.
- 끝나면 보고한다: 머지한 항목, 승인을 기다리는 것, 멈춘 것, 남은 `To Do` 항목.
