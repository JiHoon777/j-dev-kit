# task start: 항목 하나 계획하고 구현하기

백로그 항목 **하나**를 계획하고, 승인을 받고, 구현한다. 리뷰와 머지는 `/task end`가 한다.

요청한 항목: `start` 뒤의 인자.

명령은 모두 저장소 루트(`git rev-parse --show-toplevel`)에서 돌린다. 워크트리에서 일하면 그 워크트리의 루트다.

## 1. 시작할 수 있는지

`git branch --show-current`, `git status --short`, `git branch --list 'w/*'`, `git log --oneline <기준>..HEAD`로 상태를 본다. 하나라도 해당하면 멈추고 알린다. 스스로 정리하지 않는다.

| 확인 | 해당하면 |
| --- | --- |
| 기준 브랜치에 커밋이 없다 | 첫 커밋이 필요하다고 말한다 |
| 커밋하지 않은 변경이 있다 | 보여 주고 어떻게 할지 묻는다 |
| 현재 브랜치가 기준 브랜치가 아니다 | 이 항목을 위해 막 딴 워크트리(하위 세션)면 그대로 진행한다: 워크트리 안이고(`git rev-parse --path-format=absolute --git-dir --git-common-dir`의 두 줄이 다르면) 브랜치에 기준 브랜치 이후 커밋이 없다. 이름이 `w/<이름>`이 아니면(앱이 앞에 붙이는 말 등) 4단계에서 바꾼다. 그 밖이면 이어 갈지, `/task end`로 끝낼지, 버릴지 묻는다. 이어 가면 항목의 `Implementation Plan`을 읽고 5단계부터 |
| 이 항목의 `w/` 브랜치가 이미 있고 지금 그 브랜치가 아니다 | 그 브랜치에서 일하던 세션이 있으면 거기서 이어 가라고 알린다. 그 세션이 없으면 여기서 이어 간다: 그 브랜치가 다른 워크트리에 있으면(`git worktree list`) `EnterWorktree`에 그 경로를 줘서 옮기고(도구가 없거나 거부하면 이후 명령을 그 폴더에서 돌린다), 없으면 `git switch w/<이름>`. 그다음 항목의 `Implementation Plan`을 읽고 5단계부터. 다른 항목의 `w/` 브랜치는 다른 세션의 것이니 건드리지 않는다 |

항목 찾기: 인자를 `docs/backlog/`에서 찾는다(`README.md`와 `_`로 시작하는 파일은 항목이 아니다). 없거나 여럿이면 `To Do` 항목을 번호와 제목으로 보여 주고 고르게 한다. 항목 파일을 끝까지 읽고, `dependencies`가 모두 `docs/done/`에 있는지 확인한다.

## 2. 기준선과 스택 점검

0. **워크트리 준비:** 워크트리면(`git rev-parse --path-format=absolute --git-dir --git-common-dir`의 두 줄이 다르면):
   - 프로젝트에 의존성 설치가 필요하면(예: `package.json`과 잠금 파일) 기준선보다 먼저 설치한다. 새 워크트리에는 설치된 것이 없어, 설치 전에 잰 기준선은 진짜 실패를 가린다.
   - 워크트리가 기준 폴더 안에 있고(예: `.claude/worktrees/`) 테스트·린트·타입 검사 도구가 그 폴더까지 읽으면(git 의 무시 목록을 보지 않는 도구가 많다) 기준 폴더의 검증이 다른 항목의 코드까지 돈다. 그 도구 설정에서 빠져 있지 않으면 알린다.
1. **기준선:** 검증 명령을 한 번 돌린다. 이미 실패하는 것(명령, 실패한 테스트·파일 이름)만 적어 둔다. 작업을 막지는 않고 사용자에게 알린다. `/task end`가 이것과 비교해 새 실패만 본다.
2. **스택 점검:** 쓸 수 있는 스킬 중 이름이 `-start-check`로 끝나는 것을 전부 Skill 도구로 부른다(예: `server:server-start-check`). 해당하지 않는 점검은 "해당 없음"만 돌려준다. 돌려받는 것:
   - **지킬 것:** 구현 중 따를 규칙과 부를 스킬
   - **계획 전에 할 것:** 계획에 앞서 끝낼 일(예: 시안). 3단계로 가기 전에 한다
   - **플랜에 넣을 것:** 이 항목에 해당할 때만
   - **물을 것:** 판단할 수 없는 것이 있을 때만

## 3. 계획 (플랜 모드)

`EnterPlanMode`로 들어간다. 이 단계에서는 파일을 고치지 않는다. 지시문이 질문과 승인 요청을 마지막 메시지에 쓰라고 하면(띄운 세션이 지휘할 때) 플랜 모드 도구는 쓰지 않고, 계획 전문을 마지막 메시지에 쓰고 멈춘다.

**크기에 맞춘다.**

- **작은 항목**(파일 몇 개, 새 구조 없음): 에이전트 없이 관련 코드를 직접 읽는다.
- **큰 항목**(여러 모듈, 새 구조): `Explore` 에이전트를 서로 다른 영역으로 한 메시지에서 띄운다. 비슷한 기존 기능과 이어지는 코드를 따라가 꼭 읽을 파일을 돌려받고, 그 파일을 직접 읽는다.

**도구와 단계:** 설계 전에 이 항목의 일이 어느 분야의 일이고, 그 분야 최고 실무자는 어떤 도구(이름, 명령)와 단계로 하는지 정한다. 역할을 상정하지 말고 도구와 단계를 적는다. 모르면 문서나 웹에서 찾는다. 설치되지 않은 도구도 고를 수 있고, 그러면 설치를 계획에 넣는다. 스택 점검이 준 도구는 그대로 쓰고 모자란 것만 더한다.

**질문:** 코드와 문서로 답할 수 없고 계획을 바꾸는 것만, 스택 점검의 "물을 것"과 합쳐 한꺼번에 묻는다. 나머지는 합리적으로 정하고 계획에 가정으로 적는다. 답을 받기 전에는 계획을 확정하지 않는다.

**설계:** 직접 정한다. 정말 갈리는 선택(구조, 라이브러리, 데이터 모델)이 있을 때만 두 안의 차이와 추천을 보여 준다.

**계획(`ExitPlanMode`)에 넣을 것:**

1. 무엇을 하나: 한두 문장, 이번에 빼는 것
2. 도구와 단계: 분야, 그 분야 최고 실무자의 도구와 단계, 설치할 것
3. 바꿀 파일과 각각의 일, 먼저 쓸 테스트, 순서
4. 성공 기준: Acceptance Criteria 마다 어떻게 확인하나(명령, 화면, 판정 에이전트)
5. 스택 점검의 "플랜에 넣을 것"
6. 가정과 정한 것

승인 전에는 파일을 고치지 않고 브랜치도 만들지 않는다.

## 4. 기록

1. 작업 브랜치 `w/<.md 를 뺀 항목 파일 이름>`(아래 `<이름>`)을 둔다.
   - 기준 브랜치에 있으면 `git switch -c w/<이름>`.
   - 이 항목을 위해 딴 워크트리에 있고 브랜치 이름이 다르면 `git branch -m w/<이름>`. 검증 Stop 훅이 `w/` 브랜치에서만 돈다.
   - 웹 포트나 서버 포트가 설정돼 있으면 항목 포트를 `기준 포트 + 항목 번호`로 정한다(예: 웹 5000, 항목 007 → 5007). 적은 것만 정한다.
     - 다음 포트는 쓰이는 것으로 보고 1씩 올려 피한다: 지금 듣고 있는 포트(`lsof -nP -iTCP:<포트> -sTCP:LISTEN`, 없거나 실패하면 `nc -z 127.0.0.1 <포트>`), 다른 세션에서 진행 중인 항목(`docs/backlog/`의 `In Progress`)의 `### 포트`, 그리고 그 항목들의 기본 포트(기준 포트 + 그 번호). 다른 항목과 다른 프로젝트의 서버와 겹치지 않게 하려는 것이다. 듣는지 확인할 방법이 없으면 그렇다고 알린다.
     - 정하자마자 항목 파일에 적는다(아래 2). 동시에 시작한 다른 세션이 볼 수 있게 하려는 것이다.
2. 항목 파일: `status: In Progress`, `updated_date` 오늘, 승인된 계획을 `Implementation Plan`에, 기준선을 `Implementation Notes`의 `### Baseline` 아래에, 정한 포트를 `### 포트` 아래에(`- 웹: 5007`처럼 한 줄씩).
3. 커밋: `chore(backlog): <번호> start`

## 5. 구현

- `superpowers:test-driven-development` 스킬을 부르고 따른다.
- 계획의 **도구와 단계**를 따른다. 바꾸면 `Implementation Notes`에 적는다.
- 스택 점검의 **지킬 것**을 따른다.
- 통과시키려고 기존 테스트를 지우거나 약하게 고치지 않는다. 테스트가 틀렸다고 보면 멈추고 묻는다.
- Acceptance Criteria 에 있는 것만 한다. 주변 코드를 다듬거나 리팩터링하지 않는다. 필요해 보이는 다른 일은 알리고, 동의하면 `task` 스킬을 `create <그 일> --here`로 불러 따로 항목을 만든다.
- AC 를 하나 끝내면 6단계 4의 방식으로 확인되는 대로 체크한다. 계획에서 바뀐 것은 `Implementation Notes`에 적는다. 범위가 커지면 멈추고 묻는다.
- 의미 있는 단계마다 작업 브랜치에 커밋한다. 기준 브랜치에 커밋하지 않고 푸시하지 않는다.

## 6. 마무리

1. **정리:** 변경이 작지 않으면 `simplify` 스킬을 한 번 부른다. 이 스킬은 바뀐 코드에서 재사용·단순화할 곳을 찾아 직접 고친다. 동작을 바꾸는 수정은 되돌린다. 무엇을 정리했는지 한 줄로 적는다.
2. **검증:** `superpowers:verification-before-completion` 스킬을 부르고 따른다. 검증 명령을 새로 돌리고 결과를 보여 준다. 기준선에 없던 실패가 있으면 고친다.
3. **브라우저 확인:** 스택 점검이 돌려준 지킬 것에 브라우저 확인이 있고 UI 가 바뀌었으면 한다. 도구가 없으면 건너뛰지 말고 멈춰서 알린다. 한 일과 본 것을 `Implementation Notes`에 적는다.
4. **AC 판정:** 구현한 세션이 스스로 판정해 체크하지 않는다. 아래 중 하나가 있는 것만 체크한다.
   - 바깥 증거: 결과를 보여 주는 명령(테스트, grep, CLI)과 그 출력을 `Implementation Notes`에 남겼다.
   - 구현 세션이 아닌 판정자: UI 는 3의 `frontend:frontend-evaluator`, 그 밖은 새 general-purpose 판정 에이전트가 통과라고 했다. 판정 에이전트에는 항목 파일 경로와 `git diff <기준>...HEAD` 범위만 넘기고, 어떻게 구현했는지는 넘기지 않는다. 지시문: "파일을 고치지 않는다. AC 마다 통과 / 실패 / 확인 못 함과 근거(`file:line`, 명령 출력)를 쓴다. 애매하면 통과로 두지 않는다."

   "실패"는 고치고 다시 판정받는다. "확인 못 함"은 체크하지 않고 알린다. Definition of Done 도 같은 방식으로 체크하고 커밋한다. 커밋하지 않은 변경을 남기지 않는다.
5. 보고: 한 일, AC 별 결과, 계획에서 바뀐 것, 확인하지 못한 것. 다음은 `/task end`.
