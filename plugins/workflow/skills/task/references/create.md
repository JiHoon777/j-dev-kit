# task create: 백로그 항목 하나 쓰기

`docs/backlog/`에 항목 파일 하나를 만든다. 형식은 [Backlog.md](https://github.com/MrLesk/Backlog.md) 에이전트 지침을 따르고 도구는 쓰지 않는다. 끝난 항목은 `/task end`가 `docs/done/`으로 옮긴다.

만들 것: `create` 뒤의 인자. `--survey`로 시작하면 맨 아래 "서베이 모드"를 따른다.

## 0. 처음일 때

`docs/backlog/README.md`가 없으면 아래 두 파일을 만들자고 제안하고, 승인을 받아 만든다. 라벨은 사용자에게 묻는다.

- `docs/backlog/README.md`: 2단계의 규칙, 라벨 목록, "아직 항목으로 만들지 않은 메모" 섹션
- `docs/backlog/_template.md`: 아래 템플릿. `<검증 명령>`은 프로젝트의 것으로 바꾼다.

```markdown
---
id: '000'
title: 무엇을 하는지 짧게
status: To Do
labels: [common]
priority: medium
dependencies: []
created_date: YYYY-MM-DD
updated_date: YYYY-MM-DD
---

## Description

목적과 배경을 짧게. 구현 방법은 쓰지 않는다. 이번에 빼는 것이 있으면 적는다.

## Acceptance Criteria

<!-- AC:BEGIN -->

- [ ] #1 화면이나 명령으로 확인할 수 있는 결과 한 문장
- [ ] #2 …

<!-- AC:END -->

## Definition of Done

<!-- DOD:BEGIN -->

- [ ] #1 `<검증 명령>` 통과
- [ ] #2 UI 가 바뀌었으면 브라우저에서 확인함

<!-- DOD:END -->

## Implementation Plan

만들 때는 비워 둔다. `/task start`가 승인된 계획을 적는다.

## Implementation Notes

작업하며 알게 된 것, 계획에서 바뀐 것.

## Final Summary

`/task end`가 쓴다: 바뀐 것, 리뷰에서 고친 것, 미룬 것, 그대로 둔 지적과 이유, 사용자가 바로잡은 것.
```

## 1. 무엇을 왜 하는지

- 요청에 목적과 결과가 있으면 바로 2단계로 간다.
- 모호하면 `superpowers:brainstorming` 스킬을 부른다. 단, 따로 설계 문서를 쓰지 않고(항목 파일이 그 문서다) 구현 계획으로 넘어가지 않는다. 질문은 정말 모르는 것만 한꺼번에 최대 3개, 나머지는 가정으로 Description 에 적는다.
- `docs/backlog/`와 `docs/done/`에 겹치는 항목이 있으면 만들지 않고 알린다.

## 2. 항목 쓰기 (Backlog.md 지침)

| 부분 | 규칙 |
| --- | --- |
| `title` | 할 일을 요약하는 짧은 제목 |
| Description | 목적과 배경. 구현 방법은 빼고, 이번에 빼는 것은 적는다 |
| Acceptance Criteria | 방법이 아니라 결과. 하나하나 확인할 수 있어야 한다. 나쁜 예: "`handleLogin()` 함수 추가" |
| 크기 | 한 번에 리뷰하고 머지할 만큼. 크면 나누고 순서를 `dependencies`에 |
| 의존성 | 번호가 더 작은 항목만 |
| Implementation Plan | 비워 둔다 |

- 번호: `docs/backlog/`와 `docs/done/`을 통틀어 가장 큰 번호 + 1, 세 자리. `README.md`와 `_`로 시작하는 파일은 항목이 아니다.
- 파일 이름: `<번호>-<라벨>-<짧은-영어-이름>.md`. `status: To Do`, 날짜는 오늘.
- 다른 세션이 동시에 항목을 만들 수 있다. 4단계에서 파일을 쓰기 직전에 번호를 다시 세고, 그새 같은 번호가 생겼으면 다음 번호로 바꿔 알린다.
- 메모에서 온 요청이면 만든 뒤 `docs/backlog/README.md`의 그 줄을 지운다.

## 3. 보여 주고 승인

쓰기 전에 내용을 보여 준다. 고쳐 달라면 고쳐서 다시 보여 준다.

## 4. 저장

1. 파일을 쓰고, 프로젝트에 포맷 명령이 있으면 통과시킨다.
2. 항목 파일과 지운 메모 줄, 그리고 0단계에서 새로 만든 파일이 있으면 그것까지 커밋한다: `docs(backlog): <번호> <제목>`. 서베이 모드의 첫 항목이면 보고서도 넣는다. 다른 변경은 넣지 않는다. 남겨 두면 `/task start`가 "커밋하지 않은 변경"에서 멈춘다. 푸시하지 않는다.
3. 경로와 번호를 알리고, 시작하려면 `/task start <번호>`(또는 "시작해 줘")라고 말한다.

## 서베이 모드 (`create --survey <목표> [자료…] [--internal]`)

자료를 하나씩 골라 넘기지 않는다. 목표를 받아 Claude 가 안쪽(저장소)과 바깥을 조사하고 무엇을 항목으로 만들지 고른다. 항목을 만들기만 하고 `start`를 부르거나 세션을 띄우지 않는다. 후보 개수는 정하지 않는다.

1. **목표 쪼개기:** 목표를 결과 한 문장("무엇이 나아지면 됐다고 하나")과 조사 질문 몇 개로 적고, 질문마다 각도(안쪽, 바깥)를 정한다. 목표가 좁으면 질문과 각도도 적게. 몇 줄로 보여 주고 승인을 기다리지 않고 2로 간다. 사용자가 끼어들어 고치면 따른다.
2. **자료 모으기:** 자료를 주지 않아도 안쪽과 바깥을 모두 찾는다.
   - 안쪽: 오류 로그, `docs/backlog/`·`docs/done/`, README 의 메모, 쓸 수 있으면 이슈 목록(`gh issue list`), 사용 데이터.
   - 바깥: 쓰는 도구·라이브러리의 공식 문서·변경 기록·이슈, 같은 일을 하는 다른 도구와 선례, 그 분야 실무자의 글·발표.
   - 사용자가 준 자료(파일·폴더 경로, 명령의 출력, URL)는 출발점이고 범위를 좁히지 않는다. 바깥은 사용자가 `--internal`이나 그런 말로 빼라고 할 때만 뺀다.
   - 검색은 짧고 넓은 검색어로 시작해 좁힌다. 공식 문서, 원저자의 글, 저장소 원문을 요약 글보다 앞에 둔다.
   - 각도마다 하위 에이전트(general-purpose)를 한 메시지에서 띄워 병렬로 모은다. 지시문에 넣을 것: 목표와 맡은 조사 질문, 출력 형식(아래 메모), 쓸 출처(위 안쪽·바깥 중 그 각도의 것), 경계(읽기만 한다. 메모 파일 말고는 쓰지 않는다. 명령은 읽기만 하는 것. 맡은 각도 밖으로 넓히지 않는다).
   - 에이전트는 자료마다 메모를 `.claude/.local/survey/<날짜>-<짧은 이름>/<각도>.md`에 쓰고 경로만 돌려준다. 메모: 무엇을 봤나, 짧은 원문 인용, 위치(`file:line`, 명령, URL), 읽은 날짜, **[직접]**(원문을 열어 읽음) 또는 **[검색]**(검색 결과 요약만 봄).
   - 날것을 직접 읽는다. 후보의 근거로 쓰는 주장은 메인 세션이 그 원문을 다시 열어 확인한다. 열지 못하면 **[검색]**으로 두거나 근거에서 뺀다. 명령은 읽기만 하는 것을 돌린다.
3. **후보 고르기:** 메모 → 범주 → 세기 순서로 한다.
   - 메모를 가로질러 범주로 묶는다. 범주는 메모에서 만들고 미리 정한 틀에 끼우지 않는다. 같은 원인으로 보이는 자료는 한 범주로 묶고 근거 위치를 모두 적는다.
   - 범주마다 근거 수를 센다.
   - 새로 읽은 자료가 범주를 더하지 않으면 수집을 멈춘다. 더하면 그 범주 쪽을 더 읽는다(2).
   - 목표에 맞는 범주만 후보로 올린다. 후보는 해법이 아니라 문제·필요로 적고, 해법은 그 아래 한 줄로. 후보마다 크기(근거 수, 몇 곳에서)와 목표에 닿는 정도를 한 줄씩 붙인다. 점수 공식은 만들지 않는다.
   - 버그 제보에서 온 후보는 기준 브랜치에서 재현해 본다. 근거에 재현한 방법, 또는 재현하지 못했다는 것을 붙인다.
     - 이 폴더에서는 읽기만 하는 방법으로 재현한다. 설치·빌드가 필요하면 임시 워크트리(`git worktree add <임시 경로> <기준>`)에서 하고 끝나면 지운다(`git worktree remove <임시 경로>`). 끝나면 `git status --short`가 비어 있는지 본다.
4. **거르기:** 후보를 보이기 전에, 이 세션이 아닌 새 general-purpose **판정 에이전트** 하나에 후보 목록, 메모 파일 경로, `docs/backlog/`·`docs/done/` 경로만 넘긴다. 모델은 이 세션과 같다. 지시문: "파일을 고치지 않는다. 후보마다 근거가 주장을 받치는지(원문을 열어 본다), 이미 있는 항목이나 이미 고쳐진 것과 겹치는지, 출처가 1차인지 보고 통과 / 근거 약함 / 탈락과 이유를 쓴다. 탈락은 근거가 주장과 어긋나거나, 이미 있는 항목·이미 고쳐진 것과 겹치거나, 출처가 없을 때만이다. 사실은 맞는데 그 영향을 보여 주는 1차 출처가 없거나 2차 출처뿐이면 근거 약함이다." 근거 약함은 후보에 남기고 그 표시와 이유를 붙인다. 탈락한 후보는 버리지 않고 "제안하지 않는 것"에 이유와 함께 둔다. 사실을 확인한 후보를 "영향의 1차 출처가 없다"는 것만으로 떨어뜨리면, 사용자가 고를 만한 후보가 보이지 않게 된다.
5. **보고서:** `.claude/.local/reports/<날짜>-<짧은 이름>.md`에 쓴다.
   - 확인 날짜와 표기(**[직접]**, **[검색]**)
   - 결론 요약
   - 후보 표: 문제·필요, 해법 한 줄, 근거(위치와 [직접]/[검색]), 크기, 목표에 닿는 정도, 됐는지 확인할 수단(명령, 화면, 수치)
   - 제안하지 않는 것과 이유
   - 읽지 못한 것
6. **한 번에 보여 주기:** 보고서 경로와 후보 표를 보여 주고 고르게 한다.
7. **쓰기:** 고른 후보만 2단계 규칙대로 쓴다. 확인 수단은 그 항목의 Acceptance Criteria 에 넣는다. 쓴 항목들을 한꺼번에 보여 주고 한 번 승인받는다(3단계). 그다음 항목마다 4단계대로 번호를 다시 세어 쓰고 따로 커밋한다. 고르지 않은 후보는 쓰지 않는다.
   - 고른 후보가 있으면 보고서를 `docs/backlog/references/`로 옮기고, 항목마다 Description 에 그 경로를 근거로 적고, 첫 항목 커밋에 보고서를 함께 넣는다. 고른 것이 없으면 보고서는 `.claude/.local/reports/`에 둔다.
