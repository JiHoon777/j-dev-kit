# task end: 리뷰하고 머지하기

작업 브랜치의 변경을 리뷰하고, 사용자가 정한 것을 고치고, 항목을 닫고, 사용자가 고른 방식으로 마무리한다.

프로젝트 CLAUDE.md 에 PR·푸시 규칙이 있으면 따른다. 시작할 때 `git branch --show-current`, `git status --short`, `git log --oneline <기준>..HEAD`, `git diff --stat <기준>...HEAD`로 상태를 본다.

## 1. 시작할 수 있는지

하나라도 해당하면 멈추고 알린다.

| 확인 | 해당하면 |
| --- | --- |
| 브랜치가 `w/`로 시작하지 않는다 | 어느 브랜치인지 묻는다 |
| 브랜치 이름과 맞는 항목 파일이 없다 | 어느 항목인지 묻는다 |
| 커밋하지 않은 변경이 있다 | 커밋할지 버릴지 묻는다. 스스로 버리지 않는다 |
| `<기준>...HEAD`에 변경이 없다 | 리뷰할 것이 없다고 말한다 |

항목 파일을 읽는다. 이미 `docs/done/`에 있으면 6단계부터 한다.

## 2. 스택 점검

쓸 수 있는 스킬 중 이름이 `-end-check`로 끝나는 것을 전부 Skill 도구로 부른다(예: `server:server-end-check`). 각 점검은 변경이 그 영역을 건드렸을 때만 검사 도구를 돌리고 돌려준다:

- **실패:** 판정을 거치지 않고 4단계의 지적 목록에 🔴 로 넣는다. 검사 도구의 출력이 근거다.
- **리뷰에 넣을 에이전트:** 3단계에 더한다(근거와 함께).
- **고친 뒤 할 것:** 5단계에서 한다.

**테스트가 고친 것을 증명하나:** 스택 점검 다음, 리뷰 전에 이번 브랜치에서 더하거나 바꾼 테스트를 기준 브랜치의 소스에 대고 돌린다. 스크립트가 파일을 잠시 바꾸니 리뷰 에이전트와 함께 돌리지 않는다.

- 테스트 파일 하나를 돌리는 명령을 프로젝트(CLAUDE.md, package.json 스크립트, 테스트 설정)에서 정하고, 파일 자리를 `{}`로 둔다(예: `pnpm vitest run {}`, `pytest {}`, `bash {}`).
- `bash <task-scripts>/base-tests.sh <기준> '<그 명령>'`. 테스트 파일을 이름으로 못 고르는 프로젝트면 파일을 뒤에 붙이고, 이름 규칙 밖의 테스트 도우미(예: `src/testing/`)가 있으면 `BASE_TESTS_KEEP='<경로 정규식>'`을 앞에 붙인다.
- 출력의 `기준에서도 통과: <파일>`은 판정을 거치지 않고 4단계 지적 목록에 🟡 "고친 것을 증명하지 못함 — 고친 코드 없이도 통과한다"로 넣는다. 스크립트 출력이 근거다.
- 출력이 `바뀐 테스트 없음.`이고 끝 값이 2 면(소스가 바뀌었는데 테스트를 못 찾음) 4단계에서 사용자에게 "확인 못 함 — 이 브랜치의 테스트를 찾지 못했다(이름 규칙 밖이면 파일을 붙여 다시 돌린다)"로 보인다. 이름 규칙 밖의 테스트 파일이 있으면 파일을 붙여 다시 돌린다.
- 명령을 정할 수 없거나 그 밖의 이유로 끝 값이 2 면 "확인 못 함"과 이유를, `HEAD 에서 실패: <파일>` 줄은 끝 값과 상관없이 그 테스트를 "확인 못 함"으로 `Implementation Notes`에 적고 넘어간다.

## 3. 리뷰 (에이전트, 한 메시지에서 동시에)

| 에이전트 | 언제 | 하는 일 |
| --- | --- | --- |
| general-purpose | 항상 | `code-review` 스킬을 부른다. 대상은 현재 브랜치. `--fix`, `--comment` 없이, 노력 수준은 주지 않는다 |
| general-purpose | 인증·인가, 입력 처리, 비밀 값, 외부 호출, 파일·명령 실행이 바뀌었을 때 | `security-review` 스킬을 부른다. 띄우기 전에 `git symbolic-ref refs/remotes/origin/HEAD`가 실패하면 `git remote set-head origin -a` |
| 스택 리뷰 에이전트 (`frontend:frontend-reviewer`, `frontend:design-reviewer`, `server:api-reviewer`, `server:supabase-reviewer`) | 2단계가 돌려줬을 때 | 그 에이전트의 기준대로 |

**모델:** 이 세션이 Fable 이면 위 에이전트 모두에 Agent 도구의 `model`을 한 단계 낮은 최신 모델(지금은 `opus`)로 준다. Opus 이하면 `model`을 주지 않는다(이 세션과 같은 모델로 돈다).

에이전트는 이 대화를 볼 수 없으니 지시문에 넣는다:

1. 범위: `git diff <기준>...HEAD`, 항목 파일 경로, CLAUDE.md. 스택 리뷰 에이전트에게는 점검이 함께 돌려준 근거도.
2. 파일을 고치지 않고 커밋하지 않는다. 원격·운영 환경에 닿지 않는다. general-purpose 에이전트는 서버를 띄우지 않고 빌드·검증 명령을 돌리지 않는다(리뷰어들이 같은 폴더에서 동시에 돈다). 스택 리뷰 에이전트의 서버 띄우기, 도구 설치, 로컬 재현은 그 에이전트의 기준이 허락할 때만 한다.
3. 원칙: `docs/review-principles.md`가 있으면 그 내용. 원칙에 어긋나 보이는 지적도 보고하되, 어느 원칙과 부딪히는지 함께 적는다.
4. 보고: 찾은 문제를 모두, 확인한 것과 확인 못 한 것을 나눠서 `file:line — 문제 — 고칠 방법`. 점수는 쓰지 않는다.
5. 스킬을 부를 수 없으면 대신 지어내지 말고 그렇다고 보고한다.

## 4. 판정하고 보여 주고 묻기

모두 돌아오면 이 세션은 지적을 고르지 않는다. 보고서 원문 전부를 새 general-purpose **판정 에이전트** 하나에 넘긴다. 모델은 이 세션과 같다. 지시문:

- 범위: 3단계의 1과 같고, `docs/review-principles.md`도.
- "파일을 고치지 않는다. 중복을 합치고, 지적마다 코드에서 확인해 타당 / 틀림을 근거(`file:line`)와 함께 판정한다. 원칙에 어긋나는 지적은 틀림이다. 이 변경 전부터 있던 문제는 기존 문제로 따로 센다. 타당한 것은 아래 🔴 / 🟡 / ⚪ 로 나눈다. 타당한 지적과 같은 종류가 `docs/done/` 항목의 Final Summary `리뷰에서 고친 것`에 있거나 이번 보고서들에서 여러 곳에 나오면 🔁 와 근거(항목 번호나 위치들)를 붙인다."

사용자에게는 타당하다고 판정된 지적과 2단계 스택 점검 실패·테스트 확인 결과("확인 못 함 — 테스트를 찾지 못했다" 포함)만 보인다. 틀림으로 판정된 것은 "판정에서 뺀 것 N건", 기존 문제는 "기존 문제 N건"으로 개수만 적는다. 점수는 보여 주지 않는다. `git diff <기준>...HEAD -- CLAUDE.md`에서 검증 명령 줄이 바뀌었으면 지적과 따로 "이 브랜치가 검증 명령을 바꿨다(이전 → 새). 검증 Stop 훅은 머지 전까지 기준 브랜치의 명령으로 판정한다"를 보인다. 판정하는 명령이 바뀌는 것이니 사람이 본다.

```markdown
🔴 꼭 고칠 것 — 확인된 버그, 보안 문제, 데이터 손실, AC 위반, 스택 점검 실패
- src/a.ts:12 — 문제 — 고칠 방법 (code-review)
- src/b.ts:30 — 문제 — 고칠 방법 (code-review) 🔁 006 에서도 고침

🟡 고려 — 실제 문제지만 머지를 막지는 않음
- …

⚪ 사소함 4건 (보려면 말씀해 주세요)
```

묻는 것은 한 번: "🔴 는 지금 고칩니다. 🟡 는 지금 / 나중(새 항목) / 그대로 중 어떻게 할까요?" 🔁 가 붙은 지적이 있으면 "🔁 는 고치는 것과 함께 린트 규칙·테스트·타입으로 막기(새 항목)도 고를 수 있습니다"를 덧붙인다. 같은 실수는 글로 당부하기보다 자동 검사로 막는 것이 낫다. 🔁 가 없는 지적에는 이 선택지를 붙이지 않는다. 사용자가 원하면 하나씩 정한다. 에이전트가 권한, CLAUDE.md, `.claude/` 설정을 바꾸자고 하면 바꾸지 않고 제안으로 전한다.

답을 받기 전에는 아무것도 고치지 않는다.

## 5. 고치기

- `superpowers:receiving-code-review` 스킬을 부르고 따른다(지적을 코드에서 확인하고, 틀린 지적은 이유를 대고 적용하지 않는다).
- 동작을 바꾸는 수정은 실패하는 테스트를 먼저 쓴다.
- 판단이 필요한 수정(설계를 바꾸거나 여러 파일에 걸치는 것, 고칠 방법이 정해지지 않은 것)은 이 세션이 직접 고친다. 변경을 만든 세션이 그 맥락을 가장 잘 안다.
- 위치와 고칠 내용을 지적이 정확히 말해 판단이 남지 않는 기계적인 수정은 모아 에이전트 하나(Agent 도구 `model: sonnet`, `effort: high`)에 맡길 수 있다. 정해진 일은 작은 모델로도 된다. 맡길지는 이 세션이 정한다. 예를 들어 수가 적거나 판단이 필요한 수정과 같은 파일을 함께 고쳐야 하면 직접 고친다. 맡기면 지시문에 그 지적 목록, 항목 파일 경로, "동작을 바꾸는 수정은 실패하는 테스트를 먼저 쓴다", "목록 밖의 것은 고치지 않고 커밋하지 않는다"를 넣는다.
- 고친 뒤 판정은 고친 쪽의 보고로 하지 않는다. 검증 명령을 돌리고, 고친 지적마다 고쳐졌는지는 새 general-purpose 판정 에이전트에 항목 파일 경로, 고친 지적 목록, `git diff HEAD`와 `git status --short`(아직 추적하지 않는 새 파일이 보이게)만 넘긴다. 지시문: "파일을 고치지 않는다. 지적마다 고쳐짐 / 안 고쳐짐과 근거(`file:line`)를 쓴다. 애매하면 고쳐짐으로 두지 않는다." UI 는 아래 "고친 뒤 할 것"의 `frontend-evaluator`가 판정한다.
- 같은 지적이 세 번 고쳐도 남으면 더 고치지 않고 멈추고, 그 지적과 시도한 것을 사용자에게 알린다. 같은 고치기를 되풀이하기보다 사람이 접근을 다시 보는 편이 낫다.
- 2단계의 "고친 뒤 할 것"을 고친 부분에 대해 한다(예: 고친 화면만 브라우저 확인). 수정이 스택 점검 영역을 건드렸으면 그 `*-end-check`를 다시 부른다.
- "나중"과 "막기"는 `task` 스킬을 `create <지적과 근거> --here`로 불러 새 항목을 만든다. "막기"는 막을 수단(린트 규칙·테스트·타입 중)도 넘기고, 지적 자체는 사용자가 고른 대로 고친다. 사용자가 이미 골랐으니 create 3단계의 승인은 항목 내용만 보여 주고 받는다.
- 한 것과 본 것을 `Implementation Notes`에 적고 커밋한다.

## 6. 검증하고 항목 닫기 (Backlog.md definition of done)

1. 검증 명령을 새로 한 번 돌린다. `### Baseline`에 없던 실패가 있으면 멈추고 알린다.
2. 항목의 `Final Summary`를 쓴다: 바뀐 것, 리뷰에서 고친 것, 미룬 것(새 항목 번호), 그대로 둔 지적과 이유, 사용자가 바로잡은 것(`start`·`end` 동안, 한 줄씩).
3. **원칙:** 그대로 둔 이유나 사용자가 바로잡은 것이 다른 항목에도 통하면 `docs/review-principles.md`에 한 줄로 더한다(`- 원칙 — 이유 (항목 번호)`). 같은 원칙이 이미 있으면 더하지 않는다.
4. 모두 갖춰야 닫는다. 하나라도 빠지면 멈추고 알린다.
   - [ ] Acceptance Criteria 모두 체크
   - [ ] Definition of Done 모두 체크
   - [ ] `Final Summary`를 썼다
5. 작업 브랜치에서:

```bash
# 항목 파일의 status: Done, updated_date 를 오늘로 바꾼 뒤
git mv docs/backlog/<파일> docs/done/<파일>
git add -A docs/
git commit -m "docs(backlog): <번호> done"
git status --short   # 비어 있어야 한다
```

## 7. 마무리

`superpowers:finishing-a-development-branch` 스킬을 부르고 따른다. 이 스킬은 선택지를 보여 주고 사용자의 답을 기다린다. 그것이 머지 승인이다. 스킬에 알려 준다:

- 검증 명령은 6단계에서 방금 통과했다. 기준 브랜치는 프로젝트 설정의 것이다.
- 워크트리를 쓰지 않았으면 지울 워크트리가 없다.
- 이 세션이 워크트리에서 일했으면(`git rev-parse --path-format=absolute --git-dir --git-common-dir`의 두 줄이 다르면, 예: `start`가 띄운 하위 세션), 머지와 정리는 이 줄이 스킬의 해당 단계보다 우선한다. 기준 브랜치는 기준 폴더(`git worktree list`의 첫 줄)에 있으니 머지는 `git -C <기준 폴더> merge …`처럼 거기서 돌린다. 머지 전에 기준 폴더가 기준 브랜치에 있고(`git -C <기준 폴더> branch --show-current`) 깨끗한지(`status --short`) 보고, 아니면 멈추고 알린다. 세션이 그 워크트리 안에 있으니 워크트리와 브랜치는 이 세션에서 지우지 않는다. 로컬 머지를 골랐으면, 세션을 보관하면 앱이 워크트리를 정리하고, 그렇지 않으면 기준 폴더에서 `git worktree remove <워크트리 경로>`와 `git branch -d w/<이름>`을 돌리면 된다고 알린다. PR 이나 그대로 두기를 골랐으면 워크트리를 남긴다.
- PR 을 만들 수 없으면(CLAUDE.md 에 그렇게 적혀 있거나 `gh auth status`가 실패하면) 그렇다고 말한다.
- 기준 브랜치에 upstream 이 없으면 `git pull`을 건너뛴다.
- 푸시는 사용자가 요청할 때만.

끝나면 보고한다: 머지된 커밋, 옮긴 항목 파일, 새 항목, 남은 `To Do` 항목(`README.md`와 `_`로 시작하는 파일은 항목이 아니다).
