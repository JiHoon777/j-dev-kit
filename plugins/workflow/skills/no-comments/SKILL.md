# No comments

> 원문: `cursor/plugins`의 `pstack/skills/no-comments/SKILL.md` (MIT, Lauren Tan). Cursor 이름을 Claude Code 것으로 바꿨다.

**언제:** 리뷰 전, 코드가 바뀌었을 때. 사용자가 "주석 정리해", "no comments"라고 할 때.

comment-sicko 를 띄운다. 받아들인 지적을 처리한다.

comment-sicko 의 새 눈을 따른다.

## 범위

부른 쪽이 준 파일이나 diff 를 쓴다. 없으면 기준 브랜치(기본 `main`) 대비 지금 diff 를, 작업 트리까지 넣어 쓴다.

## 단계

1. `Agent` 도구로 `workflow:comment-sicko` 에이전트를 띄운다. 띄우기 전에 지금 상태의 스냅숏을 잡아 둔다(`git stash create`가 찍는 해시. 커밋하지 않은 변경이 없으면 `HEAD`). 지시문의 첫 줄은 `먼저 <start 스킬 폴더의 절대 경로>/references/worker.md 를 읽는다.`이다. 범위와 `why` 스킬 본문의 절대 경로(`${CLAUDE_SKILL_DIR}/../why/SKILL.md`)를 넘긴다. 모델은 `start` 스킬의 `references/settings.md`의 `review` 역할을 따른다. 그 에이전트의 규칙을 지시문에 다시 적지 않는다.
2. 보고와 diff 를 살핀다. 다음은 받아들이지 않는다: 애플리케이션 코드를 고친 것, 범위를 벗어난 것, 예외로 보호되는 주석을 지운 것, 이유를 틀리게 적은 `MUST KILL`, 일부러 남긴 코드를 잘못으로 본 지적.
   - 우리 코드의 뜻밖의 동작을 짚은 모양 바꾸기 지적은 그대로 처리할 일이다. 그 주석을 되살리지 않는다.
   - 남기기는 우리가 바꿀 수 없는 것에 관한 주석이라는 증거가 있을 때만 살아남는다.
   - 범위 안에서 놓친 린트·TypeScript 억제를 다시 본다. 정확성이나 안전을 지키는 규칙의 억제는 처리할 `MUST KILL`이다.
   - 지운 것을 되살리는 것은 정확한 예외와 범위 안의 증거가 있을 때뿐이다.
   - 근거가 얇은 `IMPORTANT`·`do not remove` 지우기나 남기기를 받아들이기 전에, 그 심볼을 따라가거나 `why` 스킬을 돌린다. 지우기가 애매하면 되살리지 않는다. 남기기가 반박되거나 여전히 애매하면 지운다.
   - 받아들이지 않은 보고는 되돌리고, 무엇이 틀렸는지 적어 한 번 다시 돌린다. 되돌릴 때는 comment-sicko 가 건드린 파일만 1의 스냅숏으로 되돌린다(`git checkout <스냅숏> -- <파일>`). 사용자의 커밋하지 않은 변경을 지우지 않는다. 두 번째도 받아들일 수 없으면 열린 것으로 보고하고 `no-comments`를 실패로 끝낸다.
3. 받아들인 사소한 지적은 바로 고친다: 죽은 경로를 지우고, 매개변수를 빼고, 진짜 API 를 쓴다. 모양을 정해야 하는 수정이 있으면 받아들인 지적 묶음과 주변 코드에 `architect` 스킬을 한 번 돌린다. 스케치에서 멈춘다. architect 는 모양을 정하고, 4단계가 구현한다.
4. 범위 안에서 가장 작은 근본 원인 수정을 구현한다. 이름이 나온 임시방편을 모두 걷어 낸다. 근본 원인이 범위 밖이면 범위 안의 가장 작은 수정을 넣고 나머지는 열린 것으로 보고한다. `principle-fix-root-causes`와 `principle-redesign-from-first-principles` 스킬은 방향만 잡아 준다. 어느 쪽도 범위를 넓히거나 범위 밖의 사례를 고쳐도 된다는 뜻이 아니다. 증상을 막는 가드를 덧대지 않는다.
5. 제약 주석은 `do not remove`, `do not change wording`, `talk to X before changing` 같은 말을 한다. 우리가 바꿀 수 없는 것에 관한 남기기는 둔다. 나머지에는 범위 안에서 가장 싼 타입, 런타임 검사, 테스트, CI 린트를 내놓는다.
   - 사용자가 직접 불렀으면 승인을 기다린다. 승인하면 박고 나서 주석을 지운다. 승인하지 않으면 주석을 지우고, 제약을 열린 것으로 보고하고, 범위 밖의 일을 스케치한다.
   - `start` 흐름 안이거나 사람이 자리를 비운 실행이면 기다리지 않는다. 부른 쪽이 미리 승인해 뒀으면 박고 나서 주석을 지운다. 아니면 주석을 지우고, 제약과 박을 방법을 마지막 메시지의 "나중" 후보로 올린다.
6. 보고한다: 지운 주석 수, 되살린 주석, 다시 돌린 횟수, architect 스케치, 고친 것, 내놓은 박기 제안, 박은 것, 강제되지 않는 제약, 그 밖의 열린 일.
