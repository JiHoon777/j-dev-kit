# 백로그 생성

## 저장 위치와 형식

프로젝트 CLAUDE.md 에 `backlog:` 경로가 있으면 그것을 쓴다. 없으면 아래가 기본이다.

```
docs/backlog.md            항목 목록. 한 줄에 한 항목
docs/backlog/<ID>.md       항목별 상세(브리프)
```

`docs/backlog.md` 가 없으면 아래 틀로 만든다. 이미 있으면 절대 덮어쓰지 않는다.

```markdown
# Backlog

## 사용법
- 한 줄에 한 항목: `- [ ] B-001 제목. → [상세](backlog/B-001.md)`
- 상태: `[ ]` 대기, `[~]` 진행 중, `[x]` 완료(날짜·메모), `[-]` 취소(이유)
- ID 는 다시 쓰지 않는다. 다음 ID 는 파일 맨 끝에 적는다.
- 섹션 안의 순서가 우선순위다. 위가 먼저.

## Now
## Backlog
## Bugs
## Inbox
아직 정의가 덜 된 아이디어.
## Done

---
다음 ID: B-001
```

파일에 `## 사용법` 섹션이 있으면 그 규칙이 이 스킬보다 우선한다.

## 절차

1. **아이디어만 적어 두려는 것인지 본다.** "나중에 생각해 볼 것" 수준이면 질문 없이 Inbox 에 한 줄만 넣고 끝낸다. 상세 파일은 만들지 않는다.
2. **모호한 점을 질문으로 좁힌다.** 원하는 결과, 왜 필요한지, 범위 밖인 것, 예외 상황, 선행 항목이 있는지. 요구사항을 지어내지 않는다. 지금 답할 수 없는 질문은 상세 파일에 그대로 적고 항목을 Inbox 에 둔다.
3. **스택을 판별한다.** CLAUDE.md 의 `stack:` 을 보고, 없으면 `supabase/` 폴더(supabase), 프론트 프레임워크 의존성(frontend), 서버 프레임워크(server)로 추정한다. 여러 개면 전부 해당한다.
4. **상세 파일 초안을 쓴다.**
   ```markdown
   # B-0NN 제목

   **무엇을**: 한두 문장.
   **왜**: 누구에게 어떤 이득이 있는지.

   ## 수용 기준
   - [ ] AC1: <상황>에서 <행동>하면 <눈에 보이는 결과>.
   - [ ] AC2: …

   ## 범위 밖
   ## 기술 메모
   ## 열린 질문
   ```
   - 수용 기준은 참·거짓으로 판정할 수 있는 동작으로 쓴다. 구현 방법을 쓰지 않는다. 정상 흐름, 대표적인 실패·빈 상태, 권한 규칙을 덮는다.
   - 범위는 사용자가 말한 그대로 쓴다. "전부 바꾼다"면 지금 찾은 파일 목록이 아니라 "X 를 쓰는 곳이 남지 않는다"처럼 쓴다. 파일 목록은 금방 낡는다.
   - 해당 스택의 기준을 빠뜨리지 않는다.
     - **frontend**: 로딩·빈 상태·에러 상태가 어떻게 보이는지.
     - **supabase**: 새 테이블·컬럼이면 RLS 정책(누가 읽고 쓰는지)을 기준으로 넣는다. 스키마 변경이면 마이그레이션이 있어야 한다는 것도.
     - **server**: 바뀌는 API 의 요청·응답 형식과 에러 응답.
5. **크기를 점검한다.** 독립적으로 가치 있는 동작이 여럿 섞였거나 수용 기준이 8개를 넘으면 나누자고 제안한다. 나눌지는 사용자가 정한다.
6. **넣을 위치를 제안한다.** 기본은 섹션 맨 끝이지만, 기존 항목과 비교해 급한 정도·의존 관계로 위치를 제안하고 이유를 한 줄로 말한다. 버그는 Bugs.
7. **쓰기 전에 확인받는다.** 목록 한 줄과 상세 초안을 보여 주고 승인받은 뒤 쓴다.
8. **쓴다.** 상세 파일을 만들고, `docs/backlog.md` 에 한 줄을 넣고, 맨 끝의 다음 ID 를 올린다. 파일 전체를 다시 쓰지 않고 해당 줄만 고친다.
9. **커밋.** 바뀐 파일이 백로그뿐이면 `docs: B-0NN 추가` 로 따로 커밋해도 되는지 묻는다. 다른 작업 변경이 섞여 있으면 커밋하지 않고 그 작업과 같이 커밋되게 둔다.
10. 무엇을 어디에 넣었는지 한 줄로 보고한다.
