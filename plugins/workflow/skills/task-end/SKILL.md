# 작업 종료

프로젝트의 CLAUDE.md·AGENTS.md 에 작업 규칙이 있으면 그쪽이 이 스킬보다 우선한다. 백로그 위치와 형식은 `backlog-create` 스킬을 따른다(기본 `docs/backlog.md`, 상세는 `docs/backlog/<ID>.md`).

## 규칙

- **아래 단계는 전부 한다. 해당 없는 단계만, 이유를 남기고 건너뛴다.** "선택 사항"이라며 빼거나 단계를 합치지 않는다.
- **완료는 증거로 판단한다.** 수용 기준마다 실제로 돌린 테스트나 직접 확인한 결과가 있어야 한다. 실패했거나 예전 결과는 증거가 아니다. "구현했다"는 말은 증거가 아니다.
- 커밋·푸시·PR 은 사용자 승인 뒤에만 한다.

## 1. 대상과 스택

1. 대상 항목을 정한다. ID 를 받았으면 그것, 아니면 Now 에 있는 `[~]` 항목. 여러 개면 묻는다. 백로그 없이 한 작업이면 diff 를 대상으로 하고 수용 기준 확인(4)은 사용자가 말한 목표로 대신한다.
2. 스택을 판별한다. CLAUDE.md 의 `stack:` → 없으면 `supabase/` 폴더(supabase), 프론트 프레임워크 의존성(frontend), 서버 프레임워크(server). **여러 개면 3의 해당 섹션을 전부 적용한다.**

## 2. 검증과 리뷰

1. 프로젝트에 있는 것을 돌린다: 타입 체크, 린트, 테스트, 빌드. 없는 것은 "없음"으로 남긴다. 실패하면 고치고 다시 돌린다.
2. 기준 브랜치와의 diff 를 처음부터 다시 읽는다. 버그, 빠뜨린 처리, 남은 디버그 코드, 쓰지 않는 코드를 찾아 고치고 1을 다시 돌린다.

## 3. 스택별 점검 (해당하는 것 전부)

### frontend
- 바뀐 화면마다 로딩·빈 상태·에러 상태, 긴 텍스트·많은 데이터, 좁은 화면, 새로고침·뒤로 가기 뒤 상태를 사용자 확인 체크리스트로 만든다.
- 시안이나 기획이 있으면 그대로 보이는지·동작하는지를 체크리스트에 넣는다. 없으면 무엇을 기준으로 확인했는지 적는다.
- 브라우저는 사용자가 요청할 때만 연다.

### supabase
- 스키마를 바꿨으면 마이그레이션 파일이 변경에 들어 있는지, 로컬에서 처음부터 적용(`supabase db reset`)해도 깨지지 않는지 확인한다.
- 타입 파일을 다시 생성했는지 확인한다.
- 새 테이블·뷰에 RLS 가 켜져 있고 정책이 있는지, 다른 사용자의 행이 보이지 않는지 확인한다.
- service role 키가 클라이언트 코드나 변경에 들어가지 않았는지 확인한다.

### server
- 바뀐 API 의 요청·응답 형식이 문서·타입과 맞는지, 이를 쓰는 쪽이 깨지지 않는지 확인한다.
- 새 환경변수는 예시 설정 파일(`.env.example` 등)에 이름만 더한다. 값은 커밋하지 않는다.
- 마이그레이션이 있으면 되돌리는 방법을 확인한다.
- 에러 응답과 로그에 민감한 값이 찍히지 않는지 본다.

## 4. 수용 기준 확인

상세 파일의 수용 기준을 하나씩 판정한다: **통과**(증거와 함께), **실패**, **미확인**(확인할 방법이 없었음). 사용자가 직접 봐야 하는 것은 3의 체크리스트와 함께 보여 주고 결과를 받는다.

- 전부 통과 → 5로.
- 실패나 미확인이 남음 → 완료 처리하지 않는다. 고칠지, 이번 범위에서 빼고 새 항목으로 넘길지 묻는다. 넘기는 것은 `backlog-create` 형식으로 만든다.
- 이번 세션에 못 끝냄 → 상세 파일 끝에 `## 인계`(한 것, 남은 것, 건드린 파일, 마지막 확인 결과, 다음 행동)를 남기고 `[~]` 그대로 둔다. 여기서 멈춘다.

## 5. 완료 처리

1. 상세 파일의 수용 기준을 체크하고, 아래에 `## 완료` 로 날짜와 증거 요약을 적는다.
2. 백로그에서 항목을 `[x] … (YYYY-MM-DD, 한 줄 메모)` 로 바꿔 Done 맨 위로 옮기고 Now 의 줄을 지운다.
3. 작업 중 미룬 일, 리뷰에서 나중으로 넘긴 일은 `backlog-create` 형식으로 Inbox 나 Backlog 에 넣는다.

## 6. 커밋 · 푸시 · PR (승인 후)

1. 커밋 메시지와 포함할 파일을 보여 주고 승인받는다. 백로그 변경은 작업과 같은 커밋에 넣는다. 프로젝트 커밋 규칙이 없으면 `<type>: <요약> (B-0NN)`.
2. `git push -u origin <브랜치>`.
3. PR 제목과 설명(무엇을, 왜, 수용 기준별 확인 결과, 확인 못 한 것)을 보여 주고 승인받아 만든다. GitHub 이면 `gh pr create`. 도구나 인증이 없으면 설명문과 웹 생성 링크를 넘긴다.

## 7. 요약

단계마다 한 줄씩 표로 보고한다: 단계, 결과(완료·건너뜀·실패), 근거나 건너뛴 이유. 빈 줄이 있으면 끝난 것이 아니다.
